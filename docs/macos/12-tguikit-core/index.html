1. 키 윈도우가 아닌 윈도우로 전체 기능의 AppMenu를 직접 그리기

#12-01 · TelegramSwift · AppKit · 리포트 선정 12-1 · 검증 방식: 소스 분석

소스: TelegramSwift:packages/TGUIKit/Sources/AppMenuController.swift L607–L681

무엇을 했나요: NSMenu의 네이티브 팝업 흐름을 호출하지 않아요. 대신 이렇게 해요.

  • 메뉴 계층마다 윈도우를 하나씩 만들어요. 이 윈도우는 투명하고, 키 윈도우(키보드 입력을 받는 윈도우)가 아니며, 메인 윈도우도 아니에요.
  • 윈도우 레벨은 .screenSaver로 설정해요.
  • 메뉴 내용은 MenuView와 테이블이 그려요.

왜 이렇게 했나요: 네이티브 NSMenu로는 커스텀 행, 동적 검색, 다단계 애니메이션을 담기 어려워요. 독립된 윈도우를 쓰면 하위 메뉴가 따로 레이아웃돼요. 또 메뉴가 Window의 전역 이벤트 디스패치를 재사용할 수 있어요.

아래 도표는 메뉴 하나가 전용 윈도우와 전역 이벤트 디스패치에 연결되는 구조를 보여 줘요.

핵심 코드 발췌

대가와 위험: .screenSaver는 메뉴를 매우 높은 레벨에 올려 놓아서 다른 오버레이를 가릴 수 있어요. 이 방식은 접근성과 시스템 메뉴에 대한 기대를 깨뜨릴 수 있어요. 또 유지보수하는 사람은 여러 윈도우의 포커스와 닫기도 처리해야 해요.

증거 체인 #12-01 (개별 검증 안 함)

  • 소스 분석: TelegramSwift 고정 커밋에서 행 단위로 확인했어요. 소스 위치는 총 1곳이에요.
  • 리포트 요약(구현 방법): Window + MenuView를 자체 구축해서 레이아웃과 이벤트를 독립시켜요.
  • 바이너리 검증: 이 항목은 개별 대조하지 않았어요. REA 주제 노트에 대조를 마친 20개 항목이 나열되어 있어요.

무엇을 했나요: VisualEffect는 updateLayer()가 끝날 때마다 글래스 서브트리(글래스 효과를 이루는 레이어 트리)를 검사하고 이렇게 정리해요.

왜 이렇게 했나요: 일반 NSVisualEffectView는 시스템 머티리얼의 배경과 추가 효과를 유지해서 Telegram의 테마에 맞추기 어려워요. 그래서 이렇게 정리하면 시스템 글래스가 투명한 블러 바탕판으로 격하되고, 색조는 커스텀 overlay가 맡아요.

아래 도표는 글래스 서브트리를 투명한 블러 바탕판으로 줄이는 순서를 보여 줘요.

핵심 코드 발췌

대가와 위험: AppKit이 보장하지 않는 레이어 순서, 레이어 이름, 필터 서술에 기대고 있어요. backdrop, Backdrop, filters의 조합은 새 시스템에서 작동하지 않을 수 있어요. 코드는 최소 버전을 macOS 10.13으로 보호하지만 호환성 최후 대비책(폴백)은 없어요.

3. 우선순위로 Window 키보드 디스패치 재작성하기

#12-03 · TelegramSwift · AppKit · 리포트 선정 12-3 · 검증 방식: 소스 분석 · 태그: 텍스트와 입력

소스: TelegramSwift:packages/TGUIKit/Sources/Window.swift L781–L824

무엇을 했나요: Window.sendEvent(_:)는 먼저 responder(이벤트를 받을 객체)를 자동으로 골라요. 이어서 .All 전역 핸들러를 먼저 디스패치해요. 그 뒤의 규칙은 이래요.

  • 우선순위가 더 높은 전역 핸들러만 특정 키를 가로챌 수 있어요.
  • .supreme은 수정자 키 판정을 건너뛸 수 있어요.
  • 핸들러는 이벤트를 소비하거나, 거부하거나, AppKit에 넘길 수 있어요.

왜 이렇게 했나요: AppKit의 responder chain(이벤트를 받을 객체를 차례로 찾는 체인)은 모달, 내비게이션, 팝업, 안내 메시지의 명시적 우선순위를 표현하지 못해요. 이 방식은 Escape, Return, 전역 닫기 동작에 확정된 순서를 줘요. 또 낮은 계층의 페이지가 높은 계층 오버레이의 키 입력을 가로채지 못하게 막아요.

아래 도표는 Window.sendEvent(_:)가 키 이벤트를 처리하는 흐름을 보여 줘요.

핵심 코드 발췌

4. 조건부 updateLayer로 UIKit 변환 속성 흉내 내기

#12-04 · TelegramSwift · AppKit · 리포트 선정 12-4 · 검증 방식: 소스 분석 · 태그: Core Animation

소스: TelegramSwift:packages/TGUIKit/Sources/View.swift L109–L153

무엇을 했나요: View는 앵커 포인트, 변환, 하위 레이어 변환을 저장 속성으로 감싸요.

  • 속성이 바뀌면 updateLayer()를 직접 호출해요.
  • 속성이 하나라도 쓰일 때만 AppKit의 updateLayer 경로를 요청해요.

왜 이렇게 했나요: 이렇게 감싸면 NSView가 UIKit에 가까운 layer-transform API를 갖게 돼요. 조건부 wantsUpdateLayer는 모든 일반 뷰가 layer 업데이트를 타는 일을 피해요. 일반적인 방식은 각 호출 지점에서 layer를 직접 고쳐서 상태가 더 흩어져요.

핵심 코드 발췌

대가와 위험: setAnchorPoint의 구체적인 보정 구현은 다른 익스텐션에 있어요. 이 코드는 nil이 아닐 때만 값을 써요. 속성을 다시 nil로 설정해도 여기서는 기본 변환이 복원되지 않아요. 그래서 호출하는 쪽이 이 동작 방식을 알아야 해요.

5. 기본 View에서 좌표 뒤집기를 통일하고 암시적 애니메이션 끄기

#12-05 · TelegramSwift · AppKit · 리포트 선정 12-5 · 검증 방식: 소스 분석 · 태그: Core Animation

소스: TelegramSwift:packages/TGUIKit/Sources/View.swift L356–L397

무엇을 했나요: 모든 View는 기본적으로 layer-backed(뷰가 CALayer를 바탕으로 동작하는 방식)예요. flip(좌표 뒤집기)의 기본값은 true예요. 초기화에서는 이렇게 설정해요.

  • 레이어의 암시적 애니메이션을 꺼요.
  • 자동 서브뷰 크기 조정을 꺼요.
  • layer를 필요할 때만 다시 그리게 해요.

왜 이렇게 했나요: 각 설정에는 이유가 있어요.

  • 좌표를 뒤집으면 원점이 왼쪽 위가 되어서 UIKit 및 채팅 목록 레이아웃과 맞아요.
  • 암시적 애니메이션을 끄면 frame이나 색상을 한 번 갱신했을 때 통제할 수 없는 CA(Core Animation) 애니메이션이 일어나는 일을 피할 수 있어요.
  • onSetNeedsDisplay는 그리기 요청을 명시적 무효화로 모아요.

핵심 코드 발췌

대가와 위험:

  • 모든 하위 클래스가 뒤집힌 좌표를 물려받아요.
  • 네이티브의 뒤집히지 않은 NSView와 섞을 때는 명시적으로 변환해야 해요.
  • 기본 masksToBounds는 그림자와 경계를 벗어나는 애니메이션을 잘라 내요.

증거 체인 #12-05 (개별 검증 안 함)

  • 리포트 요약(구현 방법): 초기화 때 layer를 설정하고 layerContentsRedrawPolicy=.onSetNeedsDisplay를 지정해요.
  • 바이너리 검증: 이 항목은 개별 대조하지 않았어요. REA 주제 노트에 대조를 마친 20개 항목이 나열되어 있어요.

6. 빈 CAAction으로 계층 진입 알림 겸용하기

#12-06 · TelegramSwift · AppKit · 리포트 선정 12-6 · 검증 방식: 소스 분석 · 태그: Core Animation

소스: TelegramSwift:packages/TGUIKit/Sources/SimpleLayer.swift L19–L42

무엇을 했나요: SimpleShapeLayer는 CA의 onOrderIn과 onOrderOut 액션 조회를 가로채요.

  • 이 두 액션을 계층 생명주기 콜백(레이어가 계층에 들어가고 나갈 때 불리는 함수)으로 바꿔요.
  • 이벤트가 무엇이든 아무 동작도 하지 않는 CAAction을 반환해요.
  • 초기화 때 Retina 배율을 설정해요.

왜 이렇게 했나요: 일반 CALayer에는 didMoveToSuperview에 해당하는 공개 콜백이 없어요. 이 방식을 쓰면 레이어를 넣고 빼는 걸 감시하려고 별도의 NSView를 두지 않아도 돼요. 레이어 속성의 암시적 애니메이션도 한꺼번에 꺼요.

아래 도표는 SimpleShapeLayer가 CA의 액션 조회를 가로채는 흐름을 보여 줘요.

핵심 코드 발췌

대가와 위험: action(forKey:)는 이 레이어의 모든 기본 CA 애니메이션을 막아요. 그래서 호출하는 쪽이 애니메이션을 직접 추가해야 해요. kCAOnOrderIn과 kCAOnOrderOut이 언제 발동하는지는 계속 회귀 검증을 해야 해요.

증거 체인 #12-06 (개별 검증 안 함)
