REA 바이너리 검증

REA로 공식 Telegram for macOS 13.0을 분석해서, 소스 노트의 비공개 API 및 시스템 통합 기법 20건을 대조해요.

결론

대조한 20건 중 16건은 13.0 릴리스 빌드 바이너리에서 직접 증거가 나왔어요. 2건은 버전 차이예요. HackUtils 클래스가 사라졌고, iOS 쪽 MetalEngine의 메서드 교체가 macOS 버전에 들어왔어요. macOS 26.7에서는 비공개 경로 2건이 시스템 구조와 더는 맞지 않아요. 나머지 1건은 소스에 선언만 있고 한 번도 쓰이지 않은 클래스(CAPortalLayer)예요.

iOS 버전은 바이너리 검증을 하지 않았어요. App Store의 IPA는 FairPlay(Apple의 앱 암호화)로 암호화되어 있어서 복호화된 실행 파일을 합법적으로 얻을 수 없기 때문이에요.

macOS 바이너리는 telegram-ios 서브모듈의 공유 모듈(MetalEngine, Postbox, TelegramCore, MtProtoKit)을 정적으로 링크하고 있어요. 그래서 UI가 아닌 iOS 쪽 기법 일부는 간접적으로 검증됐어요.

아래 도표는 소스 노트 20건을 13.0 바이너리와 대조해 상태로 분류하는 전체 흐름을 보여 줘요.

방법

분석은 다섯 단계로 했어요.

  1. 메타데이터 읽기. rea inspect-plist와 rea inspect-signature로 Info.plist, 서명, entitlements를 읽어요.
  2. 로드 관계 해석.
    • rea trace-dylib-resolution --architecture arm64로 실행 루트 4개, 이미지 6개, 로드 엣지 193개를 해석했어요.
    • rea inspect-macho로 load command 113개, 의존 라이브러리 95개, import 심볼 4,587개를 읽었어요.
  3. 문자열과 클래스 테이블 스캔. rea execute-rizin-command로 arm64 슬라이스에서 iz, ic, iS, pd를 실행했어요. 그래서 데이터 세그먼트 문자열 117,189개, ObjC 클래스 6,393개, 섹션 테이블, 부분 디스어셈블리를 뽑았어요.
  4. 짧은 문자열 보충. Rizin의 izz와 / 검색은 REA의 -q -c 모드에서 출력이 없었어요. 알려진 문자열로 대조해서 도구의 한계라는 걸 확인했어요. 그래서 짧은 문자열은 직접 작성한 스크립트로 찾았어요. 스크립트는 두 가지를 했어요.
    • __TEXT.__text의 arm64 MOVZ/MOVK 즉치값을 디코딩했어요.
    • Swift 작은 문자열의 메모리 레이아웃에 맞춰 파일 전체를 검색했어요.
  5. 시스템 실측과 런타임 관측. macOS 26.7에서 검사 프로그램을 컴파일해서, 비공개 클래스, selector, 뷰 트리가 아직 있는지 확인했어요. rea observe-native-calls는 LLDB 아래에서 ad-hoc으로 다시 서명한 사본을 40초 동안 실행하며, 중단점 8세트의 호출을 기록했어요.

rea inspect-native-dispatch-metadata는 결과가 없었어요. 이유는 입력 크기예요. REA는 이 명령의 입력 상한을 64 MiB로 두었는데, arm64 슬라이스는 104 MiB예요.

핵심 발견

런타임 문자열로만 접근하는 비공개 클래스

inspect-macho는 import된 ObjC 클래스 315개를 나열해요. SDK의 공개 인터페이스 6,007개와 대조하면 SDK 헤더 파일에 없는 클래스가 26개 남아요. 이 클래스들은 WebKit, AuthenticationServices, JavaScriptCore, Sparkle, dispatch에서 왔고, 모두 공개 클래스이거나 서드파티 클래스예요. 따라서 릴리스 빌드의 정적 링크 계층에는 비공개 UI 클래스 참조가 전혀 없어요.

비공개 클래스는 NSClassFromString, KVC, selector 문자열로 런타임에만 얻어요. 이건 소스의 작성 방식과 일치해요.

문자열 이어 붙이기가 숨기는 것과 숨기지 못하는 것

Swift는 15바이트 이하의 문자열을 String의 기계어 워드 두 개에 그대로 저장해요. 두 번째 워드의 최상위 바이트는 0xE0과 길이를 비트 OR한 결과예요. 이 때문에 리터럴의 모양에 따라 컴파일 산출물이 세 가지로 나와요.

  1. 배열 리터럴(예: ["CA", "Emitter", "Behavior"])은 __DATA.__data에서 연속된 16바이트 슬롯으로 저장돼요.
  2. 직접 인자로 넘기는 짧은 리터럴(예: "AVMovableView")은 MOVZ/MOVK 명령 2~4개로 컴파일되고, 바이트가 이어지지 않아요.
  3. 15바이트를 넘는 리터럴(예: emitterBehaviors.fingerAttractor.enabled)은 __TEXT.__cstring에 들어가서 strings로 바로 보여요.

아래 도표는 Swift 문자열 리터럴이 컴파일되어 바이너리에 남는 위치를 보여 줘요.

그래서 strings와 Rizin의 iz 모두 CAEmitterBehavior와 behaviorWithType:을 찾지 못해요. 하지만 조각과 KVC 경로는 여전히 읽을 수 있어요.

클래스 이름을 조각으로 이어 붙이면 완전한 클래스명으로 하는 단순 스캔은 피할 수 있어요. 하지만 조금만 조합해서 검사하면 막지 못해요. 평문을 실제로 없앤 건 iOS 쪽의 XOR 난독화(NativeTextChecking.swift)예요. 다만 iOS 바이너리는 검증할 수 없어요.

릴리스 빌드와 소스 사이의 버전 드리프트

TelegramSwift master는 2025-07-29에 멈춰 있어요. TelegramSwift 공개 소스를 읽을 때는 릴리스 빌드보다 약 15개월 뒤처져 있다고 생각해야 해요. 13.0은 2026-10에 빌드되었고 더 새로운 telegram-ios 서브모듈을 썼어요. 증거는 두 가지예요.

  1. MetalEngine의 FileManager 메서드 교체(#08-05)가 이미 macOS 바이너리에 들어 있어요. FailedMoveErrors 클래스와 완전한 selector 문자열도 함께 있어요.
  2. 소스에 있던 HackUtils 클래스는 바이너리에서 사라졌고, 같은 이름의 기능은 ObjcUtils에서만 나타나요.

시스템에 따라 조용히 무력해지는 비공개 경로

이 기법들은 시스템 내부 구조에 기대고 있어서 시스템 버전에 따라 달라져요. 실패하더라도 대부분 조용히 실패해요.

  • NSVisualEffectView에 sdrNormalize 필터와 CAChameleonLayer가 새로 생겼어요. Telegram의 화이트리스트는 이들을 삭제해요. 코드가 대소문자 두 가지 레이어 이름을 모두 매칭하므로 구조상으로는 여전히 작동해요.
  • 시스템 텍스트 메뉴의 공유 항목은 _performStandardShareMenuItem:로 바뀌었어요. Telegram은 _shareServiceSelected:만 비교하므로 공유 항목이 더는 삭제되지 않을 수 있어요.
  • MKZoomSegmentedControl은 여전히 등록된 클래스지만 이번 테스트에서는 지도 뷰 트리에 나타나지 않았어요. Telegram의 if let 때문에 이 코드는 아무 일도 하지 않게 돼요.
  • 비공개 커서, CAEmitterBehavior, contentsMultiplyColor, NSTitlebarView, AVMovableView는 26.7에서도 모두 있어요.

배포 방식이 정하는 기법의 범위

공식 직접 설치 버전은 App Sandbox를 켜지 않지만 hardened runtime은 켜요. 그래서 다음을 할 수 있어요.

  • 자기 bundle의 리소스 포크에 쓰고 killall Dock을 실행해요.
  • IORegistry를 읽어요.
  • 전역 CGEvent tap을 만들어요. 이때 사용자가 입력 모니터링 권한을 줘야 하고, 코드는 IOHIDCheckAccess와 IOHIDRequestAccess로 이를 확인해요.

이런 능력은 Mac App Store의 샌드박스 버전에서는 제한돼요. App Store 버전은 검증하지 않았어요.

런타임 관측

hardened runtime 대상은 get-task-allow가 있어야만 LLDB로 디버깅할 수 있어요. 그래서 앱을 복사해 ad-hoc 서명으로 hardened runtime을 없애고 get-task-allow를 추가했어요. 원본 앱은 건드리지 않았어요.

한계

  • 바이너리 버전(13.0, 2026-10)은 소스(2025-07)보다 약 15개월 새로워요. “릴리스됨”은 13.0에서 증거가 있다는 뜻이에요. 소스와 한 줄씩 일치한다는 뜻은 아니에요.
  • 문자열과 import 테이블은 코드가 컴파일되어 들어갔다는 것만 보여 줘요. 런타임에 실행된다는 것은 증명하지 못해요. 런타임 관측은 시작과 로그인 화면만 다뤘어요.
  • inspect-macho의 import 테이블은 dyld_info 텍스트 출력에서 나왔고, REA는 이를 완전하지 않다고 표시해요.
  • 공유 메뉴의 “동작하지 않을 수 있음”과 지도 컨트롤의 “조용히 건너뜀”은 시스템 구조에 대한 독립 테스트에서 나왔어요. Telegram 화면 안에서 재현하지는 않았어요.
  • Hopper, Ghidra, IDA가 없어서 함수 수준의 디컴파일과 교차 참조는 하지 않았어요.
