1. 이중 가상 매핑으로 링 버퍼의 랩어라운드 없애기

#11-01 · Telegram-iOS · 비 UI · 리포트 선정 11-1 · 검증 방식: 소스 분석, REA 바이너리

소스: Telegram-iOS:submodules/RingBuffer/Sources/RingBuffer.m L33–L105

무엇을 했나요: 링 버퍼(고정 크기 버퍼를 원형으로 돌려 쓰는 구조)를 만들 때 주소 공간을 이렇게 구성해요.

  1. 먼저 페이지 정렬된 주소 공간을 두 배로 예약해요.
  2. 첫 번째 구간의 물리 페이지를 바로 뒤의 두 번째 구간에 매핑해요.

그러면 끝을 넘어가는 논리적 연속 구간도 모두 연속 포인터가 돼요.

왜 이렇게 했나요: 일반 링 버퍼는 랩어라운드(끝에 닿으면 처음으로 돌아가는) 지점에서 두 구간으로 나뉘어요. 호출자는 분기하거나 두 번 복사해야 해요. 여기서는 비용을 초기화로 옮겼어요. 그래서 핫 패스에서 memcpy 한 번이면 돼요.

아래 도표는 링 버퍼의 미러 윈도우를 만드는 초기화 순서를 보여 줘요.

핵심 코드 발췌

대가와 위험: Mach vm_remap과 주소 공간의 연속성에 기대고 있어요. 초기화는 3회 재시도해요. 가상 주소는 용량의 두 배를 차지해요.

2. “소유권 펜스”와 3회 밸브로 공유 SQLite 보호하기

#11-02 · Telegram-iOS · 비 UI · 리포트 선정 11-2 · 검증 방식: 소스 분석

소스: Telegram-iOS:submodules/Postbox/Sources/SqliteValueBox.swift L254–L303

무엇을 했나요: SqliteValueBox는 데이터베이스를 지우는 조건을 엄격하게 둬요.

  • 메인 앱의 읽기/쓰기 연결만 데이터베이스를 지울 수 있게 해요.
  • 연속으로 집계할 수 있는 열기 실패는 원자적 마커 파일에 기록해요.
  • 3회에 도달한 뒤에야 메인 DB, -shm, -wal을 함께 지워요.

왜 이렇게 했나요: 알림 확장은 메인 DB를 공유해요. 잠금 화면 데이터 보호, 락 경합, 리소스 고갈이 있다고 해서 DB가 손상된 것은 아니에요. 바로 지우면 일시적으로 열리지 않는 상황이 로컬 데이터 손실로 이어져요. 메인 DB만 지워도 오래된 WAL(변경을 로그 파일에 먼저 적는 SQLite 방식) 인덱스가 새 WAL과 짝지어져요.

아래 도표는 DB 열기 실패가 삭제로 이어지는 조건을 보여 줘요.

핵심 코드 발췌

대가와 위험: 메인 앱에서 집계할 수 있는 실패가 연속 3회 나면 여전히 빈 DB를 다시 만들어요. 이 정책은 잘못 지우는 일을 막는 데 우선순위를 두기 때문에, 실제로 손상됐을 때 복구가 늦어질 수 있어요.

증거 체인 #11-02 (iOS 바이너리 미검증)

  • 리포트 요약(구현 방법): -open-failures 마커 파일의 원자적 쓰기와 임계값 판단.

3. CPU 샘플링할 때 PAC를 직접 풀고 스택 순회를 제한하기

무엇을 했나요: CpuProfiler는 일시 중지된 스레드의 arm64 레지스터와 프레임 포인터 체인을 직접 읽어요. 먼저 arm64e 반환 주소의 PAC(포인터 인증 코드)를 없애요. 그다음 프레임 포인터를 검사하다가 아래 조건 중 하나라도 어긋나면 순회를 끝내요.

5. 하드 링크된 여러 경로를 하나의 캐시 축출 단위로 병합

#11-05 · Telegram-iOS · 비 UI · 검증 방식: 소스 분석 · 태그: 성능과 메모리

소스: Telegram-iOS:submodules/Postbox/Sources/TimeBasedCleanup.swift L255–L284

무엇을 했나요: 정리기는 이렇게 동작해요.

  • (st_dev, st_ino)로 같은 물리 파일을 알아봐요.
  • 첫 번째 경로가 크기를 기록해요.
  • 하드 링크가 더 있으면 같은 임시 데이터베이스 행에만 덧붙여요.

6. 행 ID 없는 테이블과 영속 구문으로 컴팩트한 ValueBox 구현

#11-06 · Telegram-iOS · 비 UI · 검증 방식: 소스 분석 · 태그: 성능과 메모리

소스: Telegram-iOS:submodules/Postbox/Sources/SqliteValueBox.swift L898–L952

무엇을 했나요: ValueBox는 이렇게 구성돼요.

  • 논리 테이블 ID에 따라 t<ID>를 동적으로 만들어요.
  • 바이너리 기본 키 테이블은 WITHOUT ROWID를 쓸 수 있어요.
  • 테이블별로 쿼리 구문을 캐시하고 SQLITE_PREPARE_PERSISTENT로 컴파일해요.

왜 이렇게 했나요: 작은 키-값 테이블에는 SQLite의 암묵적 행 ID를 중복해서 저장할 필요가 없어요. 자주 읽을 때 같은 SQL을 반복해서 파싱해서도 안 돼요. 객체 하나가 구문을 재사용하기 전에 reset()하고 새 키를 바인딩해요.

핵심 코드 발췌

대가와 위험: 접근한 테이블마다 미리 컴파일한 구문이 계속 남아 있어요. 동적 SQL은 테이블 ID를 이어 붙여 만들어요. 이 ID는 외부 문자열이 아니라 내부 ValueBoxTable에서 나와요.

7. SQLite mmap을 명시적으로 끄고 영속성 트레이드오프를 분리

#11-07 · Telegram-iOS · 비 UI · 검증 방식: 소스 분석 · 태그: 성능과 메모리

소스: Telegram-iOS:submodules/Postbox/Sources/SqliteValueBox.swift L590–L628

무엇을 했나요: 캐시를 끈 연결은 이렇게 설정해요.

  • SQLite 페이지 캐시를 32로 제한해요.
  • SQLite mmap은 명시적으로 꺼요.
  • WAL, synchronous=NORMAL, 메모리 임시 테이블을 함께 써요.
  • 체크포인트에는 여전히 fullfsync를 요구해요.

왜 이렇게 했나요: 이 파라미터 조합은 런타임 지연, 메모리, 영속성의 트레이드오프를 분리해요. useCaches가 거짓일 때 32페이지 제한은 임시 연결이나 확장 연결에 특히 잘 맞아요. 코드는 mmap_size를 끄는 구체적인 시스템 결함을 설명하지 않아요. 그 이유는 미검증이에요.

핵심 코드 발췌

대가와 위험: synchronous=NORMAL은 단일 트랜잭션의 내구성이 FULL보다 낮아요. cipher_memory_security = OFF는 SQLCipher의 메모리 소거 보호도 약하게 만들어요. 파라미터 호환성은 번들된 SQLite/SQLCipher에 달려 있어요.
