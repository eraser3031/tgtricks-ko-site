1. 비공개 키보드 scene delegate로 키보드 윈도우 얻기

#02-01 · Telegram-iOS · UIKit · 리포트 선정 02-1 · 검증 방식: 소스 분석 · 태그: 비공개 API, 텍스트와 입력

소스: Telegram-iOS:submodules/UIKitRuntimeUtils/Source/UIKitRuntimeUtils/UIViewController+Navigation.m L761–L782

소스: Telegram-iOS:submodules/TelegramUI/Sources/AppDelegate.swift L141–L172

무엇을 했나요: UIWindowScene의 keyboardSceneDelegate에서 keyboardWindow(시스템 키보드가 올라가는 윈도우)를 가져와요. AppDelegate는 이 경로를 먼저 타고, 그다음 모든 scene 윈도우를 훑는 폴백(앞 경로가 안 될 때 쓰는 대체 경로)으로 넘어가요.

왜 이렇게 했나요: iOS 16부터 키보드는 내부 scene에 속해요. 공개 API인 UIWindowScene.windows에는 키보드 윈도우가 더 이상 안정적으로 들어 있지 않아요. keyboardSceneDelegate라는 진입점 덕분에 앱은 키보드의 실제 뷰를 읽고, 키보드 애니메이션과 맞출 수 있어요.

아래 도표는 키보드 윈도우를 얻는 경로와 폴백 순서를 보여 줘요.

핵심 코드 발췌

대가와 위험: keyboardSceneDelegate와 keyboardWindow는 비공개 인터페이스예요. 아래 경우에는 이 방식이 막힐 수 있어요.

  • 시스템이 이름을 바꿔요.
  • 키보드가 프로세스 밖에서 호스팅돼요.
  • App Review를 통과하지 못해요.

증거 체인 #02-01(iOS 바이너리 미검증)

  • 소스 분석: Telegram-iOS 고정 커밋에서 한 줄씩 확인했어요. 소스 위치는 모두 2곳이에요.
  • 리포트 요약(구현 방법): 최소한의 프로토콜을 선언하고, respondsToSelector:와 타입 검증을 단계별로 거쳐요.
  • 바이너리 검증: 하지 않았어요. App Store에 배포된 IPA는 FairPlay로 암호화되어 있어서, 복호화된 실행 파일을 합법적으로 얻을 수 없어요.

2. 클래스 이름 패턴으로 여러 세대의 시스템 키보드 뷰 맞추기

#02-02 · Telegram-iOS · UIKit · 검증 방식: 소스 분석 · 태그: 비공개 API, 텍스트와 입력

소스: Telegram-iOS:submodules/TelegramUI/Sources/AppDelegate.swift L73–L106

무엇을 했나요: 접두사와 접미사로 아래 클래스를 찾아요.

  • UIRemoteKeyboardWindow
  • UITextEffectsWindow
  • UIInputSetHostView
  • UIKeyboardItemContainerView
  • 컨테이너인 UIInputSetContainerView와 UITrackingWindowView도 같은 방식으로 찾아요.

왜 이렇게 했나요: 비공개 클래스 이름은 시스템 버전에 따라 바뀌어요. 접두사와 접미사로 찾으면 전체 클래스 이름에 완전히 기대지 않아도 돼요. 구형 시스템에서 윈도우를 하나씩 돌아보는 폴백 경로에서도 이 패턴이 판단 근거가 돼요.

핵심 코드 발췌

대가와 위험: 비공개 구현 세부 사항이에요. 엉뚱한 뷰가 걸리거나 새 시스템에서 구조가 바뀌면 키보드 높이가 0이 되거나 아예 동작하지 않아요.

증거 체인 #02-02(iOS 바이너리 미검증)

  • 바이너리 검증: 하지 않았어요. App Store에 배포된 IPA는 FairPlay로 암호화되어 있어서, 복호화된 실행 파일을 합법적으로 얻을 수 없어요.

3. 앱 콘텐츠 대신 시스템 키보드 레이어를 직접 옮기기

#02-03 · Telegram-iOS · UIKit · 리포트 선정 02-2 · 검증 방식: 소스 분석 · 태그: 비공개 API, Core Animation, 텍스트와 입력

소스: Telegram-iOS:submodules/Display/Source/KeyboardManager.swift L65–L79

소스: Telegram-iOS:submodules/Display/Source/WindowContent.swift L1407–L1420

무엇을 했나요: 세 가지가 함께 일어나요.

  1. 키보드 뷰의 bounds.origin.y를 음수 오프셋으로 설정해요.
  2. 같은 CALayer에 additive 이동 애니메이션(현재 값에 더해서 적용하는 애니메이션)을 걸어요.
  3. 같은 때에 윈도우 레이아웃은 입력 높이에서 이 오프셋을 빼요.

왜 이렇게 했나요: 일반적인 resignFirstResponder()는 시스템이 키보드를 통째로 접게 할 뿐이에요. 키보드 레이어를 직접 옮기는 이 방식에서는 키보드가 손가락을 따라 내려가고, 채팅 레이아웃도 같은 진행도로 갱신돼요.

아래 도표는 키보드 레이어를 직접 옮길 때 함께 일어나는 일을 보여 줘요.

핵심 코드 발췌

대가와 위험: 시스템 비공개 뷰의 레이어를 수정해요. 시스템 키보드의 계층이나 애니메이션 모델이 바뀌면 키보드가 튀거나, 남아 있거나, 접히지 않을 수 있어요.

증거 체인 #02-03(iOS 바이너리 미검증)

  • 소스 분석: Telegram-iOS 고정 커밋에서 한 줄씩 확인했어요. 소스 위치는 모두 2곳이에요.
  • 리포트 요약(구현 방법): 전후의 bounds를 기록하고, transition에 따라 애니메이션 여부를 정하고, 콜백으로 완료를 알려요.
  • 바이너리 검증: 하지 않았어요. App Store에 배포된 IPA는 FairPlay로 암호화되어 있어서, 복호화된 실행 파일을 합법적으로 얻을 수 없어요.

4. 여러 좌표로 키보드 알림의 잘못된 높이 보정하기

#02-04 · Telegram-iOS · UIKit · 리포트 선정 02-3 · 검증 방식: 소스 분석 · 태그: 텍스트와 입력

소스: Telegram-iOS:submodules/Display/Source/WindowContent.swift L650–L761

무엇을 했나요: 키보드 높이를 구할 때 아래처럼 처리해요.

  • 실시간 키보드 뷰의 frame.minY를 가장 먼저 믿어요.
  • iOS 16.1 이상에서는 알림에 담긴 화면 좌표를 이벤트 윈도우 좌표로 변환해요.
  • 다음 오차도 보정해요.
    • 가운데 정렬된 윈도우의 반 높이 차이
    • iPad의 경계 근처 오차
    • 하위 윈도우의 27pt 편차

왜 이렇게 했나요: keyboardWillChangeFrame의 좌표가 늘 앱 윈도우 좌표와 같지는 않아요. 분할 화면, 윈도우 모드, 다중 scene에서는 흔히 쓰는 “화면 높이 − 키보드 Y” 공식이 잘못된 높이를 내요.

핵심 코드 발췌

대가와 위험: 보정값에 24pt, 27pt, 5pt 같은 경험적 상수가 들어 있어요. 새 크기, 플로팅 키보드, 시스템의 알림 의미 변경이 생기면 다시 실측해야 해요.

증거 체인 #02-04(iOS 바이너리 미검증)

  • 소스 분석: Telegram-iOS 고정 커밋에서 한 줄씩 확인했어요. 소스 위치는 모두 1곳이에요.
  • 리포트 요약(구현 방법): UICoordinateSpace.convert와 경험적 임계값으로 경계를 보정해요.
  • 바이너리 검증: 하지 않았어요. App Store에 배포된 IPA는 FairPlay로 암호화되어 있어서, 복호화된 실행 파일을 합법적으로 얻을 수 없어요.

5. first responder와 액세서리 높이로 정하는 전체 윈도우 제스처의 드래그 영역

#02-05 · Telegram-iOS · UIKit · 검증 방식: 소스 분석 · 태그: 텍스트와 입력, 제스처와 스크롤

소스: Telegram-iOS:submodules/Display/Source/WindowContent.swift L1489–L1513

무엇을 했나요: 윈도우 수준의 드래그가 일어나는 영역을 이렇게 좁혀요.

  • 드래그를 키보드 위쪽으로 한정해요.
  • 히트된 뷰에서 위로 올라가며 비활성화 표시를 읽어요.
  • 입력 액세서리 높이를 키보드 상한에 포함해요.
  • 3pt 임계값에서 레이아웃 갱신을 시작해요.

왜 이렇게 했나요: 제스처는 호스트 전체에 설치되어 있어요. 위 조건이 없으면 스크롤, 하단 버튼, 커스텀 액세서리가 의도치 않게 키보드를 끌어당길 수 있어요.

핵심 코드 발췌

대가와 위험: UIView에 붙은 연관 객체 표시에 기대어 동작해요. 복잡하게 중첩된 뷰는 이 표시를 올바르게 설정해야 해요.

  • 소스 분석: Telegram-iOS 고정 커밋에서 한 줄씩 확인했어요. 소스 위치는 모두 1곳이에요.

6. 키보드 내림 제스처로 같은 손가락의 리스트 관성 명시적으로 취소하기

#02-06 · Telegram-iOS · UIKit · 리포트 선정 02-4 · 검증 방식: 소스 분석 · 태그: 텍스트와 입력, 제스처와 스크롤

소스: Telegram-iOS:submodules/Display/Source/WindowContent.swift L1547–L1573

무엇을 했나요: 터치가 끝나는 동안 “이 제스처가 키보드를 내렸다”는 사실을 기록해요. 리스트는 잠시 뒤 자신의 .ended를 받을 때 그 기록을 읽고 관성 스크롤을 포기할 수 있어요.

왜 이렇게 했나요: 윈도우 제스처와 UIScrollView는 동시에 인식될 수 있어요. 제스처끼리 주고받는 신호가 없으면, 한 번 아래로 끄는 동작이 키보드를 내리면서 리스트도 휙 던져 버려요.

아래 도표는 키보드를 내린 제스처의 기록을 리스트가 읽어 관성을 포기하는 순서를 보여 줘요.

핵심 코드 발췌

대가와 위험: UIKit의 터치 디스패치 순서에 기대는 타이밍 계약이에요. 커스텀 스크롤 컴포넌트는 dismissedKeyboardByCurrentGesture를 직접 읽어야 해요.

증거 체인 #02-06(iOS 바이너리 미검증)

  • 소스 분석: Telegram-iOS 고정 커밋에서 한 줄씩 확인했어요. 소스 위치는 모두 1곳이에요.
  • 리포트 요약(구현 방법): dismissedKeyboardByCurrentGestureValue를 설정하고, 완전히 접힐 때까지 애니메이션해요.
  • 바이너리 검증: 하지 않았어요. App Store에 배포된 IPA는 FairPlay로 암호화되어 있어서, 복호화된 실행 파일을 합법적으로 얻을 수 없어요.

7. 선택 영역 변화를 위조해 텍스트 자동 수정 일으키기

#02-07 · Telegram-iOS · UIKit · 검증 방식: 소스 분석 · 태그: 텍스트와 입력

소스: Telegram-iOS:submodules/UIKitRuntimeUtils/Source/UIKitRuntimeUtils/UIViewController+Navigation.m L850–L859

무엇을 했나요: 세 단계로 해요.

  1. 먼저 marked text(입력기가 조합 중인 글자)를 취소해요.
  2. 선택 영역을 한 글자 왼쪽으로 옮겨요.
  3. 곧바로 원래 선택 영역으로 되돌려요.

왜 이렇게 했나요: 이렇게 하면 UIKit이 표시된 텍스트와 선택 영역을 다시 처리해요. 호출한 쪽은 최종 커서 위치를 바꾸지 않고도 자동 수정을 요청할 수 있어요. UIKit 내부에서 구체적으로 어떻게 판정하는지는 검증하지 않았어요.

핵심 코드 발췌

대가와 위험: 입력기의 조합 상태가 가짜 선택 영역에 민감할 수 있어요. 첫 글자에서는 선택 영역을 옮기지 않아요. 이 로직은 다국어 입력기 테스트로 검증해야 해요.
