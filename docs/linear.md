저는 리치 텍스트 에디터와 스프레드시트 같은 협업 소프트웨어를 만들어요. 이런 소프트웨어에서는 **협업 엔진**, 다른 말로 **데이터 동기화 엔진**이 사용자 경험을 좌우해요. 협업 엔진 덕분에 여러 사람이 같은 파일을 실시간으로 동시에 편집하고, 오프라인에서도 쓰고, 파일 기록도 볼 수 있어요. 보통 엔지니어는 동기화 엔진을 만들 때 **[OT(Operational Transformation)](https://en.wikipedia.org/wiki/Operational_transformation)**나 **[CRDT(Conflict-free Replicated Data Types)](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type)**를 써요.

에디터와 스프레드시트에는 이 기술들이 잘 맞지만, 다른 종류의 애플리케이션에는 알맞지 않을 수 있어요. 이유는 이래요.

OT는 널리 쓰이지만 복잡하기로 악명이 높아요. 애플리케이션마다 데이터 모델과 연산 집합이 다르기 때문에, 올바른 연산과 변환 함수를 구현하는 데 공이 많이 들어서 그래요. OT는 편집을 동기화하고, 사용자의 의도를 지키고, 충돌을 처리하는 데 뛰어나요. 하지만 사용자 정보나 파일 메타데이터를 관리하는 것처럼 단순한 경우에는 복잡도가 지나쳐요. 이런 경우에는 **last-writer-wins**(나중에 쓴 쪽이 이기는 방식)처럼 단순한 방식으로 충분할 때가 많아요.

반면 CRDT는 더 쓰기 편해 보여요. 텍스트, 리스트, 맵, 카운터 같은 기본 자료 구조를 처음부터 지원해서 개발자의 일이 줄어요.

하지만 CRDT에는 다음과 같은 약점이 있어요.

- 메타데이터 오버헤드가 생기기 쉬워요.
- 부분 동기화나 권한 제어가 필요한 상황, 예를 들어 사용자가 파일 일부에만 접근할 수 있는 경우에는 다루기도 어려워요. CRDT가 원래 분산 시스템을 위해 설계됐는데, 요즘 애플리케이션 대부분은 여전히 중앙 서버에 의존하기 때문이에요.

저는 CRDT를 좋아하는 편이지만, 어떤 경우에는 CRDT로 부족해요.

제가 동기화 엔진에 바라는 점은 이래요.

1. **임의의 데이터 모델 지원**: 다양한 상황에 맞출 수 있어야 해요.
2. **풍부한 기능**: 부분 동기화를 지원하고, 권한 제어를 적용하고, 실행 취소/다시 실행, 오프라인 사용, 편집 기록 같은 기능이 있어야 해요.
3. **뛰어난 개발자 경험**: ORM(객체로 데이터베이스를 다루게 해 주는 도구)처럼 모델을 정의할 수 있으면 좋아요. 협업 애플리케이션을 만들려고 동기화 엔진 전문가가 될 필요는 없어야 해요.

[Linear](https://linear.app)의 동기화 엔진(Linear Sync Engine, LSE)은 위 요구 사항을 모두 우아하게 풀어내요. 게다가 복잡한 내부 구조를 감춘 직관적인 API를 줘서, 기능 개발이 훨씬 쉬워져요. 예를 들어 이슈의 제목을 바꾸는 코드는 이렇게 간단해요.

```jsx
issue.title = "New Title";
issue.save();
```

LSE가 제가 찾던 바로 그 엔진이라고 믿어요. 그래서 프런트엔드 코드를 리버스 엔지니어링해서 동작 원리를 알아보기로 했어요. 저처럼 관심 있는 분들께 도움이 되도록 알아낸 내용도 문서로 남기고 있어요.

> [!NOTE]
> 참고하면 좋은 자료
>
> 이 [gist](https://gist.github.com/pesterhazy/3e039677f2e314cb77ffe3497ebca07b#gistcomment-5184039)는 범용 동기화를 위한 기성 솔루션을 소개해요. ElectricSQL과 ZeroSync(저도 궁금해하고 있어요)도 있으니 함께 살펴보세요.

이 글에서는 LSE가 다음을 어떻게 하는지 살펴봐요.

- 모델, 프로퍼티, 참조를 정의해요.
- **MobX**(상태 변화를 감지하는 라이브러리)로 모델을 옵저버블(값이 바뀌면 알려 주는 객체)로 만들어요.
- **부트스트래핑**을 해요.
- 로컬 데이터베이스(IndexedDB, 브라우저에 내장된 데이터베이스)를 만들고 채워요.
- 지연 로딩한 데이터를 하이드레이션해요.
- 클라이언트와 서버를 동기화해요.
- 실행 취소와 다시 실행을 처리해요.

LSE가 코드 수준에서 어떻게 동작하는지 쉽게 이해할 수 있도록, Linear의 (난독화된) 코드에 자세한 주석을 단 버전을 올려 뒀어요. 이 주석에는 이 글에서 다루지 않은 내용도 담겨 있어요. 식별자 이름이 난독화돼 있어서, 원래 이름이 무엇이었을지 최대한 추측해서 달았어요. 글 끝에는 줄임말과 원래 표현을 짝지은 표도 있어요.

저장소를 클론해서 평소 쓰는 에디터로 코드를 보면서 읽기를 권해요. 글과 코드를 나란히 놓고 보면 훨씬 자연스럽게 읽혀요. 개인적으로는 VS Code를 추천해요. VS Code의 TypeScript 언어 서비스가 큰 파일을 아주 잘 다루기 때문이에요. 또 각 절 맨 앞에 관련 코드 위치를 알려 주는 안내를 넣을게요. <kbd>Ctrl + Shift + O</kbd>(macOS에서는 <kbd>Meta + Shift + O</kbd>) 단축키로 심볼을 검색하면 바로 이동할 수 있어요.

![search-for-symbols](https://github.com/wzhudev/reverse-linear-sync-engine/raw/45dc91e78e03300b69cc088057a28c42cee35a41/imgs/search-for-symbols.png)

저는 Linear 팀과 관계가 없고, 이 글을 쓰면서 팀에 문의하지도 않았어요. 그래서 실제 구현과 다르거나 틀린 내용이 있을 수 있어요. 그래도 관련 발표를 보고, 잘 연구된 OT 방식과 LSE를 비교하면서 LSE 방식을 최대한 정확하게 설명하려고 애썼어요. 비슷한 협업 엔진을 만들 때 이 글이 믿을 만한 참고 자료가 되면 좋겠어요. 틀렸거나 오해를 부르는 내용을 발견하면 이슈나 풀 리퀘스트로 알려 주세요. 바로잡는 데 큰 도움이 돼요. 의견을 기다릴게요!

다만 저도 모르게 [지식의 저주](https://en.wikipedia.org/wiki/Curse_of_knowledge)에 빠졌을 수 있어요. 이해하기 어려운 부분이 있다면 제 잘못이에요. 기꺼이 더 설명해 드릴게요. 이슈를 열어 주시면 세부 내용이나 다이어그램을 추가해서 글을 더 이해하기 쉽게 만들게요.

그럼 시작해 볼게요!

## 들어가며 [#introduction]

Tuomas의 [두](https://www.youtube.com/watch?v=WxK11RsLqp4&t=2175s) [발표](https://linear.app/blog/scaling-the-linear-sync-engine), [팟캐스트](https://www.devtools.fm/episode/61), [Local First Conf 발표](https://www.youtube.com/watch?v=VLgmjzERT08)를 아직 보지 않았다면, 이 글을 읽기 전에 먼저 보기를 추천해요. 배경 지식을 얻는 데 도움이 돼요. 그래도 LSE의 핵심 개념은 여기서 정리할게요.

![introduction to LSE](https://github.com/wzhudev/reverse-linear-sync-engine/raw/45dc91e78e03300b69cc088057a28c42cee35a41/imgs/introduction.png)

**모델**

`Issue`, `Team`, `Organization`, `Comment` 같은 엔티티를 LSE에서는 **모델**이라고 불러요. 모델은 **프로퍼티**와 다른 모델에 대한 **참조**를 가져요. 이 중 상당수는 (**MobX**로) 관찰할 수 있어서, 값이 바뀌면 뷰가 자동으로 업데이트돼요. 한마디로 모델과 프로퍼티에는 LSE 안에서 어떻게 동작할지를 정하는 **메타데이터**가 들어 있어요.

모델은 **로컬 데이터베이스**(IndexedDB)나 서버에서 불러올 수 있어요. 일부 모델은 **부분 로딩**을 지원해서, 필요할 때 로컬 데이터베이스에서 불러오거나 서버에서 데이터를 더 가져올 수 있어요. 불러온 모델은 **오브젝트 풀**에 저장해요. 오브젝트 풀은 **UUID**로 모델을 찾는 커다란 맵이에요.

모델은 지연 **하이드레이션**할 수 있어요. 프로퍼티에 접근할 때 비로소 프로퍼티를 불러온다는 뜻이에요. 꼭 필요한 데이터만 불러오기 때문에 성능을 높이는 데 특히 유용해요.

모델, 프로퍼티, 참조에 하는 추가, 삭제, 업데이트, 보관 같은 작업은 **트랜잭션**으로 묶어요. 트랜잭션은 서버로 보내 서버에서 실행하고, 그 뒤 **델타 패킷**으로 연결된 모든 클라이언트에 브로드캐스트해요. 이렇게 하면 여러 클라이언트의 데이터가 일관되게 유지돼요.

**트랜잭션**

서버로 보내는 작업은 **트랜잭션**으로 포장해요. 트랜잭션은 서버에서만 **독점적으로** 실행하도록 만들었고, 실패하면 클라이언트에서 **되돌릴 수 있게** 설계했어요. 클라이언트가 서버와 연결이 끊기면 트랜잭션을 IndexedDB에 임시로 **캐시**해 두었다가, 연결이 복구되면 자동으로 다시 보내요.

트랜잭션에는 **싱크 ID**가 붙어요. 싱크 ID는 계속 커지기만 하는 숫자라서 작업 순서를 정확하게 지켜 줘요. 이 숫자는 모든 클라이언트의 일관성을 유지하는 데 중요해요.

트랜잭션은 **실행 취소**와 **다시 실행**을 지원하는 데도 핵심 역할을 해요. 덕분에 실시간 협업 중에도 변경과 수정을 매끄럽게 할 수 있어요.

**델타 패킷**

서버는 트랜잭션을 실행한 뒤, 트랜잭션을 보낸 클라이언트를 포함해 모든 클라이언트에 **델타 패킷**을 브로드캐스트해서 모델을 업데이트해요. 델타 패킷에는 **싱크 액션**이 여러 개 들어 있고, 각 액션에도 **싱크 ID**가 붙어요. 이 방식 덕분에 클라이언트가 업데이트를 놓치지 않고, 어긋남이 생겼을 때 빠진 패킷을 찾을 수 있어요.

서버가 실행하는 동안 **부수 효과**(예: 히스토리 생성)를 일으킬 수 있어서, **델타 패킷**은 클라이언트가 보낸 원래 트랜잭션과 다를 수 있어요.
