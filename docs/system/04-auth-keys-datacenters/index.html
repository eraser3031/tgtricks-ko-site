Telegram은 데이터 센터(DC)마다 암호화 신원을 독립된 auth_key(클라이언트와 센터가 공유하는 암호화 키)로 만들고, MTContext로 주소, 영구 키, 임시 키, 데이터 센터 간 인증 토큰을 관리해요. 덕분에 메인 RPC, 미디어, CDN이 병렬로 동작할 수 있고, 한 센터의 엔드포인트 변경이나 키 무효화가 다른 센터를 직접 깨뜨리지 않아요.

iOS 구현은 MtProtoKit과 TelegramCore에 있어요. macOS는 submodules/telegram-ios를 통해 overtake/Telegram-iOS를 참조해요. 고정 fork a24bbe45는 체크아웃되어 있으며, 인증 정보 인덱스, 임시 키 바인딩, DC 간 인증 이전 경로를 모두 검증할 수 있어요.[1] [42] [43] [44] 구체적인 검증은 macOS fork 장별 검증 (01–07장)을 참고해요.

데이터 센터마다 하나씩 있는 암호화 컨텍스트

문제는 최초 로그인만이 아니에요. 클라이언트에게는 센터마다 따로 암호화 연결이 필요한 상황이 세 가지 있어요.

  • 로그인 전에도 아무 진입 센터에 접근할 수 있어야 해요.
  • 로그인 후에는 미디어가 저장된 센터에 연결해야 해요.
  • CDN 리다이렉트 시에는 또 다른 신뢰 세션을 만들어야 해요.

프로토콜도 키가 데이터 센터 사이에서 복제되지 않는다고 명시해요. 새 센터는 독립적으로 암호화 연결을 맺어야 하고, 그 뒤에야 사용자 인증을 이전할 수 있어요.[2]

MTContext는 키와 주소 상태를 오래 들고 있는 소유자예요.

  • 복합 정수 키로 datacenterId와 MTDatacenterAuthInfoSelector를 인덱싱해요.
  • 같은 DC 안에서 영구 키, 임시 메인 연결 키, 임시 미디어 연결 키의 MTDatacenterAuthInfo를 따로 저장해요.
  • 키 객체는 원본 키, authKeyId, 만료 시각, 바인딩 여부를 함께 가져요.
  • salt 집합도 키와 함께 저장되며 메시지 식별자에 따라 사용할 수 있는 salt를 골라요.[3] [4]

MTDatacenterAuthAction은 키 하나를 만드는 조정자예요. 키 종류에 따라 이렇게 달라요.

  • 영구 셀렉터는 결과를 INT32_MAX 유효 기간으로 기록해요.
  • 임시 메인 연결과 미디어 연결은 MTProto를 media로 표시하며, 후자는 enforceMedia도 설정해요.

덕분에 같은 상태 머신을 세 가지 용도에 재사용하면서도 다운로드 연결이 메인 세션의 의미를 차지하지 않게 해요.[5]

키를 요청하는 쪽이 각자 핸드셰이크를 시작하지는 않아요. authInfoForDatacenterWithIdRequired는 먼저 복합 키로 _datacenterAuthActions와 재시도 타이머를 확인해요. 둘 다 비어 있을 때만 동작을 만들어요.

임시 키를 신청할 때 영구 키가 없고 호출자가 바인딩되지 않은 키를 허용하지 않으면, 컨텍스트는 먼저 영구 키를 신청하고 그것이 갱신된 뒤에 임시 키 동작을 실행해요.

이 게이트는 두 가지를 막아요. (추론)[37]

  • 동시 worker가 같은 selector에 대해 키를 여러 개 만드는 일
  • 임시 키가 바인딩할 영구 키보다 먼저 완성되는 일

키 생성 실패 정책은 두 층으로 나뉘어요.

  • 핸드셰이크 서비스 자체의 실패 횟수: 첫 실패 후에는 기다리지 않고, 그 뒤로는 2의 0제곱에서 4제곱까지의 초를 기다려요.
  • 동작이 끝난 뒤 MTContext: 다시 1, 2, 4, 8, 16, 32초 간격으로, 상한 60초까지 대기자에게 재신청을 알려요.

바인딩이 ENCRYPTED_MESSAGE_INVALID를 반환하면 코드는 영구 키를 서버가 더 이상 알아보지 못하는 것으로 보고 타이머 재시도를 시작하지 않아요. 이 경우 재시도할 때마다 DH(Diffie-Hellman 키 교환)를 처음부터 다시 해야 하지만 성공할 수 없기 때문이에요.[6] [38]

아래 상태 도표는 키 생성의 내부 단계를 보여 줘요. 실패해도 중간 상태에 머물지 않아요. 서비스는 nonce(한 번만 쓰는 무작위 값), DH 중간값, 현재 트랜잭션을 비운 뒤 지수 지연으로 재시도해요.

트랜잭션 식별자 보관도 눈여겨볼 만해요. 서비스는 단계마다 준비된 메시지의 messageId, seqNo, 트랜잭션 ID를 보관해요. 재전송할 때 nonce를 다시 무작위로 만들지 않고 같은 요청 파라미터를 재사용할 수 있어요.

공식 프로토콜은 서버가 10분 안에 완전히 같은 요청에 대해 응답을 재전송할 수 있다고 규정하는데, 이것이 이렇게 상태를 저장하는 가치를 설명해 줘요. (추론)[6]

req_pq_multi에서 auth_key까지

이 흐름은 최초 키 교환의 두 가지 위험을 해결해요.

  • 클라이언트는 자신이 앱에 컴파일되어 들어 있는 서버 RSA 키를 쓰고 있음을 확인해야 해요.
  • 서버가 준 pq(소수 두 개의 곱)를 먼저 소인수분해해야 DH를 이어 갈 수 있어요.

이 둘을 하지 않으면 공격자가 핸드셰이크 재료를 바꿔치기하거나, 클라이언트가 유효하지 않은 큰 수를 비싼 계산에 끌어들일 수 있어요.

코드는 테스트용과 프로덕션용 RSA 공개 키를 두 개의 정적 배열로 나눠요. resPQ가 가져온 핑거프린트는 이 공개 키들로 계산한 핑거프린트와 같아야 해요. 키를 가져오는 곳은 센터 종류에 따라 달라요.

  • 일반 센터는 이 두 컴파일 시점 배열만 사용해요.
  • CDN은 컨텍스트에서 DC별로 캐시된 공개 키를 읽고, 처음에 일치하는 항목이 없으면 한 번 더 가져와요.

사용할 수 있는 키를 찾지 못하면 실패하며, 알 수 없는 인증서를 시도하지 않아요.[6] [7]

req_pq_multi의 nonce는 SecRandomCopyBytes에서 얻으며 길이는 16바이트예요. resPQ를 받으면 코드는 이렇게 처리해요.

  1. 먼저 nonce를 비교해요.
  2. pq 길이를 1~8바이트로 제한해요.
  3. 4 미만이거나 2의 63제곱 이상인 값을 거부해요.
  4. MTFactorize로 p와 q로 분해해요.

이는 공식 핸드셰이크에서 pq가 홀수 소수 두 개의 곱이며 보통 2의 63제곱 빼기 1을 넘지 않는다는 제약과 일치해요.[8] [9]

p, q를 얻으면 클라이언트는 32바이트 new_nonce를 만들어요. pq, 인수 p와 q, nonce 두 개, 대상 DC를 p_q_inner_data로 엮어요. 이때 규칙이 있어요.

  • 테스트 환경에서는 DC ID에 10000을 더해요.
  • 미디어이지만 CDN이 아닌 연결은 ID를 음수로 취해요.
  • 임시 키에는 expires_in이 추가돼요.

이것은 로컬 규약이 아니라 핸드셰이크 페이로드의 일부이므로, 환경과 연결 역할이 엔드포인트 선택에만 들어가는 것이 아니라 키 교환에도 들어가요.[6] [9]

이어서 encryptRSAModernPadding이 공식 RSA_PAD를 구현해요. 하는 일은 이래요.

  • 144바이트를 넘는 내부 데이터를 거부해요.
  • 192바이트까지 패딩해요.
  • 32바이트 임시 AES 키를 만들어요.
  • RSA 입력이 모듈러스보다 작아지도록 최대 4096번 시도해요.

그다음 req_DH_params를 보내요. 이 상한은 난수나 암호화 제공자가 비정상일 때 무한 루프를 도는 것을 막지만, 아주 드물게 연속 실패하면 전체 핸드셰이크로 돌아가요. (추론)[10]

복호화 직후에 하는 DH 파라미터 거부 검사

서버가 server_DH_params_ok를 반환하면 클라이언트는 new_nonce와 server_nonce로 임시 AES key와 IV를 도출하여 응답을 복호화해요. 복호화한 응답은 이렇게 검사해요.

  • 최소 20바이트의 SHA1이 있어야 해요.
  • TL로 파싱한 server_DH_inner_data가 무작위 padding에 잘려서는 안 돼요.
  • SHA1과 원래 nonce, 서버 nonce를 검증해요.

모든 실패 경로가 fail:을 호출하며, 부분적으로 협상된 키를 남기지 않아요.[11]

더 중요한 점은 클라이언트가 g, dh_prime, g_a를 그대로 받아들이지 않는다는 거예요. 검사는 이 순서예요.

  1. 생성원(g)이 안전한지 검사해요.
  2. g_a가 안전한 범위에 있는지 검사해요.
  3. dh_prime mod가 이 생성원의 조건을 만족하는지 검사해요.
  4. dh_prime이 안전 소수인지 검사해요.

dh_prime을 검사하는 뒤의 두 검사는 context.keychain을 받으며, 이는 비싼 소수 검증을 캐시하라는 공식 권고와 맞아요. 이어서 클라이언트는 g_b도 범위 검사를 통과할 때까지 256바이트 비공개 지수 b를 최대 8번 생성해요.[11] [9]

submodules/MtProtoKit/Sources/MTDatacenterAuthMessageService.m 770–830행 발췌.

authKey는 g_a의 b제곱을 dh_prime으로 나눈 나머지예요. 그다음 코드는 이렇게 진행해요.

  1. authKey를 256바이트로 강제해요.
  2. SHA1의 마지막 8바이트에서 authKeyId를 얻어요.
  3. new_nonce와 server_nonce의 앞 8바이트를 XOR하여 첫 serverSalt로 삼아요.
  4. SHA1과 무작위 패딩이 붙은 client_DH_inner_data를 보내요.
  5. nonce에 태그 1, 2, 3과 키 보조 해시를 붙여 세 가지 확인 값을 계산해요.
  6. dh_gen_ok의 해시가 같을 때만 델리게이트를 호출해 키를 게시해요.[12] [9]

이 완료 지점이 핵심이에요. 호출자는 최종 키 확인을 통과한 결과만 보게 되며, 로컬에서 계산한 후보 공유 비밀을 인가된 키로 착각하지 않아요. 근거는 이래요.

  • _authKey는 set_client_DH_params를 보내기 전에 임시로 보관되지만 MTContext에는 기록되지 않아요.
  • dh_gen_retry의 확인 값이 올바르면 서비스는 여전히 fail:을 호출하며, 이전 b를 재사용하지 않고 처음부터 다시 시작해요.
  • dh_gen_fail도 확인 값이 올바를 때만 실패로 받아들여요.
  • 잘못된 확인 값, 잘못된 타입, 일치하지 않는 nonce는 델리게이트를 촉발하지 않아요.[12]

리셋 경로는 두 가지예요.

  • 현재 트랜잭션만 지우는 경로: 전달 실패이거나 트랜잭션이 실패했을 가능성이 있다고 표시되었을 때만 서비스는 현재 트랜잭션을 지우고 새 전송 트랜잭션을 요구해요. “같은 단계의 패킷을 아직 다시 보낼 수 있다”에 가까워요.
  • 전체 리셋(fail:): 보안 전송의 리셋도 요청하며, 현재 메시지 ID, 시퀀스 번호, 트랜잭션 ID를 0으로 되돌려요. 전체 핸드셰이크 상태를 버려요.

두 경로의 차이는 코드의 상태 필드와 호출 위치로 결정된 것이며, 프로토콜 주석이 밝힌 설계 의도가 아니에요. (추론)[6] [12]

아래 시퀀스 도표는 핸드셰이크의 인증 경계를 보여 줘요. RSA는 알려진 서버로 보내는 내부 데이터만 보호해요. DH 산출물은 최종 nonce 해시가 확인된 뒤에야 MTContext에 들어가요.

임시 키로 만드는 PFS 연결 정책

장기 키는 재시작 후 재사용하기에 편하지만, 모든 트래픽이 오랫동안 이 키를 직접 쓰면 나중에 기기가 유출되었을 때 복호화될 수 있는 과거 범위가 커져요. Telegram의 프로토콜은 임시 키를 허용하며, 서버는 이를 메모리에만 최대 expires_in초 동안 보관한다고 설명해요. 클라이언트는 보통 이를 영구 키에 바인딩한 뒤 사용하여, 클라이언트-서버 통신의 순방향 비밀성(PFS, 키가 나중에 유출돼도 과거 통신을 풀 수 없는 성질)을 얻어요.[9]

임시 키의 수명은 이렇게 정해요.

  • TelegramCore는 네트워크를 초기화할 때 항상 useTempAuthKeys를 true로 설정해요.
  • MTContext의 기본 임시 키 수명은 24시간이에요.
  • MTDatacenterAuthMessageService는 임시 키를 만들 때 현재 Unix 시간에 이 값을 더해 validUntilTimestamp에 기록해요. 영구 키는 INT32_MAX를 써요.

따라서 키 셀렉터는 성능 격리 용도만이 아니라 무효화 가능성도 인코딩해요.[13] [14] [12]

임시 키가 생성되는 시점에는 아직 사용자 인증이 없어요. MTDatacenterAuthAction은 이렇게 진행해요.

  1. 같은 DC의 영구 키를 찾아요. 영구 키가 없으면 실패해요.
  2. 있으면 임시 키를 켠 MTProto를 새로 만들고, 핸드셰이크 연결을 재사용해요.
  3. MTBindKeyMessageService가 바인딩을 하게 해요.
  4. auth.bindTempAuthKey가 boolTrue를 반환해야만 임시 키를 컨텍스트에 기록해요.

이렇게 하면 바인딩되지 않은 키 오류를 로그인된 세션으로 잘못 취급하지 않아요.[5] [15]

바인딩 요청의 내부 내용에는 다음이 들어 있어요.

  • 임시 및 영구 authKeyId
  • 세션 ID
  • nonce
  • 전역 시간 차이로 보정한 만료 시각

내부는 영구 키로 수동 암호화하고, 외부 요청도 그 세션에서 전송해요. 이로써 서버는 두 키와 세션이 같은 주체에 속함을 검증할 수 있어요. 메시지 전달이나 트랜잭션이 실패했을 가능성이 있으면 서비스는 현재 트랜잭션을 지운 뒤 다시 전송을 요청해요. auth_key 거부가 연속 두 번 나오면 실패를 보고하여, 무효화된 키를 무한정 쓰는 일을 피해요.[15]

바인딩 동작은 일시적 오류와 영구적 오류도 구분해요.

  • 상태 코드가 500 이상이거나 420이면 동작은 최대 3번 시도하며, 두 번째와 세 번째 전에 각각 1초와 2초를 기다려요. 재시도할 때는 이전 연결의 재사용을 포기하지만 방금 생성한 임시 키는 재사용해요.
  • 다른 오류는 곧바로 bindError에 저장하고 실패해요.

그래서 상위 계층은 네트워크 흔들림의 비용을 DH 한 번 이후로 한정하고, 영구 키를 알 수 없다는 신호는 컨텍스트가 무의미한 갱신을 멈추도록 넘길 수 있어요.[5]

이것은 종단 간 채팅 키의 대체재가 아니에요. 여기서의 PFS는 클라이언트와 Telegram 서버 사이의 임시 인증 키 교체만을 가리켜요. 보호하는 것은 클라우드 세션의 전송 키 이력이에요. 비밀 채팅의 종단 간 키 도출, 기기 키, 삭제 경로는 종단 간 암호화와 로컬 보안을 참고해요.

업스트림 iOS 체크아웃의 갱신 정책은 만료를 기다리지 않아요.

  • 이미 사용했고, 갱신 가능하며, 대응하는 영구 키가 있는 임시 메인 키 또는 미디어 키만 갱신해요.
  • 선행 시간(만료보다 앞서 갱신하는 시간)은 수명의 4분의 1이며 최소 1초, 최대 1시간이에요.
  • 스케줄러는 매번 최대 300초까지만 기다려요.
  • 바인딩 오류 ENCRYPTED_MESSAGE_INVALID는 그 키의 재시도 시각을 최댓값으로 설정해요.
  • 다른 실패는 60초 뒤에 재시도해요.

이는 아직 쓸 수 있는 키를 유지하면서, 서버가 영구 키를 잊어버린 경우의 무의미한 루프를 피해요.[16] [5]

macOS fork의 차이: MTContext를 만드는 초기화 구간은 supplementary를 받고 disableUpdates를 설정하지만 임시 키 갱신 스위치는 설정하지 않아요. context.refreshesTemporaryKeys = !supplementary는 업스트림 체크아웃에서만 보여요. 따라서 fork의 supplementary 네트워크가 임시 키 갱신을 끈다고 단정할 수 없어요.[45] [46] 검증 범위는 macOS fork 장별 검증 (01–07장)을 참고해요.

재시작 후의 키와 주소 상태

키 교환은 비싸고 데이터 센터 목록은 변하므로, 클라이언트는 런타임 컨텍스트를 저장해 두어야 해요. 다만 여기서의 Keychain이라는 이름은 오해하기 쉬워요. TelegramCore의 이 프록시는 Apple Security Keychain을 직접 호출하지 않아요. 대신 MTKeychain 프로토콜을 구현해서 다음을 해요.

  • 객체를 NSKeyedArchiver로 인코딩해요.
  • 키 이름을 group:key로 이어 붙여요.
  • 주입된 get, set, remove 클로저에 넘겨요.[17]

계정이 makeExclusiveKeychain을 만들 때, get, set, remove 클로저를 그 계정 Postbox의 keychain 테이블에 연결해요. 각 AccountRecordId에 증가하는 인스턴스 ID를 부여해요. 낡은 네트워크 객체의 읽기와 쓰기는 거부되므로 이전 계정이나 교체된 네트워크가 새 계정의 인증 상태를 덮어쓸 수 없어요.

KeychainTable은 바이트 값을 ValueBox 테이블에 그대로 기록해요. 삭제할 때는 secure: false를 전달하므로, 여기서 삭제가 물리적 보안 소거를 한다고 추론할 수 없어요.[18] [19]

업스트림 MTContext.setKeychain:은 프록시를 주입한 뒤 다음을 복원해요.

  • 전역 시간 차이
  • 영속 주소 집합
  • 수동으로 고른 전송 방식
  • 인증 정보
  • CDN 공개 키
  • 전송 통계
  • DC 간 인증 토큰

복원할 때 만료된 비영구 키를 삭제하고, 남은 임시 키에는 갱신을 예약해요. 주소 집합, 인증 정보, 인증 토큰의 갱신은 모두 해당 그룹에 즉시 기록돼요. 덕분에 앱을 재시작해도 DC마다 DH를 다시 할 필요가 없고, 만료되었거나 서버가 폐기한 항목만 재구성하면 돼요.[20] [21]

각 그룹의 의미는 완전히 같지 않아요.

  • persistent: datacenterAuthInfoById, 주소 집합, 수동 방식, 인증 토큰
  • ephemeral: CDN 공개 키
  • temp: 시간 차이와 전송 방식 통계
  • cleanup: 세션 정리 목록

그런데 임시 인증 정보도 persistent:datacenterAuthInfoById에 기록되며, 다음 로드 때 만료 시각에 따라 걸러져요. 따라서 그룹 이름만으로 키의 유효 기간이 정해지지 않으며, validUntilTimestamp가 결정 조건이에요.[20] [21]

공유 경로는 계정을 여는 방식에서도 드러나요. accountWithId는 계정 경로로 Postbox를 열며, 프로세스에 따라 다르게 전달해요.

  • 메인 프로세스는 isMainProcess: true를 전달해요.
  • 보조 프로세스는 false를 전달하고 캐시를 비활성화해요.

이어서 두 경로 모두 makeExclusiveKeychain을 만들어 initializedNetwork에 넘겨요. 그래서 같은 계정의 보조 프로세스는 같은 Postbox에서 네트워크 상태를 읽을 수 있고, 배타적 인스턴스 ID는 이미 비활성화된 네트워크 객체가 계속 쓰는 것을 막아요. (추론)[35]

MTContext.copyAuthInfoFrom:toTempKeychain:은 임시 keychain으로 인증 정보를 복사하는 상황을 위해 더 좁은 복사 집합을 제공해요. 복사하는 것은 이래요.

  • 임시 시간 차이
  • 영속 주소 집합
  • 영속 인증 정보
  • 임시 CDN 공개 키

authTokenById는 복사하지 않으며, 코드에서 이 행은 주석 처리되어 있어요. 따라서 인증 이전 토큰을 컨텍스트 간에 무조건 복사할 수 있는 데이터로 볼 수 없어요. 이 선택은 임시 컨텍스트가 DC 간 요청에서 토큰 이전을 다시 기다리게 할 수 있지만, 단기 인증 상태가 모든 사본으로 퍼지는 것을 피해요. (후반부는 추론)[39]

객체 아카이브에는 호환성 비용도 있어요.

  • Keychain.dictionary와 number는 모두 MTDeprecated.unarchiveDeprecated를 쓰며, 이 함수는 NSKeyedUnarchiver가 던진 예외를 잡은 뒤 빈 값을 반환해요.
  • 예상치 못한 타입을 읽으면 Swift 쪽에서 단언 실패가 발생해요.

코드는 단일 키 값 때문에 시작 과정 전체가 크래시하는 것보다 오래된 아카이브를 디코딩하지 못하는 것을 감수하는 쪽을 택해요. 대가는 유실된 키가 이후 네트워크 접근 때 재인증을 촉발하며, 진단할 수 있는 아카이브 버전 오류가 남지 않는다는 점이에요. (추론)[17]

인증 정보는 불변 키 하나만으로 이루어지지 않아요. MTDatacenterAuthInfo의 saltSet은 MTDatacenterSaltInfo 여러 개를 보관해요.

  • 메시지를 보낼 때 authSaltForMessageId는 집합을 순회하여 그 메시지 ID 이후에도 사용할 수 있고 남은 유효 메시지 수가 가장 많은 salt를 골라요.
  • 새 salt를 병합할 때 코드는 현재 시간에 해당하는 메시지 ID에 대해 아직 유효한 항목만 남기고 firstValidMessageId로 중복을 제거해요.

그래서 시계 조정이나 서버의 새 salt 전달 시, 이전 salt와 새 salt가 잠시 공존할 수 있어 호출자가 단일 패킷 경계에서 전환할 필요가 없어요. (마지막 문장은 추론)[4]

전역 시간 차이도 저장되는데, 메시지 ID가 서버 시간과 관련되기 때문이에요. setGlobalTimeDifference:는 새 값을 temp:globalTimeDifference에 기록해요. 재시작 후의 setKeychain:은 이 값을 먼저 복원한 뒤 주소와 키를 복원해요. 시계 보정을 UI 설정이 아니라 네트워크 인증 컨텍스트의 일부로 취급해요. 대가는 임시 저장소가 무효화되면 클라이언트가 이후 프로토콜 메시지에 기대어 시간을 다시 맞춰야 한다는 점이에요. (마지막 문장은 추론)[20] [21]

여기서 프로세스 공유는 신중하게 표현해야 해요. 앱, 알림 서비스, 기타 확장이 같은 계정 경로로 같은 Postbox를 열면 keychain 테이블을 통해 같은 아카이브 데이터를 보게 돼요. (추론) 이 코드 구간이 증명하는 것은 공유 저장소 추상화이며, 독립된 Apple Keychain access group의 사용이 아니에요. 확장 프로세스 협력의 실제 수명 주기는 푸시, 확장 프로세스와 다중 프로세스 협업을 참고해요. Postbox의 트랜잭션과 크래시 복구는 Postbox 스토리지 엔진을 참고해요.

시드에서 서버 설정으로 이어지는 주소 탐색

앱은 컴파일 시점의 IP를 완전한 디렉터리로 취급할 수 없어요. 진입 주소는 지역, 부하, 네트워크 정책에 따라 바뀌어요. 그래서 TelegramCore는 네트워크를 초기화할 때 먼저 최소한의 시드 집합(컴파일 시점에 들어 있는 초기 주소)을 설정하고, 인증된 DC의 help.getConfig로 모든 dcOption을 학습해요.

  • 테스트 환경에는 IPv4 시드 주소 3개를 설정해요.
  • 프로덕션 환경에는 DC 1~5의 IPv4와 IPv6 주소를 설정해요.

초기 주소의 포트는 모두 443이며 미디어나 CDN 주소가 아니에요.[13]

MTContext는 시드 주소 집합과 탐색된 주소 집합을 함께 보관해요. 조회할 때는 탐색된 집합을 우선 쓰고, 집합이 없거나 비어 있을 때만 시드 집합으로 폴백해요. 주소 집합을 갱신하면 이렇게 해요.

  • persistent:datacenterAddressSetById에 영속화해요.
  • 리스너에게 알려요.
  • 조건에 따라 기존 전송 방식을 리셋해요.

전송의 세부 사항은 MTProto 전송 계층에 속해요.[21]

MTDiscoverDatacenterAddressAction은 대상 DC에 주소가 없는 경우를 해결해요. 동작은 이래요.

  1. 아직 시도하지 않은 알려진 DC를 순회하며, 그 DC의 영구 키를 먼저 요구해요.
  2. 키가 준비되면 그 센터에서 백그라운드 요청 서비스를 시작하고, 직렬화기가 제공하는 getConfig 요청을 호출해요.
  3. 성공하면 대상 DC의 주소 목록만 취해 컨텍스트에 되써 넣어요.

마이그레이션 오류와 데이터 센터 간 인증

303 오류가 뜻하는 것은 연결 재시도가 아니라, 요청을 다른 DC에서 다시 실행해야 한다는 거예요. 공식 문서는 네 가지 오류를 정의하고, 각각 다음에 대응해요.

  • PHONE_MIGRATE_X: 번호 귀속
  • NETWORK_MIGRATE_X: 등록 출처 주소
  • USER_MIGRATE_X: 사용자 귀속
  • FILE_MIGRATE_X: 파일 위치

X는 재시도해야 할 DC ID예요.[24]

로그인의 실제 처리는 sendAuthorizationCode에 있어요.

  1. 정규식으로 PHONE_, USER_, NETWORK_에 MIGRATE_와 숫자 접미사가 붙은 것을 매칭하여 대상 DC ID를 꺼내요.
  2. changedMasterDatacenterId를 호출해 같은 계정 ID, Postbox, 전용 Keychain, 네트워크 설정, 테스트 환경으로 Network를 새로 만들어요.
  3. 새 네트워크에서 같은 auth.sendCode 요청을 다시 보내요.[34] [35]

여기서의 재실행 범위는 좁고 검증할 수 있어요. 최초 auth.sendCode의 오류 스트림만 감싸요. 두 번째 요청이 다시 실패하면 코드는 SESSION_PASSWORD_NEEDED에 대해서만 비밀번호를 가져오는 특별 처리를 하고, 다른 오류는 계속 밖으로 전파해요. 이렇게 하면 “실패한 API는 모두 멱등하게 재시도할 수 있다”는 가정이 범용 네트워크 계층에 묻히는 것을 피해요. 쓰기 작업이 DC를 넘어 자동으로 재실행될 수 있는지는 호출 지점이 API 의미에 따라 결정해야 해요. (추론)[34]

계정 메인 DC의 변경도 기존 Network를 제자리에서 수정하는 방식이 아니에요. changedMasterDatacenterId는 공유 설정과 Postbox 환경설정을 읽은 뒤 initializedNetwork를 호출하고, 새 네트워크로 새 UnauthorizedAccount를 만들어요. 이 객체는 원래의 shouldBeServiceTaskMaster 신호를 유지해요. 이전 객체는 전용 Keychain의 인스턴스 ID 때문에 쓰기 권한을 잃어요. 이 객체 교체는 이전 네트워크와 새 네트워크가 같은 미인증 계정에 동시에 키 상태를 쓰는 일을 막아요. (추론)[35] [18]

FILE_MIGRATE_X는 위의 로그인 분기를 타지 않아요. 파일 객체 자체가 dc_id를 포함하므로 다운로드 스케줄러가 이를 근거로 미디어 DC를 고를 수 있어요. 고정 iOS 커밋에는 이 오류에 대한 범용 DC 간 최후 대비책(폴백)이 없어요.

  • MTInternalMessageParser는 RPC 오류를 MTRpcError로 구성하고, MTRequestMessageService는 303에 대해 대상 DC를 고쳐 쓰거나 재전송하지 않아요.
  • V1, V2 다운로드는 각각 식별되지 않는 오류를 일반 실패로 분류하며, 업로드도 일반 오류로만 분류해요.
  • 클라이언트는 이를 근거로 새 worker를 만들거나, 인증을 import하거나, 새 DC에서 조각을 재실행하지 않아요.
  • Download.part를 직접 쓸 때의 일반 재시도도 여전히 원래 worker를 가리키므로 마이그레이션 폴백이 아니에요.[47] [48] [49] [50] [51] [52] [53]

네트워크 텔레메트리는 여전히 모든 303을 migrate로 분류하지만 재전송은 담당하지 않아요.[36] 자세한 내용은 FILE_MIGRATE의 최후 대비책(폴백) 경로를 참고해요.

macOS fork에도 범용 DC 간 재실행은 없어요. 마이그레이션 텍스트 매칭은 로그인의 PHONE_, USER_, NETWORK_ 접두사만 다루며, RPC 오류는 여전히 MTRpcError로 위로 던져져요. V1, V2 다운로드와 업로드 모두 이 오류에서 새 DC를 고르는 분기가 없어요.[54] [55] [56] [57] [58] [59] [60]

  • MTProto는 requiredAuthToken을 달고 시작할 수 있어요.
  • 대상 DC의 토큰이 일치하지 않으면 MTContext에 토큰을 가져오도록 요청해요.
  • 컨텍스트는 대상 DC마다 MTDatacenterTransferAuthAction을 하나만 유지하며, 실패하면 1, 2, 4, 8, 16, 32, 60초 상한의 지수 백오프로 여전히 대기 중인 연결에 다시 알려요.[25] [26]

  1. 소스 연결을 멈춰요.
  2. 대상 DC에 요청 서비스를 만들어요.
  3. auth.importAuthorization을 호출해요.
  4. 성공하면 전달받은 authToken을 컨텍스트에 기록해요.

대상 세션은 토큰을 아직 import하지 않았을 때 일반 전송을 먼저 만들지 않아요. MTProto는 자신에게 requiredAuthToken이 있고 컨텍스트에 있는 같은 DC의 값과 다르면 이렇게 해요.

  • AwaitingDatacenterAuthToken 상태를 설정해요.
  • MTContext에 이전을 요청해요.

이 차단 지점 덕분에 로그인 상태가 필요한 worker는 대상 센터에서 잘못된 인증으로 비즈니스 요청을 곧바로 보내지 않아요. 이는 이전이 막히면 그 세션이 조용히 미인증 모드로 강등되지 않고 대기 상태를 유지한다는 뜻이기도 해요.[25] [40]

인증 이전과 QR 코드 로그인 이전은 혼동해서는 안 돼요. AuthTransfer.swift가 auth.exportLoginToken의 loginTokenMigrateTo 생성자를 처리할 때도 미인증 계정 네트워크를 다시 만들고 auth.importLoginToken을 호출해요. 이 흐름은 로그인 토큰을 위한 것이고, 이 글의 MTDatacenterTransferAuthAction은 기존 사용자의 다른 DC에서의 인증 가용성을 위한 거예요. 둘 다 대상 DC를 바꾸지만 메시지 타입, 상태 머신, 완료 조건이 달라요.[41]

미디어 DC, CDN, 연결 풀

미디어 트래픽의 문제는 처리량이 메인 세션을 압박한다는 거예요. 공식 문서는 큰 파일 요청을 미디어 연결에 두어 업데이트와 일반 RPC를 방해하지 않게 하라고 권고해요. 현재 클라이언트는 Download worker의 역할을 worker로 두고 masterDatacenterId, isMedia, isCdn을 명시적으로 전달해요. 다운로드 연결의 온라인 상태와 일시 정지 상태는 메인 세션과 독립적이에요.[2] [29]

MultiplexedRequestManager는 대상과 continueInBackground에 따라 작업 풀을 나눠요. 상한은 이래요.

  • 일반 DC의 상한은 worker당 요청 3개, 대상당 worker 4개예요.
  • CDN의 기본값도 3과 4예요.
  • 현재 네트워크 엔진이 Rust이면 생성자는 CDN 상한을 worker당 요청 4개, 대상당 worker 8개로 조정해요.

요청은 같은 리소스의 최고 우선순위로 정렬하고, 우선순위가 같으면 큐 진입 ID로 정렬해요. 비어 있는 worker는 20분 지연 후 제거해요.[30] [31]

대상 키에 continueInBackground가 포함되므로, 같은 DC의 포그라운드 요청과 백그라운드 허용 요청은 같은 worker 그룹을 다투지 않아요.

구독을 취소하거나 요청이 끝나면 관리자는 이렇게 처리해요.

  • 구독을 취소하면 먼저 대기 배열에서 요청을 지워요. 요청이 이미 실행 중이면 이 worker 요청을 dispose하고 실행 목록에서 제거해요.
  • 성공 또는 오류 콜백마다 점유한 슬롯을 해제하고 곧바로 다음 배치를 스케줄링해요.

이 모델은 직렬 Queue 하나가 큐, 우선순위, worker 목록을 보유하므로 이 스케줄링 구조가 스레드를 넘나들며 부분적으로 갱신되는 일이 없어요. (추론)[30]

Download는 별도의 요청 인코딩을 자체 구현하지 않아요. worker requestService를 NetworkEngineRequest로 감싸 범용 오류 정책과 타임아웃 옵션을 재사용해요.

  • uploadPart의 정적 버전은 saveFilePart 요청을 .main(datacenterId)로 향하게 하고 백그라운드 계속 실행을 요구해요.
  • part는 upload.getFile의 일반 파일 응답을 파싱하며, CDN 리다이렉트 생성자를 만나면 이 저수준 메서드 안에서 내용을 해석하지 않아요.

라우팅, 세션, 동시성, 파일 조각 파싱이 각각 하나의 컴포넌트에 귀속돼요.[29] [30]

CDN은 일반 DC의 하드코딩된 RSA 공개 키를 재사용하지 않아요. 대신 이렇게 해요.

  • 서버와 클라이언트 모두 CDN 키가 하나뿐일 때만 그 하나로 격하하여 사용하고, 그렇지 않으면 실패해요.[32] [6]

이 정책의 보안상 이점은 CDN 신뢰 앵커가 메인 DC가 돌려준 설정에 따라 갱신되며, CDN이 스스로 보고한 키를 받아들이지 않는다는 거예요. 대가는 CDN을 처음 쓸 때 메인 네트워크가 설정을 가져올 수 있어야 한다는 점이에요. 메인 네트워크를 쓸 수 없으면 CDN 핸드셰이크는 계속되지 않아요. 가용성을 위해 핑거프린트를 건너뛰는 것보다 이 거부 우선 정책이 더 알맞아요. (추론)

미디어 DC의 주소 플래그와 CDN 플래그는 모두 MTDatacenterAddress에 저장되며 동등성 판단에 참여해요. MTContext.transportSchemesForDatacenterWithId는 enforceMedia일 때 preferForMedia 주소만 남겨요. 요청이 미디어로만 표시되고 미디어가 강제되지 않았더라도, 목록에 미디어 우선 주소가 있으면 미디어가 아닌 주소는 여전히 걸러내요. 파일 조각의 길이, CDN 리다이렉트, 캐시 재사용은 이 장에서 다루지 않으며 미디어 리소스, 다운로드/업로드, 캐시를 참고해요.[33] [21]

관리자의 포화 판단은 전역 제한이 아니라 대상별로 해요. 먼저 대상 하나가 worker 수 상한에 도달했는지 보고, 그다음 각 worker가 요청 수 상한에 도달했는지 확인해요. 대상이 포화되지 않았을 때만 worker를 새로 만들거나 대기 중인 요청을 기존 worker에 넣어요. 그래서 바쁜 CDN DC의 큐가 다른 일반 미디어 DC의 worker 몫을 고갈시키지 않아요. 대가는 대상마다 유휴 연결이 여러 개 남을 수 있다는 점이며, 그래서 구현은 즉시 중지하지 않고 20분 지연 후 회수해요. (추론)[30]

리소스 우선순위도 요청의 고정 필드가 아니에요. 호출자는 resourceId로 우선순위를 하나 이상 Bag에 넣어요. 스케줄러는 매 라운드마다 같은 리소스의 최댓값을 취한 뒤, 그 우선순위 최댓값의 내림차순과 요청 ID의 오름차순으로 정렬해요. 마지막 우선순위 disposable이 해제되면 리소스 카운터가 제거되고 다시 스케줄링돼요.

이 설계는 스크롤하는 미디어 뷰가 이미 큐에 있는 요청을 복제하거나 취소하지 않고도 같은 리소스의 다운로드 가중치를 일시적으로 높일 수 있게 해요. 비용은 우선순위가 다음 스케줄링 라운드에서야 적용되며, 이미 worker로 보낸 요청은 선점되지 않는다는 거예요. (추론)[30]

CDN 키 캐시에는 무효화 복구 경로도 있어요. MTDatacenterAuthMessageService.reset:은 CDN에 대해 먼저 publicKeysForDatacenterWithId를 읽어요. 그다음은 경우에 따라 달라요.

  • 목록이 비어 있으면 대기 상태로 들어가 컨텍스트에 알림을 요청해요.
  • 목록이 비어 있지 않지만 resPQ 핑거프린트와 일치하지 않으면 한 번만 다시 가져와요.
  • 두 번째에도 일치하는 항목이 없으면, 서버의 핑거프린트 목록과 클라이언트의 목록이 모두 정확히 한 항목일 때만 그 유일한 키를 사용해요.

이 특수 분기는 단일 키 설정 갱신 중의 가용성을 높이되, 다중 키의 모호함은 추측하지 않아요. (추론)[6] [32]

호출 관계로 보면 NetworkHelper는 메인 Network에서만 help.getCdnConfig를 시작하고, 반환된 cdnPublicKey를 dcId로 걸러요. 이어서 MTContext가 그 결과를 대기 중인 CDN 핸드셰이크 서비스에 알려요. 따라서 CDN의 첫 키 생성에는 최소한 메인 DC 네트워크가 동작하거나 복구할 수 있는 CDN 공개 키 캐시가 이미 있어야 해요. CDN 주소의 cdn 플래그를 키의 출처로 오해하지 않아요. 주소는 어디로 연결할지를 맡고, 메인 DC가 돌려준 키는 누구를 신뢰할지를 맡아요. (마지막 두 문장은 추론)[32] [6] [33]

설계 트레이드오프

  • Telegram은 전역 공유 키 대신 DC별 독립 키를 택했어요.

    • 장점은 키, 엔드포인트, 인증 이전의 경계가 분명하다는 거예요.
    • 비용은 새 DC에 처음 접근할 때 DH와 인증 import가 필요하고 더 많은 상태를 영속화해야 한다는 거예요.

  • 세션 ID만 교체하는 대신 영구 키와 바인딩된 임시 키를 택했어요.

    • 장점은 순방향 비밀성을 수명과 갱신기로 명시적으로 강제할 수 있다는 거예요.
    • 비용은 바인딩 실패, 만료 임박, 영구 키 유실이 모두 상태 머신의 분기를 늘린다는 거예요.

  • IP 목록만 유지하는 대신 help.getConfig를 주소 속성으로 해석하는 방식을 택했어요.

    • 장점은 같은 디렉터리가 미디어, CDN, TCP 제한, 프록시 선호를 표현할 수 있다는 거예요.
    • 비용은 주소를 갱신할 때 기존 연결에 알려야 하고 시드와 캐시의 폴백 순서를 처리해야 한다는 거예요.

  • 다운로드마다 연결을 만드는 대신 상한이 고정된 다중화 worker 풀을 택했어요.

    • 장점은 동시성, 백그라운드 트래픽, 유휴 리소스를 명확히 통제할 수 있다는 거예요.
    • 비용은 다운로드 스케줄링이 리소스 우선순위, 포화 판단, 지연 회수를 유지해야 한다는 거예요.
