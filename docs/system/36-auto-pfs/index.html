비밀 채팅 자동 키 교체의 트리거 지점

고정 iOS 및 macOS fork의 자동 PFS 키 교체는 로컬 발신 작업 카운트가 트리거하며, 1주일 타이머가 트리거하지 않아요.

검증 대상: 종단 간 암호화와 로컬 보안

미검증 사항:

  • overtake/Telegram-iOS 고정 커밋은 체크아웃했지만, 이 fork의 PasscodeCore 전체 호출 경로가 업스트림 iOS의 로컬 보호 경로와 일치하는지는 여전히 미검증이에요.

자동 트리거의 실제 호출 지점

고정 iOS TelegramCore는 PFS(전방 비밀성) 키 교체를 실제로 자동 시작해요. 시작을 판단하는 트리거 함수는 secretChatInitiateRekeySessionIfNeeded이고, 상수 keyUseCountThreshold의 값은 100이에요. 이 함수는 다음 순서로 동작해요.

  1. 시퀀스 레이어 채팅만 받아들여요.
  2. 이미 rekeyState가 있으면 즉시 반환해요.
  3. 현재 사용 가능한 key를 가져와요.
  4. 그 key의 useCount(key를 쓴 횟수)가 100 이상이면 .pfsRequestKey 발신 작업을 기록하고, 상태를 .requesting으로 설정해요. [1]

macOS fork의 같은 함수도 동일한 임계값과 상태 전이를 유지해요. [15]

[1]

트리거 함수를 호출하는 곳도 소스 코드에서 확인돼요. 발신 작업을 기록하는 helper addSecretChatOutgoingOperation이 다음 순서로 일해요.

  1. 현재 key의 useCount에 1을 더해요.
  2. 전달받은 발신 작업을 기록해요.
  3. 마지막에 위 트리거 함수를 호출해요. [2]

SecretChatKey는 카운트를 필드 u로 인코딩하므로 카운트는 재시작 후에도 복원돼요. [3] 그래서 helper를 100번째로 거치는 로컬 작업은 먼저 카운트를 99에서 100으로 올린 다음, 같은 트랜잭션 안에서 임계값을 검사하고 키 교체 요청을 추가해요.

카운트 단위는 addSecretChatOutgoingOperation을 거치는 로컬 SecretOutgoing 작업이에요. 엄밀한 의미의 사용자 텍스트 메시지 100건이 아니에요. 다음 서비스 작업이 모두 이 helper를 호출할 수 있어요.

  • 메시지 전송
  • 읽음 확인
  • 삭제
  • 스크린샷
  • 레이어 공지
  • 재전송

pfsRequestKey 자체는 트리거 함수가 작업 로그에 직접 기록하므로 helper를 다시 호출하지 않아요. [1] [2]

실제 전송은 worker(작업 로그를 구독하다가 항목이 생기면 처리하는 쪽)가 맡아요. 계정이 시작될 때 SecretOutgoing 병합 작업 로그를 지속적으로 구독하는 worker가 만들어지고, 이 worker는 pfsRequestKey 작업에 대해 전용 pfsRequestKey 함수를 호출해요. [4] [5]

그래서 오프라인일 때도 요청은 먼저 영속화(저장)돼요. 네트워크를 쓸 수 있게 되면 worker가 이렇게 이어서 처리해요.

  1. 검증된 DH 구성을 가져와요.
  2. gA를 계산하고 검증해요.
  3. .requesting을 .requested로 바꿔요.
  4. 암호화된 서비스 액션을 전송해요. [6]

macOS fork의 동일한 호출 체인

macOS fork도 iOS와 호출 체인이 같아요. overtake/Telegram-iOS의 고정 커밋 a24bbe45f9861f736a79916a50898512f751e0dc를 보면 다음과 같아요.

  • keyUseCountThreshold를 100으로 정의해요.
  • useCount가 임계값에 도달하면 곧바로 .pfsRequestKey를 기록하고 .requesting으로 설정해요. [15]
  • fork의 addSecretChatOutgoingOperation도 먼저 현재 key의 카운트를 증가시킨 뒤 secretChatInitiateRekeySessionIfNeeded를 호출해요. [16]
  • useCount 역시 필드 u로 인코딩되므로 카운트는 재시작 후에도 유지돼요. [17]

fork를 정적으로 검색해 보니 secretChatInitiateRekeySessionIfNeeded를 호출하는 곳은 이 helper뿐이었어요. 그래서 보충 32의 “fork에서는 임계값을 시작 작업으로 바꾸는 스케줄링 지점을 찾지 못했다”는 결론은 이번 검증으로 뒤집혔어요. macOS fork 장별 검증(08–15장) fork의 로컬 발신 작업이 100에 도달하면 PFS 요청이 자동으로 추가돼요.

iOS 경로에 없는 1주일 스케줄

iOS TelegramCore와 macOS fork의 자동 시작 체인에는 1주일 임계값도, 유휴 시계 트리거도 없어요. 이번 정적 추적에서 확인한 근거는 이래요.

  • 두 경로 모두 자동 시작 체인의 호출자는 addSecretChatOutgoingOperation 하나뿐이었어요.
  • 트리거 함수는 rekeyState, 발신 작업 인덱스, useCount만 읽어요.
  • SecretChatKey는 지문, key, 유효 구간, useCount를 저장하며 마지막 키 교체 시각은 저장하지 않아요.

그래서 일주일 동안 새로운 로컬 발신 작업이 없으면, 이 경로들은 시간이 흘렀다는 이유만으로 .pfsRequestKey를 만들지 않아요. [1] [2] [3] [15] [16] [17]

여기서 “자동”은 이벤트 기반이며 백그라운드 타이머 작업이 아니에요.

  • 계정 시작 시 만들어진 worker는 작업 로그 뷰를 구독하고, 로그에 entry가 있으면 이 네트워크 동작을 실행해요.
  • 대화를 열거하지도, 키 교체 판정을 주기적으로 호출하지도 않아요.

따라서 새로운 로컬 발신 작업이 helper를 거칠 때만 카운트와 임계값이 다시 검사돼요. [2] [4] [5]

저장소에는 TDLib의 또 다른 Secret Chat 구현도 들어 있어요. SecretChatActor::run_pfs는 다음 중 하나에 해당하는 경우를 실제로 검사해요.

  • 메시지 ID가 마지막 키 교체 이후 100을 넘었어요.
  • last_timestamp가 현재 시각으로부터 7일을 넘었어요.

코드는 엄격한 less-than 부호를 쓰므로, 메시지 ID 조건은 차이가 101이 되었을 때 성립해요. [11]

[11]

이 TDLib 조건은 이 장의 iOS 주 경로에 대한 증거가 될 수 없어요. 이유는 이래요.

  • iOS Bazel 규칙은 libtde2e.a와 libtdutils.a만 내보내요. [12]
  • tde2e의 소스 파일 목록에는 td/e2e 파일만 있으며, tdutils, OpenSSL, zlib만 private으로 링크해요. [13]
  • 반대로 SecretChatActor.cpp는 tdcore의 TDLIB_SOURCE 목록에 속해요. [14]

따라서 고정 커밋 안의 TDLib 7일 조건은 저장소와 함께 들어왔지만 이 iOS TD 라이브러리로는 내보내지지 않는 또 다른 구현이에요. TelegramCore에 1주일 트리거가 없다는 위의 결론은 바뀌지 않아요.

영속 상태와 키 교체 진행

SecretChatRekeySessionData는 진행 중인 키 교체 세션을 requesting, requested, accepting, accepted 네 가지 상태로 나타내요. 이 중 두 상태는 값을 저장해요.

  • requested: private a와 검증된 DH 구성을 저장해요.
  • accepted: 후보 key와 fingerprint를 저장해요.

이 값들은 PostboxCoding을 통해 SecretChatSequenceBasedLayerState.rekeyState에 기록돼요. [7]

인바운드 복호화기(받은 메시지를 푸는 쪽)는 네트워크로 오가는 네 가지 wire action을 SecretChatRekeyServiceAction으로 매핑해요. 같은 처리 트랜잭션 안에서 그 액션을 secretChatAdvanceRekeySessionIfNeeded에 넘겨요. [8] 상태는 이렇게 전진해요.

  • 로컬 요청이 전송될 때에야 .requesting에서 .requested로 전진해요.
  • 수락 측이 gB를 보낼 때에야 .accepting에서 .accepted로 전진해요. [6]

세션이 끝나는 과정은 시작 측(키 교체를 먼저 요청한 쪽)과 수락 측(요청을 받은 쪽)이 달라요.

  • 시작 측: 세션 ID가 일치하는 AcceptKey를 받으면 gB와 fingerprint를 검증해요. 검증에 성공하면 CommitKey를 추가하고 rekeyState를 지운 다음, 커밋 작업 이후의 표준 발신 인덱스로 새 key를 만들어요.
  • 수락 측: 일치하는 CommitKey를 받으면 후보 fingerprint를 확인하고, 같은 인덱스 규칙으로 새 key를 저장하며, 상태를 지우고 noop을 추가해요. [9]

새 key의 useCount 초깃값은 0이에요. [9]

도표에서 시작 측이 AcceptKey를 받은 이후의 상태를 Stable로 표기한 건, 소스 코드가 이 시점에 이미 rekeyState를 지우기 때문이에요. 이 표기가 네트워크상의 CommitKey가 확인되었다는 뜻은 아니에요. 새 key의 유효 하한은 이 커밋 작업 이후에 놓이므로, CommitKey는 여전히 이전 key로 보호돼요. [9]

양측이 동시에 시작했을 때의 판정

이 구현에서는 더 작은 세션 ID가 이겨요. iOS TelegramCore는 부호 있는 64비트 rekeySessionId를 수치로 비교해 판정하는데, 로컬 상태가 .requesting 또는 .requested일 때만 비교해요.

  • 인바운드(상대가 보낸) 세션 ID가 로컬 ID보다 작으면: 코드는 로컬 세션에 AbortKey를 추가한 뒤, 더 작은 ID를 가진 원격 세션을 수락해요.
  • 인바운드 ID가 로컬 ID보다 크거나 같으면: 코드는 acceptSession을 거짓으로 설정해 그 원격 요청을 수락하지 않아요. 두 ID가 같은 경우는 랜덤 ID 충돌 확률이 극히 낮지만, 코드는 이때도 거부 분기를 타요. [10]

판정은 두 RequestKey의 전송 확인을 기다리지 않아요. 인바운드 서비스 액션을 처리하는 Postbox 트랜잭션 안에서 결정하고 후속 작업을 기록해요. [8] [10]

이 규칙은 두 세션이 모두 로컬 시작 단계에 있을 때만 적용돼요. 로컬이 이미 .accepting 또는 .accepted에 있으면 이 분기는 ID를 비교하지 않고 기존 상태를 유지해요. [10]
