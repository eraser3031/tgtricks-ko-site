음성 녹음과 사전 업로드

음성 메시지와 원형 비디오의 녹음 데이터 흐름, 사전 업로드 재사용, 취소 정리 경로를 나눠서 살펴봐요.

시스템 설계 · 검증과 보충 · 보충 39 · 도표 1 · 코드 발췌 5 · 인용 18 · 소스 기준선: TelegramMessenger/Telegram-iOS@f1dd7a2d, overtake/TelegramSwift@579cebbf

검증 대상: 메시지 전송 파이프라인과 오프라인 작업 큐

미검증 사항:

  • 음성 미리보기가 삭제된 뒤에도 deleteMediaRecording은 현재 파일에서 리소스 삭제를 직접 부르지 않아요. 이 초안의 LocalFileMediaResource가 디스크에 쓴 바이트를 MediaBox가 언제 회수하는지는 미검증이에요.
  • 원형 비디오가 discardVideo를 부른 뒤, 모든 표시 경로에서 컨트롤러와 노드가 언제 반드시 사라지는지는 미검증이에요. 그래서 interface가 사라질 때 하는 정리를, 취소 이벤트가 동기적으로 보장하는 동작이라고 말할 수 없어요.

녹음기와 사전 업로드의 실제 경계

MessageMediaPreuploadManager(전송 전에 미디어를 미리 올리는 관리자, 이하 manager)를 모든 녹음기가 직접 부르는 건 아니에요. 이 보충 문서는 그 경계를 확인해요.

  • 음성 메시지: 녹음 경로가 preUpload를 부르지 않아요. 녹음을 멈추면 완전한 Ogg 데이터를 받아 LocalFileMediaResource에 쓰고, 그다음 EnqueueMessage를 만들어요. manager에는 그 뒤 전송 대기 메시지를 업로드하는 경로에서야 들어가요. 그래서 음성 메시지는 녹음하면서 업로드하는 방식이 아니에요. [1] [2]
  • 원형 비디오: 채팅 컨트롤러가 대상이 비밀 채팅이 아닐 때만 allowLiveUpload를 참으로 설정해서 VideoMessageCameraScreen에 넘겨요. [3] 이 화면은 LegacyLiveUploadInterface로 실시간 파일 업로드를 감싸요. 이 인터페이스는 TelegramEngine.Resources.preUpload를 거쳐 계정의 MessageMediaPreuploadManager.add를 간접적으로 불러요. [4] [5]

그래서 원형 비디오 구현은 07장에서 설명한 manager를 실제로 다시 써요. 다만 manager를 부르는 쪽은 비디오 화면의 실시간 업로드 인터페이스이고, 음성 녹음기가 아니에요.

앞서 채팅 화면 기법에서 녹음 제스처와 전송 전환을 설명했어요. 이 보충 문서는 전송 수명 주기만 따라가요.

인코딩을 거쳐 전송 대기 미디어가 되는 음성

ManagedAudioRecorder는 입력 버퍼를 60밀리초, 1,920바이트짜리 인코딩 패킷으로 이어 붙여 TGOggOpusWriter에 써요. 이 패킷은 녹음 인코딩의 입력 단위이고, MTProto 업로드 part(업로드를 나눈 조각)가 아니에요.

takeData는 호출한 쪽이 요청하면 쓰기를 끝내고, dataItem 안의 완전한 압축 데이터와 길이, 파형을 돌려줘요. [1]

[1]

음성을 바로 보내는 분기는 이렇게 움직여요. [2]

  1. stop을 부른 다음 takenRecordedData를 받아요.
  2. 무작위 로컬 파일 id를 만들고, storeResourceData로 완전한 compressedData를 써요.
  3. 이 리소스와 .Audio(isVoice: true, ...)를 sendMessages의 EnqueueMessage에 넣어요.

미리보기 후 전송도 마찬가지예요. 이미 있는 초안 리소스를 같은 종류의 전송 대기 파일로 감싸서 enqueueMessages를 불러요. [6]

[2]

이 경로를 보면 “녹음이 끝난 뒤에야 업로드한다”는 경계가 분명해요. 전송 대기 파일은 이후에 messageMediaPreuploadManager.upload로 업로드되지만, 이때 원본 리소스는 이미 완전해요. 그래서 음성은 녹음하는 동안 네트워크 작업을 겹쳐 실행할 수 없어요. [7]

원형 비디오의 녹화 중 업로드

파일이 커지면서 공유 업로드를 움직이는 구조

최신 원형 비디오 카메라는 0.09초마다 같은 출력 파일의 경로를 알려줘요. 비디오 화면은 첫 보고를 받으면 setupLiveUpload를 부르고, 1.5초 뒤에 그 경로로 LegacyLiveUploadInterface를 만들어요. [8]

이 인터페이스의 부모 클래스는 매초 파일 크기를 확인해요. 파일이 지난번보다 32 KiB 넘게 커지면 부모 클래스가 fileUpdated(false)를 일으켜요. [9]

파일이 처음 커졌다는 알림이 오면 인터페이스는 무작위 id를 만들고, 그 id로 preUpload가 돌려준 disposable(구독을 해제하는 핸들)을 쥐고 있어요. 그리고 파일 경로와 현재 바이트 수를 ResourceData로 내보내되 isComplete는 거짓으로 둬요. 녹화가 끝나면 fileUpdated(true)가 같은 경로와 크기로 완료 상태를 내보내고, 이 id를 돌려줘요. [4]

[4]

Resources.preUpload는 업로더를 따로 만들지 않아요. 네트워크, Postbox, id, 계속 갱신되는 source(업로드할 데이터를 읽어 오는 원본)를 그대로 계정의 MessageMediaPreuploadManager.add에 넘겨요. [5] 그래서 비디오 파일이 커지는 것, 사전 업로드 구독, 최종 전송 대기 메시지가 로컬 파일 id 하나로 이어져요.

카메라 프레임이 아닌 전송 part

preUpload가 넘기는 건 .custom source예요. multipartUpload는 이런 source에 1,024바이트짜리 header 표식을 설정하지만, 데이터를 읽는 일정은 여전히 MultipartUploadManager가 관리해요. [10]

part 크기는 이렇게 정해져요. [11]

  • 크기 hint가 없으면 manager는 처음에 128 KiB 기본 part와 병렬 슬롯 3개를 써요.
  • 업로드가 시작되기 전에 이미 완전한 파일을 받았다면, 보통 크기의 소형 파일은 16 KiB part로 바꿔 써요.
  • 파일이 10 MiB보다 크면 512 KiB big part로 바꿔요.

스트리밍 중에는 manager가 기본 크기의 완전한 part만 보내요. header를 아직 제출할 수 없을 때는 첫 part 자리를 먼저 비워 두고, 뒤따르는 완전한 part가 먼저 진행되게 해요. source가 complete가 되면 상태 머신이 첫 part를 뒤늦게 보내서 InputFile을 완성해요. 그래서 실시간 업로드는 계속 커지는 MP4를 읽으면서도, 끝에는 쓸 수 있는 헤더 정보를 기다리게 돼요. [12]

[12]

녹화 종료 후의 메시지 연결

원형 비디오가 끝나면 화면은 클립 조정이 없을 때만 이렇게 해요. [13]

  1. LegacyLiveUploadInterfaceResult.id로 LocalFileMediaResource를 만들고 최종 비디오 데이터를 동기적으로 저장해요.
  2. .instantRoundVideo 속성이 붙은 TelegramMediaFile을 만들고, completion을 통해 채팅 컨트롤러가 큐에 넣게 해요.

채팅 컨트롤러는 답장과 연결 id를 채운 뒤 마지막으로 sendMessages를 불러요. [3]

전송 대기 미디어를 업로드할 때는 .resource로 manager를 불러요. manager는 리소스가 LocalFileMediaResource라는 것만 알아채면 그 file id를 꺼내 기존 upload context(업로드 하나의 진행 상태를 담은 객체)에 추가해요. 새 multipart 세션은 시작하지 않고, 둘 중 하나를 해요.

  • 이미 알려진 진행률이나 완료 결과를 다시 보내 줘요.
  • 아직 실행 중인 업로드를 구독해요. [7] [14]

[14]

클립 편집, 여러 녹화 결과 이어 붙이기, 그 밖의 조정은 실시간 인터페이스의 id를 유지하지 않고 LocalFileVideoMediaResource 분기를 타요. [13] 반면 localIdForResource는 LocalFileMediaResource만 알아봐요. 그래서 이런 원형 비디오는 실시간 업로드 context를 찾지 못하고, 최종 리소스를 기준으로 업로드 경로를 처음부터 다시 거쳐야 해요. [14]

서버가 확인해 주면 applyUpdateMessage가 로컬과 서버 TelegramMediaFile의 크기와 MIME 타입을 비교하고, 로컬 리소스 데이터를 서버 리소스 id로 옮겨요. 07장의 random id 매핑은 여전히 로컬 메시지를 클라우드 메시지로 다시 쓰는 식별 메커니즘이에요. [15]

취소, 실패, 리소스 보존

음성 녹음을 취소하면 deleteMediaRecording이 이렇게 정리해요. [16]

  • 녹음기를 해제하고 recorderDataDisposable을 취소해요.
  • 녹음 초안 상태를 지워요.
  • 입력 패널에 녹음 미디어를 삭제하라고 알려요.

녹음기가 사라질 때는 Audio Unit을 멈추고 오디오 세션과 tone renderer를 해제해요. 그래서 녹음 중이지만 아직 LocalFileMediaResource에 쓰지 않은 음성에는 취소할 사전 업로드 작업이 없어요. [17]

원형 비디오는 달라요. 실시간 인터페이스가 preUpload의 disposable을 인스턴스 필드에 저장하고, 인터페이스가 사라질 때 이 필드를 dispose해요. [4] manager는 마지막 holder(업로드를 구독 중인 쪽)가 떠났다는 걸 받으면 1초 동안 기다려요. 그때까지도 구독자가 없으면 multipart upload를 dispose하고, 그 id의 context를 지워요. [14] “원형 비디오 화면을 닫으면 실시간 업로드를 해제한다”는 동작에서, 소스 코드로 확인된 네트워크 정리 경로는 이거예요.

하지만 원형 비디오의 cancelVideoRecording 자체는 화면 밝기만 되돌려요. discardVideo는 취소를 일으키고 컨트롤러를 닫아 달라고 요청하지만, liveUploadInterface를 직접 dispose하지는 않아요. [18] 그래서 실시간 업로드는 화면 노드와 인터페이스가 소멸 단계에 들어가야 멈춰요. 취소 동작이 곧바로 내보내는 전용 네트워크 취소 호출로 멈추는 게 아니에요.

사용자가 1초 유예 안에 같은 id에 다시 관심을 만들면 manager는 context를 재사용해요. 지금 원형 비디오 UI에는 이렇게 다시 연결하는 경로가 보이지 않아요. [14]

미검증 문제

  • 음성 미리보기가 삭제된 뒤에도 deleteMediaRecording은 현재 파일에서 리소스 삭제를 직접 부르지 않아요. 이 초안의 LocalFileMediaResource가 디스크에 쓴 바이트를 MediaBox가 언제 회수하는지는 미검증이에요.
  • 원형 비디오가 discardVideo를 부른 뒤, 모든 표시 경로에서 컨트롤러와 노드가 언제 반드시 사라지는지는 미검증이에요. 그래서 interface가 사라질 때 하는 정리를, 취소 이벤트가 동기적으로 보장하는 동작이라고 말할 수 없어요.
