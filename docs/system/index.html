시스템 설계 개요

Telegram iOS와 macOS 클라이언트의 계층, 데이터 흐름, 엔지니어링 체인, 복구 경계를 정리해요.

Telegram 클라이언트는 플랫폼 UI, 공유 도메인 코어, 전송, 저장의 네 계층으로 이루어져 있어요.

  • 화면과 시스템 쪽: TelegramUI, iOS 확장, macOS AppKit 계층이 화면 표시와 시스템 연동을 맡아요.
  • 코어, 전송, 저장 쪽: TelegramCore, Postbox, TelegramApi, MtProtoKit이 계정, 상태, 프로토콜, 네트워크를 담당해요.

계정마다 독립된 Postbox, 네트워크 객체, 백그라운드 작업을 가져요. 계정 디렉터리는 현재 계정과 계정 간 설정을 저장해요. 전체 아키텍처와 모듈 계층 다중 계정, 로그인, 구성 동기화

Postbox(로컬 저장소 계층)는 로컬 상태를 기록하는 유일한 주체예요. 도메인 테이블, 작업 로그, 인덱스, 파생 뷰를 같은 직렬 큐의 SQLite 트랜잭션에 둬요.

기록이 커밋되면 변경이 뷰 증분(바뀐 부분만 담은 뷰 업데이트)으로 UI에 흘러가요. 네트워크와 백그라운드 작업은 UI 상태를 직접 고치지 않아요. 먼저 상태 관리자나 영속 작업에 들어간 뒤, 트랜잭션이 관찰할 수 있는 결과를 발행해요. Postbox 스토리지 엔진 Postbox 뷰와 메시지 이력 모델

데이터 흐름은 SwiftSignalKit의 Signal(구독해서 값을 받아 보는 비동기 스트림)이 중심이에요. 구독, 취소, 큐 전환, 공유 값 모두 분명한 객체가 있어요. AccountStateManager, 전송 관리자, 미디어 페처는 각자의 큐에서 비동기 이벤트를 모아요. 이 모델 덕분에 푸시, RPC, 디스크, UI가 비동기로 실행되는 중에도 상태 커밋은 복구할 수 있는 경계로 좁혀져요. 리액티브와 동시성 모델 업데이트 동기화

macOS는 submodules/telegram-ios의 공유 코어를 재사용해요. 이 서브모듈은 현재 체크아웃되어 있고 a24bbe45f9861f736a79916a50898512f751e0dc에 고정되어 있어요. overtake/Telegram-iOS의 fork이고, TelegramCore는 macOS Swift Package 형태로 데스크톱 앱에 제공돼요. [1] [2]

20장에서 추가로 검증했어요. 이 고정 지점은 공통 병합 기준점과 비교해 파일 트리 내용 차이가 없지만, 이 사이트의 iOS 업스트림 고정 지점보다 앞서 있어요. 그래서 데스크톱이 공유 아키텍처를 쓴다고 해서 업스트림 이후에 추가된 모든 기능을 갖췄다는 뜻은 아니에요. macOS fork의 출처와 차이

시스템 지도

아래 도표는 주요 하위 시스템을 하나의 상태 흐름 안에 배치해요. 실선은 호출 방향, 상태 흐름, 리소스 흐름을 뜻해요. 네트워크가 돌려준 업데이트도 결국 계정 상태 관리자와 Postbox를 거쳐 뷰 계층으로 돌아와요. 엔지니어링 체인은 검증된 생성물과 네이티브 라이브러리를 두 플랫폼의 앱 산출물로 조립해요.

이 도표에서 계정은 격리 단위예요. 한 계정의 pts(공개 업데이트의 순서 번호), 작업 로그, 미디어 캐시 참조, 인증 상태를 다른 계정이 공유하면 안 돼요. 계정 디렉터리, App Group, 플랫폼 확장은 또 다른 경계 집합이에요. 이 세 가지는 시작과 접근 권한을 해결할 뿐, 계정 내부의 트랜잭션과 큐 제약을 대신하지 못해요. 다중 계정, 로그인, 구성 동기화 푸시, 확장 프로세스와 다중 프로세스 협업

Rust 엔진은 iOS 업스트림에서 교체할 수 있는 MTProto 데이터 평면(실제 데이터를 주고받는 부분)이에요.

  • C FFI(언어 사이 함수 호출 인터페이스)로 NetworkEngine에 연결돼요.
  • MTContext는 여전히 주소, 키, salt, 인증 토큰, 시간 차이를 보관해요.
  • 엔진이 어떤 컨텍스트를 거부하면 코어는 MtProtoKitEngine으로 폴백할 수 있어요.

고정된 macOS fork에는 이 Rust와 WebProxy 경로가 없어요. Rust MTProto 엔진 [3] [4] [24] [25]

장 지도

아키텍처와 동시성

  • 01장: 전체 아키텍처와 모듈 계층은 Bazel 모듈 경계, Account 런타임 루트, 플랫폼 프로세스 경계를 설명해요.
  • 02장: 리액티브와 동시성 모델은 Signal, Disposable, Promise와 큐 격리를 설명해요.

네트워크와 프로토콜

  • 03장: MTProto 전송 계층은 세션, 메시지 컨테이너, 확인 응답, 재전송, 연결 백오프를 설명해요.
  • 04장: 인증 키와 다중 데이터 센터는 영구 키, 임시 키, 인증 이전, 미디어 센터 선택을 설명해요.
  • 05장: TL 직렬화와 API 호출 계층은 생성된 TL 타입이 Network와 도메인 모델에 들어오는 방식을 설명해요.
  • 06장: 업데이트 동기화는 pts, qts, seq, 공백, getDifference를 설명해요.
  • 16장: Rust MTProto 엔진은 Rust 데이터 평면, C FFI, Swift 래퍼, 활성화와 폴백 조건, 동시성 소유권, 오류 매핑을 설명해요.

고정된 macOS fork의 프로토콜 버전은 더 이전 거예요.

  • TL layer(프로토콜 스키마 버전) 210과 Api0부터 Api39까지 40개의 생성 샤드(생성된 코드 조각)를 써요.
  • 업스트림 iOS 체크아웃은 layer 230과 더 많은 샤드를 써요.
  • fork의 전송 주 경로는 여전히 MtProtoKit이에요.

업스트림의 Rust나 WebProxy 전환을 데스크톱 fork의 기능으로 서술하면 안 돼요. [3] [26] [27]

메시지 전송과 오프라인 작업

  • 07장: 메시지 전송 파이프라인과 오프라인 작업 큐는 로컬 메시지, 업로드, RPC, 서버 확인이 어떻게 복구할 수 있는 큐를 이루는지 설명해요.

전송 파이프라인의 사전 업로드(녹화가 끝나기 전에 업로드를 시작하는 것)는 모든 녹음·녹화 경로에 공통된 특성이 아니에요. 경로마다 달라요.

  • 음성 녹음: 정지한 뒤에야 완전한 로컬 리소스를 기록해요.
  • 비밀 채팅이 아닌 곳의 조정되지 않은 원형 비디오: 같은 파일 식별자로 녹화하면서 업로드할 수 있어요.
  • 클립 편집, 다중 세그먼트 이어 붙이기, 음성 녹음: 이 실시간 업로드 컨텍스트를 재사용하지 않아요. [21]

저장과 검색

  • 08장: Postbox 스토리지 엔진은 단일 큐 트랜잭션, ValueBox, WAL(SQLite의 쓰기 선행 로그), 계정 데이터베이스 경계를 설명해요.
  • 09장: Postbox 뷰와 메시지 이력 모델은 메시지 네임스페이스, hole, 증분 뷰, 부분 기록을 설명해요.
  • 10장: 미디어 리소스, 다운로드/업로드, 캐시는 리소스 식별자, 범위 읽기, 업로드, 캐시 축출을 설명해요.
  • 19장: 검색과 로컬 인덱스은 FTS5 메시지 색인, peer와 메시지 검색, iOS와 macOS의 병합, 페이징, 중복 제거, 취소를 설명해요.

전문 검색 테이블은 Postbox의 FTS5(SQLite의 전문 검색 모듈) 가상 테이블이에요. peer 범위, 완전한 메시지 식별, 텍스트, 태그를 저장해요. 클라우드 검색에는 여전히 RPC가 필요해요. 비밀 채팅과 로컬에 이미 캐시된 콘텐츠는 이 색인으로 오프라인에서 검색할 수 있어요. [5]

기록 공백(hole, 아직 내려받지 못한 메시지 기록 구간)을 채우다 실패할 때의 경계는 이미 검증했어요.

  • 첫 RPC 오류는 maxRetries: 0 때문에 곧바로 결과 없이 완료로 바뀌어요.
  • 관리자는 대기 중인 항목을 정리하고 20초 동안 같은 hole을 억제하지만 hole 자체는 남겨요.
  • 코드는 두 번째 RPC 재시도를 예약하지 않아요.
  • 이후 hole 뷰가 바뀌거나, 서비스 주 인스턴스가 재구성되거나, 새 hole이 기록되어야 요청이 다시 트리거돼요. [18]

캐시 용량은 기록하는 시점의 하드 쿼터가 아니에요. TimeBasedCleanup은 설정이 MediaBox에 들어간 뒤 10초 지연해 스캔을 한 번 실행해요.

  1. 먼저 보존 기간에 따라 지워요.
  2. 이어서 파일 수정 시각이 오래된 것부터 스캔된 논리 크기만큼 지워요.
  3. 용량 값 아래로 내려갈 때까지 계속해요.

이 경로는 근사적인 최근 사용 축출이에요. 엄밀한 LRU(가장 오래 쓰지 않은 것부터 제거)나 LFU(가장 적게 쓴 것부터 제거)가 아니고, 활성 파일 컨텍스트를 명시적으로 보호하지도 않아요. [19]

보안과 프로세스 경계

  • 11장: 종단 간 암호화와 로컬 보안은 비밀 채팅의 세션 키, 메시지 암호화, PFS, 로컬 보호를 설명해요.
  • 12장: 푸시, 확장 프로세스와 다중 프로세스 협업은 알림 서비스, App Group, WAL, 제한된 백그라운드 시간을 설명해요.

고정된 iOS 주 경로는 로컬 SecretOutgoing 작업 카운트가 100에 이르면 PFS(주기적으로 키를 바꿔 과거 대화를 보호하는 방식) 키 교체를 시작해요. 이 카운트에는 여러 종류의 로컬 발신 작업이 들어 있어요. 사용자 텍스트만 세는 게 아니에요.

이 경로에는 일주일 타이머 트리거가 없어요. 저장소 안의 TDLib에 있는 일주일 조건은 그 iOS 주 경로로 내보내지지 않은 다른 구현에 속해요. [20]

파일 리소스는 대체로 리소스 레코드에 기록된 데이터 센터를 기준으로 미리 라우팅돼요. 현재 고정 커밋에는 FILE_MIGRATE_X에 대한 범용 최후 대비책(폴백)이 없어요. 다운로드와 업로드 모두 이 RPC 오류에서 다음을 하지 않아요.

  • 새 데이터 센터를 꺼내지 않아요.
  • 인증을 이전하지 않아요.
  • 새 데이터 센터에서 조각을 재전송하지 않아요.

CDN 리다이렉트는 다른 성공 응답 경로에 속해요. [17]

통화

  • 13장: 통화 시스템은 1:1 통화 제어 평면, 그룹 통화 상태, DH 협상, 플랫폼 연동을 설명해요.
  • 17장: tgcalls 통화 미디어 엔진은 인스턴스 등록, 3스레드 모델, 시그널링, ICE, 오디오 장치, 비디오 협상, 그룹 통화 미디어 경로를 설명해요.
  • 18장: 컨퍼런스 통화의 종단 간 암호화는 구성원 상태 체인, 키 교체, 이모지 검증, 미디어 프레임 암호화를 설명해요.
  • 29장: 통화 모듈의 WebAssembly 런타임은 iOS WAMR 제어 코어의 빌드, ABI, 샌드박스, 리소스 경계를 설명해요.

통화의 제어 평면과 미디어 평면은 분리되어 있어요.

  • CallSessionManager: 전화 상태, DH(키 협상), 시그널링을 보관해요.
  • tgcalls: 협상이 끝난 키, 후보, 장치 객체를 받아 네트워크 및 미디어 스레드에서 전송을 구동해요.
  • 컨퍼런스 통화의 종단 간 상태: 다시 TDLib 어댑터가 구성원, 블록, 검증, 프레임 암·복호화 능력을 가지고 있어요. [6] [7]

1:1 통화의 keyVisualHash는 이모지 4개로 검증해요. 클라이언트는 이렇게 계산해요.

  1. 32바이트 값을 연속된 8바이트 구간 네 개로 나눠요.
  2. 나눈 구간들에 대해 고정된 333항목 표에 대한 나머지를 취해요.

iOS와 macOS 고정 커밋은 같은 표 항목 순서, 분할 순서, 인덱스 공식을 써요. [22] [28]

엔드투엔드 경로

백그라운드에서 새 메시지를 받음

푸시는 메시지 데이터베이스의 권위 있는 사본이 아니에요. 알림 서비스는 짧은 시간 제한 안에서 페이로드를 검증하고, 필요하면 상태를 가져오거나 읽어요. 주 앱이 실행 기회를 얻으면 여전히 정상적인 업데이트 동기화로 연속 상태를 확인해요. 이렇게 해서 알림 표시, 백그라운드 처리, 포그라운드 채팅 뷰가 모두 같은 Postbox 사실 소스로 돌아와요.

  1. APNs가 NotificationService를 깨워요. 확장은 App Group에서 임시 계정 관리자를 열고, 계정 전용 알림 비밀로 암호화된 페이로드를 검증해요. 푸시, 확장 프로세스와 다중 프로세스 협업
  2. 확장은 peer 유형에 따라 채널 폴링 또는 차이 폴링을 한 번 수행해요. 기한 안에 알림에 필요한 메시지와 미디어만 가져와요. 시간이 초과되면 작업을 해제하고 이미 있는 내용으로 폴백해요. 푸시, 확장 프로세스와 다중 프로세스 협업
  3. 확장이 기록한 상태는 공유 Postbox로 들어가요. SQLite WAL은 통제된 읽기·쓰기 공존을 허용하지만, 쓰기 가능한 트랜잭션은 여전히 단일 기록자 제약을 받아요. Postbox 스토리지 엔진 푸시, 확장 프로세스와 다중 프로세스 협업
  4. 주 앱이 재개되면 AccountStateManager가 정상적인 업데이트 흐름을 이어 가요. 푸시, RPC 업데이트, 차이 결과를 같은 작업 큐에 넣고, 어떤 푸시가 완전한 연속 기록을 담고 있다고 믿지 않아요. 업데이트 동기화
  5. 관리자는 연속된 pts, qts, seq, date의 접두 구간만 커밋해요. 공백이 생기면 getDifference를 요청하고, 반복할 수 있는 트랜잭션으로 새 상태와 메시지를 Postbox에 기록해요. 업데이트 동기화
  6. ViewTracker는 커밋된 메시지 테이블과 인덱스로 증분 뷰를 계산해요. 채팅 화면이 이 뷰를 구독하기 때문에 영향받은 기록 창과 읽지 않음 정보만 갱신해요. Postbox 뷰와 메시지 이력 모델

사용자가 사진을 보냄

전송 경로는 사용자 의도를 먼저 커밋하고 업로드와 RPC는 나중에 해요. 덕분에 UI는 로컬 메시지를 즉시 보여 줄 수 있어요. 업로드 도중 프로세스가 종료되어도 전송 대기 레코드는 데이터베이스에 남아요. 다시 시작한 관리자는 커밋된 작업에서 이어 갈 수 있어요. UI 상태에서 사용자가 무엇을 보내려 했는지 다시 추론할 필요가 없어요.

  1. UI가 Engine으로 메시지를 큐에 넣어요. 코어는 메시지에 로컬 신원과 전송 난수를 만들고, Unsent 플래그가 붙은 메시지를 Postbox에 기록해요. 메시지 전송 파이프라인과 오프라인 작업 큐
  2. 같은 트랜잭션에서 전송 대기 작업을 기록해요. 그래서 UI는 메시지 기록 뷰에서 사진 자리 표시와 전송 상태를 즉시 보여 줄 수 있어요. 이 표시는 서버가 이미 메시지를 수락했다는 뜻이 아니에요. 메시지 전송 파이프라인과 오프라인 작업 큐 Postbox 뷰와 메시지 이력 모델
  3. PendingMessageManager가 작업을 관찰하고 콘텐츠 처리를 예약해요. 사진 리소스는 MediaBox가 추적하고, 업로더는 리소스 크기와 유형에 따라 조각 크기와 동시성을 골라요. 메시지 전송 파이프라인과 오프라인 작업 큐 미디어 리소스, 다운로드/업로드, 캐시
  4. 업로드가 끝나면 코어가 생성된 TL 함수로 미디어 RPC를 보내요. Network는 요청 스케줄링을 맡고, MTProto는 세션, 확인 응답, 재전송, 데이터 센터 전송을 맡아요. TL 직렬화와 API 호출 계층 MTProto 전송 계층
  5. 서버 결과가 UI 객체를 직접 고쳐 쓰지는 않아요. 업데이트 처리가 로컬 메시지 식별자를 서버 메시지 식별자로 매핑하고, 다른 업데이트와 함께 Postbox 트랜잭션에서 적용해요. 메시지 전송 파이프라인과 오프라인 작업 큐 업데이트 동기화
  6. 커밋 후의 기록 뷰가 로컬 레코드를 전송 완료된 메시지로 바꿔요. 네트워크가 실패해도 영속화된 작업이 재시도 의미를 유지해서, UI는 여전히 실패 또는 전송 대기 상태를 표시할 수 있어요. Postbox 뷰와 메시지 이력 모델 리액티브와 동시성 모델

장을 가로지르는 설계 원칙

로컬 의도가 원격 확인보다 먼저

Telegram은 복구할 수 있는 의도를 먼저 로컬에 기록한 뒤, 백그라운드 관리자가 네트워크 부수 효과를 실행하게 해요. 이 규칙을 따르는 곳은 이래요.

  • 일반 메시지의 Unsent 레코드와 peer 작업 로그
  • 비밀 채팅의 핸드셰이크, 암호화된 수신, 발신 서비스 동작: 독립된 작업 로그를 써요.
  • 로그인 흐름: 인증 코드, 비밀번호, 가입 단계를 미인증 계정 상태로 저장해요.
  • Stories의 게시 대기 항목과 지갑의 제출 대기 이체: 같은 선행 영속화 경계를 따라요.

이 선택은 크래시 복구를 UI 문제에서 저장 문제로 바꿔요. 메시지 전송 파이프라인과 오프라인 작업 큐 종단 간 암호화와 로컬 보안 다중 계정, 로그인, 구성 동기화 Stories의 데이터와 미디어 파이프라인 지갑 모듈: TON 엔진, 백업, 플랫폼 경계

큐 격리와 단일 커밋 지점

비동기라고 해서 아무 스레드나 공유 상태를 고칠 수 있는 건 아니에요. 각 계층이 이렇게 지켜요.

  • SwiftSignalKit: Disposable로 더 필요 없는 작업을 멈추고, Queue로 상태 객체에 대한 접근을 제한해요.
  • Postbox: 자신의 직렬 큐에서 트랜잭션을 실행해요.
  • AccountStateManager: 업데이트를 단일 처리 시퀀스에 편입해요.
  • 확장 프로세스: 주 앱 메모리를 공유하지 않고 WAL과 짧은 트랜잭션에 기대요.

이 경계들이 재진입, 부분 커밋, 프로세스 간 쓰기 경합을 줄여요. 리액티브와 동시성 모델 Postbox 스토리지 엔진 푸시, 확장 프로세스와 다중 프로세스 협업

증분 투영으로 UI를 구동

메시지 테이블은 UI가 직접 스캔하는 원시 파일이 아니에요. Postbox는 채팅 목록, 읽지 않음 수, 기록 창, hole 인덱스 같은 뷰를 유지해요. 트랜잭션이 커밋되면 영향받은 부분을 구독자에게 밀어 줘요. 기록이 불완전하면 hole 뷰가 공백(hole) 채우기 네트워크 요청을 구동해요. Widget은 공유 데이터베이스를 오래 점유하지 않고 원자적 스냅샷을 받아요. 이 설계는 큰 기록과 많은 소비자의 갱신 비용을 낮추고, 소비자 유형마다 시의성 경계도 분명히 해요. Postbox 뷰와 메시지 이력 모델 푸시, 확장 프로세스와 다중 프로세스 협업

Stories, 검색, 번역은 같은 원칙을 메시지 주 테이블 밖으로 넓혀요. Stories는 개별 항목, 목록, 읽음 상한, 구독 상태를 국소 투영으로 나눠요. 검색은 FTS 적중과 원격 결과를 신원에 따라 병합해요. 번역은 결과를 메시지 속성으로 저장하고, 표시할지는 현재 채팅의 번역 상태가 정해요. Stories의 데이터와 미디어 파이프라인 검색과 로컬 인덱스 메시지 번역

네임스페이스와 단계를 가진 신원

로컬 메시지 신원, 전송 난수, 서버 메시지 신원은 같은 값이 아니에요.

  • PeerId, MessageId, MessageIndex: 네임스페이스와 정렬 필드로 출처와 위치를 표현해요.
  • 공개 업데이트의 pts, 비밀 채팅의 qts, 바깥쪽 seq: 각자 서로 다른 연속성을 지켜요.
  • 통화: 서버의 안정적인 ID와 로컬 UUID를 또 분리해요.

신원과 단계를 명시적으로 구분하면 재생, 순서 뒤바뀜, 멀티 디바이스 도착에 판단할 수 있는 의미를 줄 수 있어요. Postbox 뷰와 메시지 이력 모델 메시지 전송 파이프라인과 오프라인 작업 큐 업데이트 동기화 통화 시스템

체크포인트와 재생이 필요한 최종 일관성

클라이언트는 푸시, 연결, 단발 RPC가 항상 완전하다고 가정하지 않아요. 계층마다 이렇게 대비해요.

  • 업데이트 동기화: getDifference로 공백을 메워요.
  • 전송 계층: 세션, 확인 응답, 재전송, 시간, salt를 유지해요.
  • 설정과 순서 있는 집합: hash로 변화 없는 기록을 피하고, 주기적 갱신으로 누락된 이벤트를 처리해요.
  • 미디어 리소스: 이미 받은 바이트 구간을 기록한 뒤 필요할 때 이어 받아요.

이들이 공유하는 원칙은 확인된 체크포인트를 저장하고 그 지점에서 복구하는 거예요. 마지막 콜백 결과만 남기는 게 아니에요. 업데이트 동기화 MTProto 전송 계층 다중 계정, 로그인, 구성 동기화 미디어 리소스, 다운로드/업로드, 캐시

보안, 리소스, 시스템 권한의 계층화

데이터 센터 인증 키, 알림 암호화 비밀, 비밀 채팅 세션 키, 통화 키, 지갑 복구 문구는 서로 다른 계층에 있어요. SQLCipher(암호화된 SQLite), 논리 키체인, Keychain 자격 증명, AppLock도 같은 종류의 보호가 아니에요. 책임은 이렇게 나뉘어요.

  • 미디어 캐시: 리소스 신원과 범위로 파일을 구성해요.
  • 알림 서비스: 기한과 취소로 백그라운드 리소스를 통제해요.
  • 통화: 제어 평면의 키 협상과 WebRTC 미디어 평면을 분리해요.
  • Mini App: 이벤트 브리지로 웹 페이지가 계정과 시스템 기능에 접근하는 것을 제한해요.

이런 책임을 하나의 만능 보안 모듈이나 캐시 모듈로 뭉치면 각자의 교체, 무효화, 감사 조건이 가려져요. 인증 키와 다중 데이터 센터 종단 간 암호화와 로컬 보안 미디어 리소스, 다운로드/업로드, 캐시 통화 시스템 Mini Apps와 봇 Web 뷰 지갑 모듈: TON 엔진, 백업, 플랫폼 경계

생성 계층과 도메인 계층의 격리

TL 스키마(Telegram 프로토콜의 타입 정의)의 바이너리 세부 사항은 TelegramApi에 격리되어 있어요. 생성된 함수와 생성자가 직렬화, 응답 역직렬화, layer 호환을 맡아요. Network와 NetworkEngine은 이 타입들을 통합 요청 채널에 넣어요. 더 위 계층에서는 API 사용자, 메시지, 그룹 객체를 Postbox와 Engine 모델로 변환해요. UI는 TL 바이트를 조립할 필요가 없고, 특정 RPC의 생성자 이름에 직접 기대서도 안 돼요. TL 직렬화와 API 호출 계층

이 경계는 오류 처리에도 똑같이 적용돼요. 전송 실패, RPC 오류, 마이그레이션, 재시도는 네트워크와 코어 계층에서 먼저 분류해요. 이후 도메인 작업이 로그를 남길지, 요청을 재구성할지, 완전한 차이 동기화를 요구할지 정해요. 예를 들면 이래요.

  • 메시지 전송: 업로드, 요청, 업데이트 적용이 각각 책임을 가져요.
  • 통화: 제어 평면이 키와 버전을 먼저 검증한 뒤 미디어 엔진에 넘겨요.

모듈 사이에 전달되는 건 마음대로 해석할 수 있는 바이트 스트림이 아니라, 소유자가 분명한 도메인 상태예요. 메시지 전송 파이프라인과 오프라인 작업 큐 통화 시스템

제한된 백그라운드 시간과 취소할 수 있는 작업

백그라운드 작업에는 명확한 리소스 예산이 있어요.

  • 알림 서비스: 연결, 폴링, 첨부 가져오기에 기한을 둬요. 기한이 되면 현재 처리기를 dispose하고, 이미 있는 내용이나 시스템 원본 내용을 전달해요.
  • 주 앱의 SharedWakeupManager: 작업이 있는 계정에 대해서만 백그라운드 시간과 필요한 연결을 확보해요. 또 이미 시작된 트랜잭션이 끝나기를 기다린 뒤 백그라운드 작업을 종료해요. 푸시, 확장 프로세스와 다중 프로세스 협업

이런 구성에서는 모든 비동기 연산을 취소할 수 있어야 해요.

  • Signal 구독과 Disposable: 상위 계층이 만료된 네트워크, 타이머, 미디어 작업을 멈출 수 있어요.
  • QueueLocalObject: 큐에 묶인 객체가 해제될 때 내부 리소스를 멈추게 해요.
  • 미디어 다운로드: 바이트 범위, 우선순위, 계속 조건을 분리해서 저장해요.
  • 통화 미디어와 메시지 캐시: 각자 생명 주기를 가지고, UI의 생존 시간을 빌려 쓰지 않아요. 리액티브와 동시성 모델 미디어 리소스, 다운로드/업로드, 캐시 통화 시스템

읽기 안내

  • 오프라인 우선 채팅 앱을 만들려면 먼저 메시지 전송 파이프라인과 오프라인 작업 큐, 업데이트 동기화, Postbox 스토리지 엔진을 읽어요. 이어서 Postbox 뷰와 메시지 이력 모델을 읽고, 커밋 증분이 UI에 도달하게 하는 방법을 파악해요.
  • 자체 네트워크 스택을 구현하려면 MTProto 전송 계층부터 시작해요. 그다음 인증 키와 다중 데이터 센터와 TL 직렬화와 API 호출 계층을 읽고, 연결, 인증, 요청 구성을 분리해서 설계해요. 새 데이터 평면과 옛 데이터 평면을 비교해야 할 때는 Rust MTProto 엔진을 읽어요.
  • 미디어 캐시와 백그라운드 전송을 설계하려면 미디어 리소스, 다운로드/업로드, 캐시를 읽어요. 아울러 Postbox 스토리지 엔진과 푸시, 확장 프로세스와 다중 프로세스 협업을 보고, 리소스 범위, 트랜잭션, 시스템 기한의 경계를 분명히 해요.
  • 로컬 검색이나 번역을 구현하려면 먼저 검색과 로컬 인덱스과 메시지 번역을 읽어요. 검색 장은 FTS, 원격 보완, 취소를 설명해요. 번역 장은 언어 감지, 결과 캐시, 권한 게이트를 설명해요.
  • 다중 계정과 제한된 시스템 진입점을 지원하려면 다중 계정, 로그인, 구성 동기화부터 읽어요. 그다음 푸시, 확장 프로세스와 다중 프로세스 협업과 전체 아키텍처와 모듈 계층을 읽고, 디렉터리, 계정, 프로세스 경계를 구분해요.
  • 실시간 통화나 종단 간 세션을 구현하려면 통화 시스템과 종단 간 암호화와 로컬 보안을 함께 읽어요. 통화 시스템 장은 제어 평면과 미디어 평면을 설명해요. 종단 간 암호화 장은 영속화된 키 상태, 순서, 로컬 보호를 설명해요. 회의 시나리오에서는 컨퍼런스 통화의 종단 간 암호화와 통화 모듈의 WebAssembly 런타임을 더 읽어요.
  • 제품 기능을 연동하려면 Stars, 선물, 결제, Mini Apps와 봇 Web 뷰, Stories의 데이터와 미디어 파이프라인부터 시작해요. 지갑 구현과 플랫폼 부재 경계는 지갑 모듈: TON 엔진, 백업, 플랫폼 경계를 봐요.
  • 빌드 산출물을 재현하거나 감사하려면 iOS 빌드 시스템: Bazel과 Make.py, 코드 생성: TL, 문자열, 직렬화, macOS 빌드, 패키징, 배포, 서드파티 의존성 목록과 드문 용도를 조합해서 읽어요.

장 지도

기초와 동시성

  • 01 전체 아키텍처와 모듈 계층: Bazel 의존성, 계정 경계, 프로세스 경계로 Telegram 클라이언트 아키텍처를 읽어요.
  • 02 반응형과 동시성 모델: Telegram은 Signal, 명시적 취소, 큐 격리로 비동기 상태를 구성해요.

네트워크와 프로토콜

  • 03 MTProto 전송 계층: MtProtoKit이 세션을 유지하고, TCP 트래픽을 라우팅하며, 장애를 처리하는 방식.
  • 04 인증 키와 다중 데이터 센터: Telegram 클라이언트가 인증 키를 만들고, 저장하고, 여러 데이터 센터에 걸쳐 쓰는 방식
  • 05 TL 직렬화와 API 호출 계층: Telegram 클라이언트에서 TL 함수부터 도메인 모델까지의 호출 경계를 추적해요
  • 16 Rust MTProto 엔진: Rust MTProto 데이터 평면이 C FFI를 거쳐 TelegramCore에 연결되는 방식과, MtProtoKit과 공존하는 경계.

동기화와 메시지

  • 06 업데이트 동기화: pts, qts, seq, getDifference: Telegram 클라이언트가 업데이트 공백을 감지하고 로컬 상태를 원자적으로 복구하는 방식
  • 07 메시지 전송 파이프라인과 오프라인 작업 큐: Telegram이 로컬 의도를 복구할 수 있는 메시지와 백그라운드 작업으로 영속화하는 방식

저장과 검색

  • 08 Postbox 저장 엔진: Telegram 클라이언트가 단일 큐 트랜잭션, 바이너리 키-값 테이블, SQLCipher로 로컬 상태 저장소를 구축하는 방식.
  • 09 Postbox 뷰와 메시지 기록 모델: Telegram이 듬성듬성한 메시지 기록을 색인하고 UI를 증분 방식으로 구동하는 방법을 설명해요
  • 10 미디어 리소스, 다운로드·업로드와 캐시: Telegram 클라이언트의 리소스 식별자, 분할 전송, 캐시 축출까지의 구현을 추적해요
  • 19 검색과 로컬 색인: Postbox 전문 색인, 메시지와 peer 검색 API, iOS와 macOS의 검색 결과 병합, 페이징, 취소 메커니즘을 설명해요.

보안과 시스템 통합

  • 11 종단 간 암호화와 로컬 보안: 비밀 채팅의 키 상태, 메시지 암호화, 로컬 데이터 보호 설계.
  • 12 푸시, 확장 프로세스, 멀티 프로세스 협업: Telegram iOS가 제한된 확장 프로세스에서 푸시와 공유 상태를 안전하게 처리하는 방식

통화

  • 13 통화 시스템: Telegram iOS와 macOS의 통화 상태 머신, 미디어 엔진, 회의 암호화 설계
