Telegram iOS는 푸시, 공유, Siri, 위젯, 화면 브로드캐스트를 독립된 프로세스에 둬요. 이 프로세스들은 App Group(같은 앱 그룹의 앱과 확장이 파일을 공유하는 iOS 컨테이너) 안의 암호화된 데이터 루트 디렉터리를 함께 쓰지만, 메모리나 앱 생명주기는 함께 쓰지 않아요. 핵심 설계는 두 가지예요.

  • 확장은 작업을 마치는 데 필요한 최소한의 런타임만 열어요.
  • 영속화 동시성은 Postbox의 SQLite WAL 트랜잭션에 맡겨요.

메인 앱은 SharedWakeupManager로 시스템이 주는 짧은 백그라운드 시간 창을 계정 작업과 연결 임대(lease)로 바꿔요. [1] [10]

프로세스 경계와 공유 루트 디렉터리

iOS 확장은 메인 앱이 실행 중이라고 가정할 수 없어요.

  • 알림 서비스: APNs 알림 하나로 콜드 스타트될 수 있어요.
  • Share extension: 다른 앱에서 곧바로 시작될 수 있어요.
  • WidgetKit: 시스템 자신의 타임라인 프로세스에서 데이터를 읽기도 해요.

그래서 Telegram은 이 진입점들을 AppDelegate나 싱글턴에 대한 원격 호출로 설계할 수 없어요.

이 진입점들은 모두 먼저 이렇게 App Group 컨테이너를 찾아요.

  1. 각자의 bundle id에서 기본 앱 id를 도출해요.
  2. group.에 기본 id를 붙여 App Group 컨테이너를 얻어요.

논리적 루트 디렉터리는 이 컨테이너 아래의 telegram-data예요. 알림 서비스는 루트 디렉터리에서 accounts-metadata를 열고, 같은 루트 디렉터리로 기기 전용 ValueBox 키와 salt를 도출해요. [1] 알림 콘텐츠 확장도 같은 컨테이너, 비밀번호 환경, 키 파라미터를 써요. [18]

아래 도표는 iOS 쪽의 프로세스, 공유 매체, 시스템 경계를 보여 줘요.

App Group이 해결하는 건 네임스페이스와 접근 권한뿐이에요. 쓰기 순서, 데이터베이스 잠금, 프로세스 깨우기는 해결하지 않아요. 그래서 Telegram은 공유 디렉터리를 제약 없는 폴더처럼 쓰지 않았어요.

  • 계정 메타데이터와 메시지 상태: 여전히 AccountManager, Postbox, 트랜잭션 API로 접근해요.
  • 짧은 프로세스 간 스냅샷: 독립된 파일로 쓰고, 원자적 교체를 써요.

이렇게 나눈 덕분에 위젯이 표시용으로 읽기만 해도 메인 데이터베이스에 부담이 커지지 않아요. [1] [11]

알림 서비스는 setupAccountManager를 호출할 때 isTemporary: true, isReadOnly: false, useCaches: false, removeDatabaseOnError: false를 넘겨요. [1] 이 파라미터에는 두 가지 의미가 있어요.

  • 임시 연결이라서 메인 앱의 캐시 전략을 유지하지 않아요.
  • 데이터베이스의 소유자가 아니라서, 열기에 실패해도 메인 앱이 아직 쥐고 있을 수 있는 데이터베이스를 삭제하지 않아요.

이 선택은 푸시 한 건을 처리하는 도중에 스스로 저장소를 복구하려 하기보다, 기존 채팅 데이터를 지키는 쪽을 우선해요.

이 방식은 잠금 해제 키를 평문으로 확장에 복사해 주는 게 아니에요. BuildConfig.deviceSpecificEncryptionParameters의 결과를 ValueBoxEncryptionParameters로 감싸서 독립적인 계정 상태 관리자에 넘겨요. [1] 계정, 로그인, 설정의 장기 모델은 다중 계정, 로그인, 구성 동기화에서 다뤄요. 여기서 요점은 수명이 짧은 프로세스들이 모두 같은 규칙으로 같은 암호화 저장소를 열 수 있다는 거예요.

알림 서비스의 제한된 동기화 경로

p를 포함한 암호화 푸시 경로에서 알림 서비스는 APS alert가 아니라 p를 메시지의 사실 출처로 삼아요. 처리 순서는 이래요.

  1. URL 안전 Base64 문자열을 바이너리 데이터로 복원해요.
  2. 앞 8바이트에서 키 식별자를 꺼내요.
  3. 계정 레코드의 backupData에서 notificationEncryptionKeyId와 일치하는 것을 찾아요.
  4. 일치하면 그 계정에 대해서만 standaloneStateManager를 만들어요.

[3]

여기서는 두 종류의 키를 정확히 구분해야 해요. 소스 코드는 MTProto 데이터 센터의 auth_key로 알림을 직접 복호화하지 않아요. 계정 Postbox keychain 항목 master-notification-secret에서 만든 MasterNotificationKey를 써요.

  • 이 비밀은 256바이트 난수예요.
  • 그 SHA-1의 마지막 8바이트가 식별자예요.
  • 클라이언트가 APS나 VoIP token을 등록할 때 같은 masterKey.data를 account.registerDevice의 secret으로 업로드해요. [2] [4]

따라서 MasterNotificationKey는 계정에 묶인 푸시 암호화 키예요. 전송 계층의 인증 키가 아니에요. 인증 키와 데이터 센터 선택은 인증 키와 다중 데이터 센터를 참고하세요.

복호화 함수는 이 순서로 검증하고 풀어요.

  1. 8바이트 key id를 비교해요.
  2. 푸시에서 16바이트 msgKey를 꺼내요.
  3. 알림 비밀의 서로 다른 구간에서 SHA-256 값 두 개를 계산해 AES key와 IV를 이어 붙여요.
  4. 복호화한 뒤에는 4바이트 길이를 검사하고 msgKey를 다시 계산해요.

검사가 하나라도 실패하면 nil을 돌려줘요. [2]

덕분에 확장은 메시지 내용을 열기 전에 잘못된 계정, 잘린 페이로드, 변조된 페이로드를 거부할 수 있어요. 코드는 이 알고리즘을 고른 이유를 설명하지 않아요. key id로 먼저 계정을 고르고 메시지 키를 다시 검증하는 방식은, 계정마다 복호화를 시도하는 비용도 피하는 것으로 보여요(추론).

아래 시퀀스 도표는 알림 서비스가 암호문을 최종 알림으로 바꾸는 주 경로를 보여 줘요.

핸들러는 먼저 이 순서로 설정을 읽어요.

  1. 공유된 알림 설정, 통화 설정, 로그 설정을 읽어요.
  2. 루트 디렉터리의 잠금 화면 상태 파일도 읽어요. 앱이 잠겨 있으면 미리 기록해 둔 잠금 화면 문자열을 로드하고, 실제 본문은 표시하지 않아요. [1]
  3. 알림 소리 목록과 Lottie 설정을 읽어요.
  4. 다중 계정일 때만 현재 계정의 peer 이름을 추가로 읽어요.

코드 주석은 이 읽기가 데이터베이스 쓰기 잠금을 두고 경쟁하기 때문에 읽기 횟수를 한 번으로 줄였다고 분명히 밝혀요. [3]

복호화된 JSON이 이후의 동작을 결정해요. 핸들러는 msg_id, story_id, from_id, chat_id로 메시지나 스토리의 위치를 구성할 수 있어요. 삭제, 읽음, 리액션, 수신 통화 같은 제어 페이로드도 파싱해요.

메시지와 스토리에 대해서는 핸들러가 상태 관리자를 만들고, 상태를 폴링하거나 대상 미디어를 가져와요. 업데이트의 pts, qts, seq와 차이 가져오기 방식은 업데이트 동기화에서 설명해요. 알림 확장은 그 상태 경로를 다시 쓰는, 시간 제한이 걸린 트리거일 뿐이에요. [3]

폴링은 채널과 그 밖의 peer 두 갈래로 나뉘어요.

  • 채널: standalonePollChannelOnce를 한 번 호출해요.
  • 그 밖의 peer: standalonePollDifference를 호출해요. 이 함수는 자체 규칙에 따라 상태가 따라잡힐 때까지 페이지를 나누고 다시 시작해요.

그래서 확장은 바깥에 timeout을 씌우고, 시간이 초과되면 폴링과 재연결을 dispose해요. [19] 이게 중요해요. 차이 동기화를 평범한 RPC 한 번으로 취급하면, 오프라인이거나 프록시가 죽었을 때 알림 전체 기한을 새 연결을 시도하는 데 다 써 버리게 돼요.

비교적 새로운 업스트림의 소스 주석은 iOS가 보통 didReceive 약 30초 뒤에 확장을 만료시킨다고 설명해요. 시간 예산은 이렇게 잡아요.

  • 네트워크 연결 마감 시한: 핸들러를 시작하고 25초로 둬요.
  • poll: 15초로 제한하고, 남은 시간이 있으면 최소 0.5초는 돌려줘요.

[38] 30초가 아니라 25초로 둔 건 이후의 Postbox 쿼리, 읽지 않은 수 계산, 콘텐츠 생성에 여유를 남기기 위해서예요. 이 이유는 같은 소스 주석이 직접 설명해요.

이 연결과 poll 예산은 업스트림에만 적용돼요. macOS fork에는 connectionDeadline이나 pollBudget이 없어요. fork에서 보이는 건 미디어와 알림 소리에 각각 10초 timeout이 있다는 점이에요. [37] 자세한 내용은 macOS fork 장별 검증(08–15장)을 참고하세요.

복호화된 payload가 모두 동기화를 거쳐야 하는 건 아니에요. payload에 aps와 url이 있으면 핸들러는 곧바로 NotificationContent를 만들어요.

  • URL, 고정된 서비스 peer, 계정 id를 저장해요.
  • aps에서 소리, title, subtitle, body를 꺼내요.
  • alert가 없으면 범용 새 메시지 텍스트를 써요.

[32] 이 경로는 비용이 적게 드는 폴백이에요. 대상 메시지를 가져오지 못했거나 payload가 원래 이동 정보만 담고 있을 때도 조작할 수 있는 알림을 내놓을 수 있어요. 이 분기가 있어서, APS에 표시할 텍스트가 없다고 뭉뚱그려 말할 수 없어요.

이 버전의 알림 서비스 코드에는 고정된 메모리 상한이 선언되어 있지 않아요. 미디어 다운로드 경로는 받은 조각을 Data로 모은 뒤 첨부 데이터를 만들어요. [19] 구현은 실제로 세 겹으로 부하를 덜어요.

  • 첫째, 이미지 표현, 비디오 미리보기, 음성, 스티커 리소스만 골라요.
  • 둘째, 가져오기 단계마다 최대 10초만 기다려요.
  • 셋째, 시스템 만료 콜백에서 핸들러 전체를 dispose해요. [6] [7]

이 세 장치는 작업 지속 시간과 일반적인 첨부 규모를 제어해요. 하지만 메모리 할당량은 아니에요. 제품 엔지니어링에서는 시스템이 정하는 메모리 제한을 런타임 제약으로 보고, 큰 이미지, Lottie 렌더링, 동시 알림에 대해 실기기에서 스트레스 테스트를 해야 해요.

데이터베이스 동시성과 프로세스 간 가시성

공유 루트 디렉터리의 정확성을 받쳐 주는 건 ManagedFile이 아니라 SQLite예요. ManagedFile은 저장소에서 미디어 조각, 로그, 일반 파일 I/O에 쓰여요. 이 장의 확장들이 Postbox 쓰기를 조정하는 뮤텍스가 아니에요. Postbox의 SqliteValueBox는 journal mode를 WAL(변경을 로그에 먼저 적는 SQLite 방식)로 설정하고 5초 SQLite busy timeout을 설정해요. [10] WAL은 읽는 쪽과 커밋된 쓰는 쪽이 더 쉽게 함께 있게 해 줘요. 하지만 즉시 쓰기 트랜잭션은 여전히 하나만 허용해요.

단일 독립 계정 트랜잭션은 이 순서로 진행돼요.

  1. 계정 레코드 id로 계정 디렉터리를 계산해요.
  2. openPostbox로 그 디렉터리 안의 postbox를 여는데, isMainProcess: false와 isTemporary: true를 명시적으로 줘요.
  3. 성공한 뒤에야 전달받은 transaction 클로저를 실행해요.

열기에 실패하면 AccountTransactionError.couldNotOpen으로 매핑해요. [28] 이 API는 프로세스의 역할을 연결을 만드는 지점에 기록해요. 호출한 쪽이 데이터베이스를 삭제해도 되는지, 메인 프로세스 캐시를 쥘 수 있는지 스스로 짐작할 필요가 없어요.

  • 위젯: 원자적 스냅샷 쓰기와 WidgetCenter reload로 새 콘텐츠를 얻어요.

IpcPipe는 Darwin notification이 아니라 파일 이벤트 신호예요. 믿을 수 있는 작업 로그를 담지도 않아요. 소스 파일에서 옛 값을 읽던 코드는 이미 주석 처리되어 있어요. 현재 소비하는 쪽은 “다시 읽어야 함”이라는 힌트로 Int64.max만 내보내요. 이 장에서 나열한 확장 호출 체인에 대해, 저장소를 검색해도 이 프리미티브의 호출자는 나타나지 않았어요. 따라서 알림, 위젯, 공유가 이걸 믿고 새로 고친다고 주장할 수 없어요.

메인 앱에는 논리적인 주 클라이언트 개념도 있어요. Postbox.becomeMasterClient는 트랜잭션 안에서 metadataTable.masterClientId와 현재 sessionClientId를 비교하고, 다를 때만 새 id를 커밋해요. isMasterClient는 이 값을 불리언 Signal로 매핑해요. [36]

  • shouldKeepOnlinePresence
  • shouldKeepBackgroundDownloadConnections

포그라운드의 주 계정이나 작업이 있는 계정이 master가 될 수 있어요. 백그라운드 오디오, 위치, 전송 대기 메시지, 전송 대기 스토리가 있을 때만 worker 연결을 명시적으로 유지해요. [16] MTProto 연결 계층 자체는 MTProto 전송 계층에서, TL request 구성은 TL 직렬화와 API 호출 계층에서 다뤄요.

처리할 작업이 없을 때 관리자는 모든 걸 곧바로 거칠게 끝내지 않아요. postbox.setCanBeginTransactions를 false로 만들고, 계정마다 실행 중인 트랜잭션이 끝난 뒤의 콜백을 전달할 수 있어요. 모든 계정이 확인한 뒤에야 연장된 백그라운드 작업을 끝내요. [16] 이건 전형적인 경쟁 상태를 다뤄요. iOS 백그라운드 작업을 먼저 끝내고 이미 시작된 로컬 쓰기를 기다리면, 시스템이 transaction을 커밋하기 전에 프로세스를 일시 중지할 수 있어요. 새 트랜잭션을 계속 허용하면 백그라운드 작업이 모두 비워졌다는 걸 증명할 수 없어요.

작업이 있으면 관리자는 setCanBeginTransactions를 true로 설정해요. 나머지 설정은 이래요.

  • .always 서비스 주도권: 포그라운드 primary 계정, 작업이 있는 계정, 또는 명시적 연장 창 안의 primary 계정에만 설정해요.
  • 온라인 presence: 포그라운드 primary 계정에만 남겨요.
  • 백그라운드 다운로드 연결: backgroundDownloads 표시로만 켜요.

[16] 이렇게 세밀한 스위치가 있다는 건, 백그라운드의 “깨어 있음 유지”가 모든 계정, 모든 네트워크를 활성 상태로 유지하는 게 아니라는 걸 보여 줘요. 한정된 시스템 시간을 분명한 작업 사유가 있는 계정에 나눠 주는 거예요.

이 집중 지점은 기능마다 제각기 연결을 연장하는 일도 막아요. 네트워크 계층의 주석은 web proxy carrier가 shouldKeepConnection에 따라 시작·중지되고, 깨우기 관리자가 다루는 포그라운드, 오디오, 백그라운드 확장, 처리 작업, grace timer를 이어받는다고 분명히 밝혀요. [27] 통합된 중재는 미디어 다운로드, 전송 큐, 통화가 동시에 백그라운드 시간을 신청할 때의 경쟁 상태를 줄여 줘요. 하지만 백그라운드 동작이 비교적 큰 정책 객체 하나에 기대게 되기도 해요. 새 작업 유형을 수정할 때는 이 객체의 카운트, 만료, 계정 정책을 함께 검토해야 해요.

설계 트레이드오프

Telegram은 같은 프로세스가 아니라 같은 데이터 루트를 택했어요. 이 결정 덕분에 계정, 네트워크, 작업 큐를 다시 쓸 수 있어요. 대신 각 확장이 짧은 수명, 콜드 스타트, 잠금 경쟁을 올바르게 처리해야 해요. 알림 서비스는 계정 전용 알림 비밀로 복호화한 뒤 필요에 따라 데이터를 동기화해요. 평문이 드러나는 면은 줄어들지만, 어떤 실패에도 원래 알림으로 폴백할 준비를 해야 해요. [2] [7]

모든 확장을 위해 명시적 파일 잠금과 프로세스 메시지 버스를 만드는 대신 SQLite WAL과 데이터베이스 트랜잭션을 택했어요. 이 방안은 일관성을 잘 다져진 저장 계층에 맡기고, 읽기 전용 위젯과 Siri 쿼리도 동시에 진행할 수 있게 해요. 대가는 쓰기 경쟁이 시스템이 확장에 허락한 한정된 시간을 여전히 써 버릴 수 있다는 점이에요. [10]

데이터를 공유하는 형태도 두 가지를 택했어요. Postbox는 기준이 되는 가변 상태를 보관해요. 원자적 JSON 스냅샷은 위젯 같은 표시 소비자를 위한 거예요. 전용 IPC 파일은 브로드캐스트 같은 실시간 소비자를 위한 거예요. 이 셋을 하나의 인터페이스로 합치면 안 돼요. 지연 시간, 실패 모델, 데이터 소유권이 서로 다르기 때문이에요. [11] [12] [15]

백그라운드 실행도 SharedWakeupManager에 모았어요. 장점은 연결과 계정 역할이 작업에 따라 한 곳으로 통일된다는 점이에요. 대가는 이곳이 모든 백그라운드 기능의 정책이 만나는 결합점이 된다는 점이에요. 확장이나 백그라운드 작업을 새로 추가할 때는 트랜잭션 권한, worker 연결, 시스템 시간 창이 필요한지를 먼저 정의해야 해요. [16]
