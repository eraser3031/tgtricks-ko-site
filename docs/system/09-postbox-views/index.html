정수 하나로 담을 수 없는 신원

메시지 시스템이 가장 먼저 풀어야 하는 문제는 신원 충돌과 정렬 경계예요. 서버 메시지 번호는 일부 대화 도메인 안에서만 의미가 있어요. 로컬의 전송 대기 메시지, 예약 메시지, 비밀 채팅은 누가 만들고 언제까지 살아 있는지도 또 달라요. 그래서 Postbox는 메시지 키를 단일 Int32로 정의하지 않았어요. 대신 세 타입으로 신원을 나눠 표현해요.

  • PeerId(대화 상대의 식별자): Int64 하나를 감싸요.
  • MessageId: peerId, namespace, id 세 부분으로 이루어져요.
  • MessageIndex: 그 신원 위에 timestamp를 덧붙여요. [1]

MessageId.Namespace는 논리적 번호 공간이지, 표시 계층의 분류가 아니에요. 현재 업스트림이 정의하는 번호 공간은 이래요.

  • 0: 클라우드 메시지
  • 1: 로컬 메시지
  • 2: 비밀 채팅 수신 메시지
  • 3, 4: 예약된 클라우드 및 로컬 메시지
  • 5, 6: Quick Reply 클라우드 및 로컬 메시지 [2]

macOS fork 차이. 고정 fork도 Cloud 5와 Local 6을 정의하지만 6까지만 정의해요. 업스트림에는 ephemeral과 welcome message 공간이 더 있어요. [30]

같은 peer 안에서 id가 같아도 namespace가 다르면 서로 다른 메시지예요. 이 선택 덕분에 클라이언트는 먼저 로컬 자리 표시 메시지를 넣고, 나중에 서버가 확인한 클라우드 메시지를 저장하면서도 원래 레코드를 덮어쓰지 않아요. (추론) 또 “서버에서 이력을 보충할 수 있는가”를 알맞은 공간으로 한정해서, 로컬 큐를 원격 이력으로 잘못 보는 일을 피해요. 네임스페이스의 fork 검증은 macOS fork 장별 검증(08–15장)을 참고하세요.

이력 기록과 파생 색인

메시지 이력은 다음을 한꺼번에 지원해야 해요.

  • 정확한 신원으로 읽기
  • 시간순 페이지 넘김
  • 태그 필터링
  • 주제별 읽기
  • 텍스트 검색

테이블 하나로는 이 질의를 모두 국소 스캔으로 처리할 수 없어요. 그래서 Postbox는 정규 메시지 레코드와 여러 파생 색인을 따로 유지해요.

  • MessageHistoryTable: 직렬화된 메시지 레코드를 저장해요. 키는 peer, namespace, 메시지 번호로 위치를 정해요.
  • MessageHistoryIndexTable: 신원에서 시간 색인으로 가는 매핑을 저장해요. 그리고 더 이른 항목, 기존 namespace, 가장 가까운 색인 같은 범위 접근을 제공해요. [3] [4]

여기서 핵심은 SQLite의 구체적인 레이아웃이 아니라 커밋 프로토콜(트랜잭션을 확정할 때 파생 데이터를 함께 갱신하는 규칙)이에요. 이력 테이블은 삽입, 제거, 갱신, 시간 갱신을 MessageHistoryOperation으로 모아요. 이어서 processIndexOperations가 다음을 동기적으로 갱신해요.

  • 주 레코드
  • 태그
  • 미디어
  • 미전송 큐
  • 읽기 상태
  • 기타 색인 [3]

그래서 한 트랜잭션은 뷰에 메시지 삽입이나 색인 삭제 같은 의미 있는 연산을 알려 줄 수 있어요. 모든 관찰자가 데이터베이스 스냅샷을 비교하게 만들 필요가 없어요. 아래쪽의 ValueBox, SQLite, 암호화 세부 사항은 Postbox 스토리지 엔진에서 다뤄요.

MessageHistoryIndexTable은 각 peer에 현재 있는 namespace 집합도 캐시해요. 처음 호출될 때 그 peer의 색인 키를 스캔하고, 이후에는 캐시를 돌려줘요. 메모리 캐시를 비울 때만 다시 찾아요. [4] 이 캐시는 적은 메모리로 이력을 렌더링하는 동안의 범위 스캔을 줄이는 방식이에요. (추론)

쓰기 경로는 namespace가 생기거나 사라질 때 캐시를 올바르게 무효화해야 해요. 그렇지 않으면 필터 윈도우가 한 공간을 놓쳐요. 소스는 메모리 캐시를 비울 때 이 캐시를 명시적으로 버려요. [4]

포럼과 답글 스레드는 대화 수준 타임라인에만 기댈 수 없어요. MessageThreadIndexTable은 각 peer와 thread의 표시 가능한 정보를 저장하고, MessageHistoryThreadsTable은 스레드 안의 메시지 색인을 유지해요. 스레드 색인 뷰는 다음을 읽어요.

  • 고정 순번
  • 최상단 메시지
  • 임베디드 인터페이스 상태
  • 태그 요약

그다음 “고정이 앞, 그다음은 최신 색인의 역순”으로 주제를 배열해요. [5] [27]

덕분에 채널 포럼 목록과 한 주제의 이력이 각자 페이지를 나눌 수 있어요. 어떤 주제의 읽지 않음과 태그 요약을 구하려고 채널의 모든 메시지를 스캔할 필요도 없어요. [5]

태그 색인은 “같은 듬성듬성한 이력 안에서 사진, 링크, 읽지 않은 멘션만 나열하기” 같은 문제를 풀어요. MessageHistoryTagsTable의 키는 다음을 포함해요.

  • tag
  • thread
  • peer
  • namespace
  • MessageIndex

태그를 넣거나 뺄 때 테이블은 요약 집합에 속한 MessageHistoryTagsSummaryTable도 함께 갱신해요. 요약은 일치하는 개수와 최대 메시지 번호를 저장해서, 채팅 목록이나 필터 진입점에서 개수를 빠르게 보여 주는 데 써요. [6]

이 경로는 쓰기 증폭(한 번의 변경에 쓰기가 여러 번 필요한 것)이 있어요. 하지만 미디어 태그 페이지, 멘션 페이지, 채팅 목록을 읽을 때 메시지를 다시 돌 필요가 없어서, 읽기가 많고 쓰기가 적은 클라이언트 상호작용에 알맞아요. (추론)

hole로 내려받지 않은 이력을 표현하기

모바일 기기가 한 대화의 이력을 전부 갖고 있는 경우는 드물어요. 내려받지 않은 구간을 그냥 비어 있다고 보면, 화면은 “오래된 메시지가 없다”와 “아직 오래된 메시지를 받지 못했다”를 구분할 수 없어요. 그래서 Postbox는 빠진 구간을 hole(내려받지 않아 비어 있는 이력 구간)로 분명하게 기록하고, 이력 뷰가 hole에 대한 상대 방향을 갖게 해요.

hole 하나는 다음으로 정해져요.

  • peer
  • 선택적 thread
  • namespace
  • 공간
  • 닫힌 구간

공간은 전체 이력을 뜻할 수도 있고, 일반 태그나 사용자 정의 태그 필터를 뜻할 수도 있어요. [8] [9]

MessageHistoryHoleIndexTable은 이렇게 동작해요.

  • 구간의 상단 메시지 번호를 키로, 하단 메시지 번호를 값으로 써요.
  • hole을 추가하기 전에 범위를 1부터 Int32.max - 1까지로 자르고, 겹치는 범위를 확인해서 병합해요.
  • 이미 채워진 범위를 삭제할 때는 완전히 덮이는 hole을 지워요. 겹치는 hole이면 채워진 정수 구간을 빼고 남은 구간을 다시 써요. [8]

이렇게 끝점만 저장하면 이어진 빈 구간 하나가 항목 하나로 줄어요. 대가는 hole이 일부만 채워질 때 쪼개서 다시 써야 한다는 점이에요. 소스는 실제로 IndexSet으로 남은 범위를 다시 만들어요. [8]

이 도표는 메시지 hole이 저장소, 뷰, 네트워크 보충으로 이어지는 순환을 보여 줘요.

MutableMessageHistoryHolesView는 처음에 모든 hole을 읽고, 트랜잭션의 currentPeerHoleOperations에서 삽입과 제거를 조금씩 처리해요. 이 뷰가 내놓는 공개 MessageHistoryHolesView는 entries를 갖고, 각 항목은 peer hole과 상대 방향, 공간, 요청 수량을 줘요. [9] ViewTracker는 추적 중인 이력 뷰에 맞춰 추적할 hole을 갱신해요. 그래서 백그라운드에서 모든 peer의 모든 hole을 무차별로 가져올 필요가 없어요. [21]

ViewTracker는 Bag으로 가변 이력 뷰와 그 ValuePipe를 보관해요. 이력 뷰를 등록하거나 제거한 뒤에는 추적하는 hole을 갱신해요. 채팅 목록 뷰도 같은 패턴으로 추적하는 채팅 목록 hole을 갱신해요. [21] 이 경로는 구독 관리와 테이블 쓰기를 나눠요. 그래서 UI는 테이블을 직접 갖지도, SQL 변화를 직접 관찰하지도 않아요.

이 도표는 로컬 또는 네트워크 트랜잭션이 어떻게 UI 업데이트가 되는지 보여 줘요.

combinedView(keys:)는 화면이 서로 일관성을 지켜야 하는 여러 결과를 합쳐서 구독하는 방식이에요. Postbox는 각 키마다 mutable view를 만들어 CombinedMutableView로 감싸요. 먼저 초깃값을 전달하고, 이후 업데이트를 전달해요. 등록을 해제할 때는 Postbox 큐에서 관찰자를 제거해요. [22]

UI 입장에서는 채팅 행, 읽지 않은 개수, 환경설정이 서로 조율할 수 없는 여러 독립 콜백으로 쪼개지는 일을 피할 수 있어요. 서로 다른 Postbox 사이의 원자성은 보장하지 않고, UI 메인 스레드 스케줄링을 대신하지도 않아요. 리액티브 큐와 Signal의 동시성 제약은 리액티브와 동시성 모델을 참고하세요.

뷰와 hole이 함께 일할 때 trackHoles는 단순한 렌더링 옵션이 아니에요. 이력 뷰를 등록하면 tracker가 추적하는 hole을 갱신하고, hole 관리자는 그 hole들에 대해서만 요청을 시작해요. [21] 그래서 사용자가 이력 중간으로 스크롤하거나, 검색 결과로 점프하거나, 포럼 주제를 열 때도 모두 같은 “구독 윈도우가 hole 수요를 낳는” 메커니즘으로 보충이 시작돼요. 컨트롤러마다 따로 페이지 분할을 구현하지 않아요. (추론) 메시지를 보낸 뒤의 로컬 상태, 재시도, 오프라인 작업 큐는 메시지 전송 파이프라인과 오프라인 작업 큐를 참고하세요.

이력 윈도우의 경계 규칙

앵커는 윈도우가 어디서 시작하는지만 정해요. 메시지가 반드시 있다는 것까지 정하지는 않아요. HistoryViewAnchor는 상한, 하한, 구체적인 MessageIndex의 세 가지 값을 가져요. 그리고 anchor를 지정한 peer와 namespace로 고쳐 쓴 뒤 크기를 비교하는 보조 메서드를 제공해요. [20] 화면은 상황에 따라 값을 골라 써요.

  • 최신 메시지를 열 때: 상한
  • 타임라인의 시작을 요구할 때: 하한
  • 인용이나 검색 결과로 점프할 때: 구체적인 색인

이 경우들을 하나의 타입으로 모아서, 메시지 이력, 태그 이력, thread 이력이 윈도우 알고리즘을 함께 쓰게 해요. (추론)

윈도우는 여러 namespace도 감당해야 해요. 일반 클라우드 이력, 로컬 전송 대기 기록, 예약 메시지는 호출한 쪽이 넘긴 namespaces 집합에 따라 하나의 뷰에 함께 있을 수 있어요. [2] [20]

MessageHistoryView는 hole 연산을 검사할 때 현재 tag를 .everywhere, .tag, .customTag의 hole 공간으로 바꿔요. 그리고 peer, thread, 공간이 동시에 일치하길 요구해요. [20] 그래서 일반 이력을 내려받아도 미디어 필터 페이지의 hole이 잘못 지워지지 않아요. 어떤 포럼 주제의 hole이 채널 루트 타임라인에 표시되지도 않아요.

메시지 그룹은 윈도우 모델에서 특수한 경우예요. 뷰를 만들 때 appendMessagesFromTheSameGroup을 요구할 수 있어요. 재생 중 삽입 연산이 태그에 맞지 않는 그룹 메시지를 만나면, 그룹 안에 일치하는 메시지가 있는지 확인하고 최대 20개로 그 메시지 그룹을 가져와요. [20]

미디어 앨범 같은 논리 그룹이 필터 페이지에서 태그 필터 때문에 따로 떨어진 항목으로 쪼개지지 않고, 이어진 맥락으로 보일 수 있다는 뜻이에요. 20은 이 그룹 재조회의 소스상 상한이고 프로토콜의 제한이 아니에요. [20]

상대 hole 방향도 윈도우 경계에 영향을 줘요. hole 관리자는 MessageHistoryHolesView 항목을 받으면 그 방향과 요청 수량을 fetchMessageHistoryHole에 넘겨요. [10] Holes.swift는 범위 요청에서 방향에 따라 요청의 offsetId, addOffset, minId, maxId를 고르고, 응답이 오면 실제 메시지 번호로 filledRange를 계산해요. [11] 따라서 “위로 스크롤해 오래된 메시지 로드”와 “점프 지점 주변으로 한 페이지 보충”은 결국 같은 hole 채움 트랜잭션을 써요. 네트워크 페이지의 경계 매개변수만 달라요.

채팅 목록의 2차 색인

채팅 목록의 메시지 항목이 저장하는 건 정렬 키만이 아니에요. ChatListTable은 범위 질의에서 키로부터 group, 고정 순번, MessageIndex, 항목 유형을 풀어 내요. 메시지 항목이면 값에서 메시지 색인을 복원하고, peer 테이블, 읽기 상태 테이블, 이력 테이블과 합쳐서 목록 항목을 만들어요. [13] 그래서 마지막 메시지의 변경, 고정 상태의 변경, peer 표시 정보의 변경이 모두 채팅 목록 재생을 일으킬 수 있어요. 목록 항목은 여러 테이블에 걸친 투영이에요. 단일 메시지 색인을 그대로 보여 주는 게 아니에요. (추론)

allHoles(groupId:)는 전역 싱글턴 hole을 유지하지 않고 group의 상한과 하한으로 스캔해요. [13] 그래서 보관함과 루트 목록이 서로 다른 페이지 공백을 가질 수 있어요.

AllChatListHolesView는 latestHole만 공개해요. 내부에는 완전한 Set을 유지하고, 삽입이나 제거 뒤에 최대 원소를 꺼내요. [13] 백그라운드 동기화는 보통 가장 앞쪽에서 가져올 위치만 알면 돼요. 그 요구에 맞추면서도, 다른 hole 뷰가 쓸 수 있도록 더 완전한 집합을 보존해요. (추론)

고정 정렬에는 번호 방향에 관한 세부 사항도 있어요. ChatListIndex의 비교 구현에서는 수치가 더 큰 pinningIndex가 더 앞이에요. [12] pinningIndex를 눈에 보이는 순번으로 그대로 표시하거나 오름차순으로 정렬하면 안 돼요.

고정 값이 없을 때 정렬은 엄밀히 MessageIndex에 맡겨요. 그래서 새 메시지를 받으면 대화가 자연스럽게 위로 올라와요. 고정 값이 있으면 일반 새 메시지가 맨 위 자리를 빼앗지 못해요. [12]

group과 filter의 경계도 다시 쓸 만해요. PeerChatListInclusion은 어떤 group에 있는지 여부, 선택적 pinning index, 최소 타임스탬프만 표현해요. [14] “개인 채팅만”, “읽은 것 제외”, “연락처만” 같은 사용자 필터 규칙을 저장 레코드에 밀어 넣지 않았어요. 소스의 채팅 목록 predicate는 다음을 받을 수 있어요.

  • peer
  • group
  • 총 읽지 않음에서 제외할지 여부
  • 읽지 않음 여부
  • 연락처 여부
  • 태그 요약 계산 결과 [25]

바뀌지 않는 소속 사실은 테이블에 남기고, 자주 바뀌는 제품 규칙은 질의 계층에 두는 방식이에요. 대가는 필터 뷰가 읽을 때 술어를 평가해야 한다는 점이에요. (추론)

읽기 경계에서 배지까지

PeerReadState의 두 가지 표현은 서로 다른 정렬 방식을 아울러요. 서버 메시지 번호를 직접 비교할 수 있는 이력에서는 idBased가 최대 수신 및 발신 읽음 id로 판정해요. 복합 시간 색인으로 판정해야 할 때는 indexBased가 MessageIndex를 비교해요. [15]

두 경우 모두 count와 markedUnread를 저장해요. 그래서 “읽지 않은 메시지가 몇 개인가”와 “사용자가 직접 채팅을 읽지 않음으로 표시했는가”는 같은 불리언이 아니에요. UI가 count만으로 상태를 표시하면 markedUnread가 담은 제품 의미를 잃어요. (추론)

병합 상태를 기계적으로 하나의 최대 id로 합칠 수는 없어요. CombinedPeerReadState는 namespace에서 PeerReadState로 가는 배열을 유지해요. count를 계산할 때는 각 상태를 누적하고, isUnread와 markedUnread는 어느 하나라도 참인지 돌면서 확인해요. [15] 그래서 클라우드와 로컬 공간이 각자 읽기 경계를 가질 수 있어요. 대가는 호출한 쪽이 메시지 하나의 읽음 여부를 조회할 때 올바른 namespace의 상태를 골라야 하고, 총수만 봐서는 안 된다는 점이에요. (추론)

총 읽지 않음 요약은 “메시지 수”와 “대화 수”를 한층 더 구분해요. ChatListTotalUnreadCounters는 메시지 수와 대화 수, 이 두 Int32를 저장해요. 그룹 수준 상태는 tag를 키로 absolute와 filtered 두 사전을 가져요. [17]

커밋할 때의 변화 함수는 다음을 해요.

  • 어떤 peer의 읽지 않은 수가 0에서 0이 아닌 값으로, 또는 그 반대로 바뀌면 chat count를 조정해요.
  • 새 count와 옛 count의 차이로 message count를 갱신해요.
  • 두 수를 0 이상으로 잘라요. [17]

덕분에 앱은 알림 설정이나 카운트 선호도에 따라 읽지 않은 대화 수와 읽지 않은 메시지 수 중 무엇을 보여 줄지 고를 수 있어요. 이력 테이블을 바꿀 필요는 없어요.

UnreadMessageCountsView의 증분 조건도 갱신 범위를 제한해요.

  • total: 환경설정 항목과 루트 group의 갱신된 총 상태를 검사해요.
  • total in group: 지정한 group만 검사해요.
  • peer: 먼저 peerCombinedReadStateMayHaveChanged로 판단한 뒤 그 peer의 상태를 다시 계산해요. [18]

따라서 메시지 하나의 읽기 상태가 바뀌어도 모든 읽지 않음 구독자를 깨울 필요가 없어요. 이 효율을 얻으려면 커밋 경로가 currentUpdatedTotalUnreadStates 같은 트랜잭션 집합을 정확히 채워야 해요. (추론)

스레드 hole과 다차원 페이지 분할

일반 메시지 hole의 키에는 thread id가 없어요. 스레드 이력은 따로 MessageHistoryThreadHoleIndexTable을 쓰고, 그 범위 키는 peer, thread, namespace, hole 공간을 인코딩해요. [28]

어떤 thread의 hole 색인에 처음 접근하면 테이블이 seedConfiguration.messageThreadHoles를 조회해요. 구성이 그 peer namespace와 thread에 대해 메시지 공간을 돌려주면, 테이블은 각 공간에 1부터 Int32.max - 1까지의 초기 hole을 삽입해요. [28] 그래서 포럼 주제 하나가 “알 수 없는 전체 이력”에서 시작해 필요에 따라 가져올 수 있어요. 채널 루트 이력의 hole 집합을 오염시키지도 않아요.

스레드 hole의 초기 전체 범위는 서버에 그만큼 많은 메시지가 있다는 주장이 아니에요. 어떤 id가 이미 있는지 아직 모르는 커버리지 범위를 나타내요. 이후 네트워크 응답이 실제로 채워진 부분을 지우거나 쪼개요. [8] [28] 이렇게 낙관적으로 미지를 표현하는 방식은 듬성듬성한 캐시에 알맞아요. 하지만 처음 스레드를 열 때 논리 범위가 아주 커져요. 클라이언트는 이 범위를 도는 게 아니라 윈도우, 요청 수량, 반환 범위 제한에 기대어 실제 작업량을 제한해요. (추론) 스레드 색인 뷰는 isLoading도 공개해서, 주제 디렉터리의 hole 상태를 UI에 보이게 만들어요. [5]

포럼 주제 목록에도 메시지 id hole과는 다른 표현이 있어요. ForumTopicListHolesEntry는 peer와 선택적 StoredPeerThreadCombinedState.Index를 항목으로 삼아요. MutableForumTopicListHolesView는 집합이 바뀔 때만 업데이트를 내보내요. [29] 주제 디렉터리는 주제 최상단 색인으로 정렬되므로, 여기서는 메시지 번호보다 색인 위치가 더 알맞아요. hole 유형을 페이지로 나뉘는 집합에 맞추는 건 다른 곳에도 옮겨 쓸 수 있는 설계 원칙이에요. 모든 누락을 이어진 정수 범위로 억지로 끼워 넣지 말라는 거예요. (추론)

재생의 상태 머신 경계

MutableMessageHistoryView는 초기화된 뒤 먼저 HistoryViewState를 만들어요. 상태가 아직 로딩 중이면 loading state를 샘플링해요. 샘플링이 준비되면 HistoryViewLoadedState로 바뀌어요. HistoryViewLoadedState에는 다음이 저장돼요. [20]

  • anchor
  • tag
  • namespace
  • 절반 윈도우 한계
  • 위치 집합
  • holes

매번 render하기 전의 샘플링도 clipHoles의 제어를 받아요. 이 상태 계층은 “아직 hole 채우기가 필요함”과 “이미 표시 가능한 윈도우가 있음”을 나눠요. 그래서 UI가 로컬 기록과 로딩 자리 표시를 직접 이어 붙이는 일을 피해요. (추론)

외부 트랜잭션과 로컬 트랜잭션은 서로 다른 진입점을 타요.

  • 외부 트랜잭션: refreshDueToExternalTransaction이 메시지 이력 뷰에 대해 reset을 실행하고 참을 반환해요.
  • 로컬 트랜잭션: replay로 들어가서 관련 history operations를 수집해요. [20]

ViewTracker는 먼저 등록된 메시지 이력 뷰를 돌아요. 재생이 참을 반환하면 새 불변 뷰와 업데이트 유형을 그 뷰의 ValuePipe에 넣어요. [21] 그래서 저장 계층은 모든 레코드 변경을 UI에 브로드캐스트할 필요가 없어요. UI는 구독한 투영이 실제로 바뀐 뒤의 스냅샷만 받아요.

업데이트 유형에는 추가적인 의미가 있어요. ViewUpdateType에는 적어도 초기, 초기 읽지 않음, 일반 업데이트가 있어요. CombinedMutableView는 현재 트랜잭션에 구독한 peer와 thread의 hole 연산이 있는지 검사하고, 메시지 이력 업데이트를 FillHole로 표시할 수 있어요. [21] 컨트롤러는 이를 근거로 첫 구성, 일반 삽입, hole 채움 뒤의 재정렬을 구분할 수 있어요. 그러면 불필요한 스크롤 위치 지정이나 애니메이션을 줄일 수 있어요. (추론) 구체적인 UI 컨트롤러가 이 열거형을 어떻게 쓰는지는 Postbox 뷰 모델의 범위 밖이에요.

combinedView가 원자성을 보장하는 경계는 단일 Postbox 트랜잭션이에요. 내부적으로 키마다 mutable view를 만들어 같은 tracker 안에서 조합해요. 조합 객체는 재생할 때 각 내부 뷰를 차례로 호출하고, 어느 하나라도 바뀌면 새 CombinedView를 내보내요. [22] [24] “읽지 않은 개수와 환경설정을 읽은 뒤 배지를 결정”하는 경우에 이게 중요해요. 두 항목을 같은 커밋 상태에서 얻을 수 있기 때문이에요. 네트워크, 계정 관리자, 또 다른 계정 데이터베이스의 상태는 자동으로 병합하지 않아요. 다중 계정 진입점과 계정 설정 동기화는 다중 계정, 로그인, 구성 동기화를 참고하세요.

iOS와 macOS의 재사용 경계

이 장의 모든 Postbox와 TelegramCore 코드 인용은 Telegram-iOS의 지정 체크아웃에서 가져왔어요. TelegramSwift 작업 트리는 submodules/telegram-ios를 체크아웃해 두었고, 고정 커밋은 a24bbe45f9861f736a79916a50898512f751e0dc예요. fork도 다음이 이 장에서 설명한 메커니즘과 같아요.

  • MessageId
  • MessageIndex 비교
  • hole 구간 삭제
  • 외부 트랜잭션 reset과 로컬 트랜잭션 replay [31] [32] [33]

macOS fork 차이. 이 fork는 현재 업스트림보다 앞선 시점의 것이에요. Quick Reply Local 6까지만 정의하고, 업스트림에는 ephemeral과 welcome message 공간이 더 있어요. [2] [30] 따라서 macOS 변경은 이 고정 fork를 기준으로 해야 해요. 더 새로운 업스트림 필드를 기존 동작으로 여기면 안 돼요. fork 검증은 macOS fork 장별 검증(08–15장)을 참고하세요.

macOS 애플리케이션 코드에서 PostboxViewKey.unreadCounts를 구독하는 모습을 볼 수 있어요. 이어서 UnreadMessageCountsView에서 total을 얻고 absolute counters의 messageCount를 누적해요. [23] 뷰 추상화가 플랫폼을 가로질러 안정적인 도메인 결과를 내놓고, 각 플랫폼은 자기 윈도우, 메인 스레드, 메뉴 막대 표시 로직을 유지한다는 걸 보여 줘요. (추론) macOS 클라이언트 고유의 애플리케이션 계층과 시스템 통합은 macOS 클라이언트의 시스템 계층을 참고하세요.

새 클라이언트가 다시 쓸 수 있는 경계는 Postbox의 비공개 테이블 형식이 아니라 도메인 투영이에요. UI는 PostboxView의 불변 출력만 구독하고, 결과는 플랫폼 자체의 큐에서 전달받아야 해요. MutableMessageHistoryView를 갖고 있거나 hole 집합을 직접 수정하면 안 돼요. [19] [24] 이렇게 하면 메시지 이력, 필터, 읽지 않음, hole의 복잡한 일관성 규칙이 하나의 트랜잭션 도메인 안에 머물러요. 대가는 새로운 투영을 추가할 때 view key, mutable replay 로직, 초기 로드, 불변 결과 타입을 함께 정의해야 한다는 점이에요. (추론)

다시 쓸 수 있는 또 다른 원칙은 “미지”를 모델 안에 저장하는 거예요. 이력과 채팅 목록은 모두 가져오지 못한 구간을 hole로 표현해요. 뷰는 hole을 로딩 수요로 드러내고, Core는 결과를 트랜잭션으로 되써요. [8] [9] [10] 컨트롤러가 isLoadingMore 같은 임시 플래그를 유지하는 방식과 비교하면, 이 접근은 화면이 파괴되거나 다시 만들어지거나, 여러 화면이 같은 이력을 동시에 관찰할 때도 실제 동기화 상태를 지켜 줘요. 다만 삭제, 마이그레이션, 데이터베이스 비우기 같은 모든 작업이 hole과 색인의 대응 관계를 유지해야 해요. (추론)

설계에서 고른 절충

네임스페이스 덕분에 로컬, 클라우드, 비밀, 예약 메시지가 함께 있을 수 있어요. 하지만 모든 색인, hole, 읽기 상태, 질의 조건이 namespace를 가져야 해요. 이를 생략하면 국소 코드는 단순해지지만, 로컬 자리 표시와 원격 확인이 만나는 지점에서 신원이 모호해져요. [1] [2]

정규 테이블에 파생 색인을 더하면 페이지 분할, 태그, 스레드, 검색에 범위 질의를 쓸 수 있어요. 대신 쓸 때마다 색인을 유지하는 비용이 늘어요. Postbox는 한 트랜잭션의 의미 있는 연산 집합으로 이 부수 효과를 한곳에서 유지해요. 그래서 관찰자가 스스로 일관성을 복구해야 하는 위험이 낮아져요. [3] [6]

hole은 캐시의 불완전함을 일급 데이터로 끌어올려요. 그래서 UI는 로딩 경계를 솔직하게 보여 줄 수 있고, 필요할 때 보충도 할 수 있어요. 다만 hole의 분할, 병합, 추적, 요청 중복 제거는 상태 머신의 복잡도를 높여요. 이 커밋은 실패한 hole 채우기 RPC에 두 번째 시도를 예약하지 않아요. maxRetries: 0 때문에 명목상 0.1초에서 2.0초까지 누적되는 백오프는 효력이 없어요. [34] [35] 실패한 hole은 남고, 같은 완전한 hole 항목은 20초 동안 완료 기록 때문에 억제돼요. 그 이후에도 hole 집합의 변화, 메인 인스턴스 재구성, 자동 추적 hole의 쓰기가 있어야 다시 시작돼요. [36] 이 결론을 행 단위로 검증한 내용은 공백 채우기 실패 후의 재시도와 백오프를 참고하세요.

가변 뷰가 트랜잭션을 재생하는 방식은 전체 질의를 피하고, 구독 윈도우가 작업 집합을 자연스럽게 제한하게 해요. 대가는 모든 종류의 뷰가 어떤 연산이 관련 있는지 정확히 판단해야 한다는 점이에요. 구현이 어떤 트랜잭션 연산 하나를 빠뜨리면 화면이 낡은 상태가 될 수 있어요. 소스는 한곳에 모은 ViewTracker와 불변 출력으로 이 위험의 범위를 줄여요. [19] [21]

미검증 사항

  • 같은 LocationKey 아래의 hole이 서로 다른 namespace, 방향 또는 count를 가질 때, 소스는 안정적인 병합 규칙이나 우선순위 규칙을 정의하지 않아요. [36]
