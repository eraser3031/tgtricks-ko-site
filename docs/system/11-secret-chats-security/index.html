경계와 구성 요소

여기서 종단 간 암호화 레이어는 일반 MTProto(Telegram의 전송 프로토콜) 전송 위에 놓여요. 이 레이어는 비밀 채팅의 복호화된 메시지와 미디어 키를 보호해요. 클라이언트에서 데이터 센터까지의 전송 인증 키를 대신하지는 않아요. 이 장 밖의 주제는 다른 장을 참고하세요.

  • 전송 인증 키: 인증 키와 다중 데이터 센터
  • 음성·영상 통화의 종단 간 암호화: 통화 시스템
  • TL(Telegram의 타입 언어) 객체를 어떻게 만들고 호출하는지: TL 직렬화와 API 호출 계층

프로토콜은 비밀 채팅을 두 참여자가 가진 공유 키로 한정해요. 각 비밀 채팅은 계정의 모든 기기가 아니라 특정 기기에 묶여요. [3] 그래서 이 상태는 클라우드 이력에 기댈 수 없고, 일반 비공개 채팅처럼 다중 기기 사본으로 다룰 수도 없어요. 비밀 채팅은 요청을 수락한 기기만 쓸 수 있는 비밀 세션 상태를 가져요. [3]

아래 도표는 iOS의 주요 경계와 영속화 경계를 보여 줘요.

SecretChatState는 세션의 원자적 스냅샷이에요. 다음을 담아요.

  • 개시자(요청한 쪽) 또는 참여자(수락한 쪽) 역할
  • 내장 프로토콜 상태
  • 키체인
  • 사용자 검증 지문
  • 기본 자동 삭제 초

PeerChatState와 PostboxCoding을 구현해서 peer chat state와 함께 영속화되고, UI 메모리에 흩어져 있지 않아요. [1]

  • terminated
  • handshake
  • basicLayer
  • sequenceBasedLayer

마지막 종류인 sequenceBasedLayer는 다음을 추가로 저장해요.

  • 협상된 레이어
  • 키 교체 세션
  • 수신과 송신 기준 인덱스
  • 처리를 마친 최고 정규 수신 인덱스(기록된 기준과 로컬 작업 인덱스로 계산하는 안정적인 순번) [1]

덕분에 재시작한 클라이언트는 상태 하나와 작업 로그 둘로 프로토콜 위치를 복구할 수 있어요. 대가는 상태 전이가 로그 갱신과 같은 Postbox 트랜잭션 안에 있어야 한다는 점이에요.

SecretChatKeychain은 iOS Keychain이 아니에요. 세션 개인 키의 프로토콜 키 집합이에요. 각 SecretChatKey는 다음을 저장해요.

  • 지문
  • 원본 key
  • 유효 구간
  • 사용 횟수

latestKey는 정규 작업 인덱스를 기준으로 가장 늦게 유효한 key를 고르고, 필요하면 영구 key로 폴백(대체)해요. [4]

이 설계 덕분에 키를 교체하기 전에 남은 순서 공백(hole)도 옛 key로 풀 수 있어요. 또 옛 key가 살아 있는 범위가 믿을 수 없는 벽시계 시간(시스템 시계의 시간)이 아니라 프로토콜 인덱스가 돼요.

비밀 채팅도 TelegramCore, Postbox, MediaBox, Network를 재사용해요.

  • iOS 앱 target: AppDelegate에서 암호화 매개변수를 얻은 뒤 계정을 만들어요.
  • macOS 코드: submodules/telegram-ios에서 TelegramCore, Postbox, SSignalKit 같은 같은 이름의 코어 패키지를 참조해요. [5] 이 서브모듈은 overtake 포크의 a24bbe45f9861f736a79916a50898512f751e0dc로 체크아웃돼 있어요. 이 커밋은 이 장의 업스트림 iOS 커밋보다 앞서 있어요.

그래서 macOS 동작은 fork 기준으로 검증해야 하고, 더 새로운 업스트림으로 곧바로 넓혀 짐작할 수 없어요. macOS fork 장별 검증(08–15장)

초기 키 협상

초기 협상에서는 두 가지를 해결해야 해요.

  1. 양쪽이 같은 256바이트 비밀을 만들어야 해요.
  2. DH(Diffie-Hellman 키 교환) 매개변수나 계산 구현이 맞지 않는 경우를 최대한 일찍 발견해야 해요.

공식 흐름은 이래요. 먼저 DH 설정을 가져와요. 안전 소수와 공개값 범위를 검사한 뒤, g_a 또는 g_b를 보내도록 요구해요. [3]

encryptedChatRequested를 받으면, iOS는 이 기기에서 수락이 허용되고 로컬에 같은 peer가 없을 때만 참여자 상태를 만들어요. 순서는 이래요.

  1. 256바이트 난수 b를 만들어요.
  2. initialHandshakeAccept를 SecretOutgoing 로그에 넣어요.
  3. peer와 chat state를 기록해요. [2]

그래서 UI의 수락 동작이 네트워크 RPC를 직접 하지 않아요. 먼저 다시 재생할 수 있는 로컬 의도를 얻어요. 일반 메시지 오프라인 큐의 원칙과 같아요. 메시지 큐의 일반 설계는 메시지 전송 파이프라인과 오프라인 작업 큐를 참고하세요.

개시자는 waiting 업데이트를 받으면 .handshake(.requested(g:p:a:))를 저장해요. 참여자의 송신 처리기는 검증된 DH 설정을 얻고 MTExp로 공개값과 공유 key를 계산해요. [2] [6]

공유 key를 다루는 과정은 이래요.

  1. 상대의 공개값을 MTCheckIsSafeGAOrB로 검사해요.
  2. 공유값이 256바이트보다 길면 자르고, 짧으면 앞쪽을 0으로 채워요.
  3. SHA1의 마지막 8바이트를 keyFingerprint로 기록해요. 이게 바로 프로토콜의 협상 일관성 검사예요. [3] [6]

수락에 성공하면 처리기는 이 순서로 처리해요.

  1. 초기 key를 .indefinite로 설정해요.
  2. 활성 레이어를 layer73으로 지정해요.
  3. 두 작업 로그의 현재 기준을 기록해요.
  4. 초기 key로 SHA1과 SHA256 지문을 계산해요.
  5. 레이어 지원 공지 reportLayerSupport를 큐에 넣어요. [6]

이 순서는 로컬에 key가 영속화되기 전에 상대가 받을 수 있는 데이터를 먼저 보내는 일을 막아요.

실패하는 경우는 이래요.

  • DH 값이 안전하지 않을 때 처리기는 전송 없이 끝나요.
  • 서버의 ENCRYPTION_DECLINED는 chatCancelled로 매핑돼요. [6]

키 지문에는 두 가지 의미가 있어요.

  • 네트워크 패킷 앞의 64비트 keyFingerprint: key를 고르고 협상을 검사하는 데 써요.
  • SecretChatKeyFingerprint: 초기 key의 SHA1과 SHA256 요약을 저장하고, 사람이 검증하는 데 써요.

공식 문서는 이 둘을 분명히 구분해요. [3]

사람이 검증하는 쪽은 이렇게 보여 줘요. iOS는 secretChatKeyImage로 두 요약을 Objective C 드로어에 넘겨요. 드로어는 두 요약이 모두 있을 때 12×12 색 블록을 만들고, key를 복사할 수 있는 텍스트로 보여 주지 않아요. [7] 이 색 블록은 서로 비교할 수 있는 시각적 약속이지 새로운 키 파생 함수가 아니에요.

macOS는 SecretChatKeyViewController에서 SecretChatState.keyFingerprint를 읽어요. SHA1과 SHA256을 이어 붙여서 identicon(키를 시각화한 그림)과 네 줄의 16진수 블록으로 보여 줘요. [8] iOS와 시각적 목표가 같아요. 양쪽 사용자는 믿을 수 있는 대역 외 채널(이 통신과 별개의 믿을 수 있는 경로)에서 이 그림이나 텍스트를 비교해야 해요. 코드가 신원 인증을 자동으로 끝내 주지 않아서, 이 단계는 여전히 사람의 판단에 달려 있어요.

레이어 협상과 순서 의미론

종단 간 메시지 포맷은 클라이언트 능력에 맞춰 발전해야 해요. 비밀 채팅은 decryptedMessageLayer로 더 새로운 TL 메시지를 감싸요. 상태에는 활성 레이어와, 로컬과 원격이 요청한 레이어가 기록돼요. 현재 공유 코어는 46, 73, 101, 144의 네 시퀀스 레이어를 열거해요. [1] [9]

더 높은 레이어 번호를 받으면 수신 암호화 처리기는 basicLayer에서 sequenceBasedLayer로 넘어가요. 이때 기준을 이렇게 기록해요.

  • 수신 기준: 현재 수신 항목의 로컬 인덱스
  • 송신 기준: 다음 송신 항목 인덱스 [10]

이렇게 하면 이후의 모든 로그 항목을 안정적인 정규 인덱스로 환산할 수 있어요.

프로토콜은 더 높은 레이어의 패킷을 받으면 바로 원격 레이어를 갱신하고, 새 세션이 성공하면 로컬 레이어를 공지하도록 요구해요. [3]

순번은 서버의 재정렬, 중복, 누락, 반사를 다뤄야 해요. 일반 클라우드 메시지의 pts에는 기대지 않아요. 클라이언트는 로컬의 원시 수신·송신 카운트를 홀짝이 서로 다른 선형 순번으로 매핑해요. 홀짝 규칙은 이래요.

  • 개시자의 송신 순번: 홀수
  • 참여자의 송신 순번: 짝수 [11]

모든 서비스 메시지도 순번을 차지해서, 레이어 공지, 재전송, 키 교체가 이 검사를 피해 갈 수 없어요.

구체적인 구현은 네트워크 패킷을 메시지 테이블에 곧바로 쓰지 않아요. 수신은 두 단계로 나뉘어요.

  1. ProcessSecretChatIncomingEncryptedOperations가 먼저 패킷 헤더 8바이트에서 key fingerprint를 꺼내요. 상태 keychain에서 대응하는 key를 고르고 복호화 함수를 호출해요. 검증이 통과하면 평문 TL bytes, 레이어, 시퀀스 정보, 파일 참조를 SecretIncomingDecrypted 로그에 기록해요. [10]
  2. 이후 processSecretChatIncomingDecryptedOperations가 레이어 전용 SecretApi 객체를 성공적으로 파싱해야만 StoreMessage를 만들거나 서비스 동작을 실행해요. [12]

키 교체와 전방 비밀성

같은 공유 key를 오래 쓰면 유출됐을 때 영향 범위가 커져요. 공식 규격은 Layer 20부터 PFS(전방 비밀성, 키가 유출돼도 과거 통신을 보호하는 성질) 지원을 요구해요. 다음 중 하나이면 재협상을 시작하라고 권장해요.

  • key로 암호화·복호화한 메시지가 100개를 넘을 때
  • key를 일주일 넘게 썼고 그동안 메시지를 암호화한 적이 있을 때 [15]

고정 iOS와 macOS fork의 실제 자동 개시 정책은 로컬 송신 작업 카운트만 검사해요. 저장소 안의 TDLib 독립 SecretChatActor에는 일주일 조건이 있지만, iOS는 그 조건이 들어 있는 tdcore를 링크하지 않아요. 자동 PFS 키 교체 트리거 지점

옛 key는 공백이 채워진 뒤 삭제되고, 초기 key의 SHA1은 시각화 용도로 남겨 둬요. [15]

  • accepting
  • accepted: 후보 key와 fingerprint를 저장해요. [1]

이 구분은 불리언 하나보다 정밀해요. 프로세스를 재시작해도 다음을 구별할 수 있어요.

키 교체는 이렇게 진행돼요.

  • 수락 측: 난수 b를 만들고 pfsAcceptKey를 보내요. 후보 key와 지문은 accepted로 기록해요. [6]

commit을 받으면 처리기는 이 순서로 처리해요.

  1. 세션 ID와 후보 지문을 검증해요.
  2. “다음 송신 로그 항목”의 정규 인덱스에서 새 key의 유효 범위를 시작해요.

이 인덱스 경계가 순서가 뒤섞여 도착하는 경우를 처리하는 핵심이에요. 도착 시간만으로 메시지가 옛 key를 쓸지 새 key를 쓸지 정하는 일을 막아 줘요.

양쪽이 동시에 개시하면 처리기는 rekeySessionId를 비교해요.

  • 더 작은 ID를 받으면: 현재의 requesting 또는 requested는 abort를 큐에 넣어요.
  • 그렇지 않으면: 원격 세션의 수락을 거부해요. [12]

이 동작은 공식 규격에서 더 작은 ID 쪽이 물러난다는 동시 개시 해결 규칙에 대응해요. [15] 대가는 추가 제어 패킷과 옛 key가 잠깐 함께 있는 것이에요. 이득은 양쪽이 서로 키 교체를 끝없이 중단하지 않는다는 점이에요.

PasscodeCore와 AppLock이 해결하는 건 앱 접근 제어이고, 위의 SQLCipher key 파생이 아니에요. PasscodeKeychainScope는 generic password 항목을 동기화할 수 없게 두고 kSecAttrAccessibleWhenUnlockedThisDeviceOnly로 표시해요. [23] Keychain의 인증 실패나 상호작용 불허는 읽을 수 없음 또는 시스템 잠금으로 구분해요. 덕분에 상위 계층은 기기 잠금 화면을 “암호 오류”로 잘못 보고하는 일을 피할 수 있어요.

상태 복구와 거부 경로

비밀 채팅의 진짜 어려움은 AES 호출 한 번이 아니에요. 어려운 점은 네트워크, 디스크, 프로세스가 어느 단계에서든 실패할 수 있다는 거예요. 그래서 TelegramCore는 수신 암호문, 수신 평문, 송신 의도에 서로 다른 OperationLogTags를 써요.

  • 암호화된 수신 기록: 서버 payload를 보존해요.
  • 복호화된 수신 기록: 검증을 마친 평문 TL bytes를 저장해요.
  • 송신 기록: 아직 확인되지 않은 사용자 메시지나 서비스 동작을 저장해요. [6] [10] [12]

이 세 기록 계층의 순서가 중요해요. 네트워크 업데이트는 먼저 SecretChatIncomingEncryptedOperation으로 변환돼요. SecretChatIncomingEncryptedOperation은 encrypted message bytes의 앞에서 8바이트 fingerprint를 읽고 선택적인 SecretChatFileReference를 보존해요. [27] 처리기는 대응하는 세션 key를 찾아야만 복호화를 시도해요. key를 찾지 못하면 로그를 남기고 이 암호화 기록을 소비하지 않아요. [10] 방금 새 key로 전환했거나 아직 공백을 채우는 중인 상태에 재시도할 기회를 남겨 두는 거예요.

복호화 함수가 돌려주는 건 바로 표시할 수 있는 텍스트가 아니에요. message contents, 파싱된 layer, 선택적인 sequence info를 돌려줘요. 이어서 처리기는 현재 세션 상태를 검사해요.

  • terminated와 handshake: 모두 메시지를 거부해요.
  • basicLayer: 예상되는 옛 레이어만 허용하거나, 새 레이어가 처음 도착할 때 상태를 전환해요.
  • 이미 sequence layer일 때: 46 미만의 레이어를 거부해요. [10]

이렇게 해서 “어떤 wire format을 언제 허용하는가”가 영속 상태 머신의 명시적 조건이 돼요.

아래 시퀀스 도표는 초기 키 수립 이후의 영속화와 전송 순서를 보여 줘요.

개시자와 참여자는 초기 핸드셰이크의 로컬 상태가 달라요.

  • 개시 측: waiting 업데이트에서 g, p, 개인 a를 저장해요.
  • 참여 측: 먼저 accepting을 저장한 뒤 개인 b를 대기 중인 작업 안에 감싸 둬요. [2]

덕분에 재시작해도 공유 key 계산에 필요한 비밀을 잃지 않아요. 개인 지수를 UI나 임시 클로저에 넘기는 일도 피해요. 대가는 Postbox의 기밀성이 종단 간 키 보호의 일부가 된다는 점이에요.

초기 협상을 마친 뒤 초기 key, 지문, 활성 레이어, 레이어 공지를 만드는 일도 하나의 트랜잭션 경로에서 일어나요. [6] 이 경로의 원자성은 네트워크 원자성과 같지 않아요. 서버가 이미 RPC를 받아들였는데 로컬 프로세스가 확인 전에 종료될 수 있어요. 작업 로그의 delivered 상태와 안정적인 전역 난수 ID 덕분에 재시도도 프로토콜이 해석할 수 있어요. 서비스 동작은 이미 전달된 뒤에 재전송하면 새 동작 난수 ID를 골라요. [6] (추론) 이렇게 하면 서버 재시도 의미론과 로컬 크래시 복구가 서로 충돌할 가능성이 낮아져요.

다음 경우에는 실패를 기록하고 경로에 따라 작업을 제거하거나 보존해요.

  • payload를 복호화할 수 없을 때
  • 레이어가 지원되지 않을 때
  • 사전 파싱 조건을 어길 때 [10]

읽어 본 구현은 실패한 암호문을 일반 텍스트로 강등해서 표시하지 않아요. handshake 상태에서는 일반 암호화 메시지도 받아들이지 않아요. 보안 시스템은 읽기 쉬움을 최대로 끌어올리려 하기보다, 구조가 올바르다고 증명할 수 없는 데이터를 우선 거부해야 해요.

순서 검사도 복구의 일부예요. 정규 인덱스는 기록된 기준과 로컬 작업 인덱스로 계산해요. topProcessedCanonicalIncomingOperationIndex는 순서대로 해석을 마친 위치를 나타내요. [1] 그래서 클라이언트는 재시작한 뒤에도 중복 패킷, 현재 패킷, 먼 미래의 패킷을 구분할 수 있어요. 서버의 전달 순서를 믿을 필요가 없어요. 프로토콜은 원격이 보고한 in_seq_no가 이쪽이 보낸 위치에 1을 더한 값을 넘지 않는지도 검사하라고 요구해요. [11]

정상 재전송은 이미 있는 송신 로그 항목을 다시 활성화할 뿐이에요. 같은 순번에 새 메시지를 다시 구성하지 않아요. [12] 이 점이 핵심 차이예요. 상대가 요청한 범위 안의 로컬 항목 하나가 없으면, 처리기는 couldNotResendRequestedMessages를 참으로 설정해요. 이후의 파싱은 이 플래그의 제약을 받아요. [12] 이 방식은 가용성의 일부를 희생하지만, 클라이언트가 이미 약속한 순번을 다른 내용으로 채우는 일을 막아요.

확인되지 않은 비밀 메시지를 삭제할 때도 원래 항목을 그냥 버릴 수 없어요. 공식 규격은 원래 메시지를 자체 삭제 동작으로 바꾸고, 순번의 연속성을 유지하려고 삭제 메시지를 따로 보내라고 요구해요. [11] 이 장에서는 읽은 범위에서 이 특수 삭제 변환의 호출 지점을 일일이 추적하지 않았어요. 여기서는 프로토콜 정의만으로, 비밀 채팅의 삭제 경로가 왜 순번의 제약을 받아야 하는지 설명해요. 메시지 이력 인덱스와 뷰의 저장 표현은 Postbox 뷰와 메시지 이력 모델을 참고하세요.

인증 패딩과 복호화 선택

MTProto 2.0의 msg_key는 복호화된 길이 접두사, TL 내용, 무작위 패딩에 대한 무결성 검사 입력이에요. [3] 수신자는 msg_key를 다시 계산해서 암호문 헤더에 실려 온 16바이트 값과 비교해야 해요. 일치할 때만 평문을 받아들일 수 있어요. 이 비교는 잘못된 공유 key와 대부분의 payload 변조를 함께 찾아내요. 독립적인 표준 AEAD 태그가 아니라 프로토콜이 규정한 조합 검증 방식이에요. [3]

iOS 송신 측은 역할에 따라 공유 key의 서로 다른 바이트 위치에서 데이터를 가져와요. creator에는 오프셋 0을, participant에는 오프셋 8을 골라요. [13] 양쪽이 같은 공유 key를 가지고 있어도, 반대 방향에서는 서로 다른 AES key와 IV를 얻어요. 이렇게 하면 한쪽 방향의 암호문을 원래 송신자에게 되돌려 보내는 단순한 공격을 막아요. 이 보안 동기는 프로토콜의 방향 매개변수에서 나와요. iOS 소스는 오프셋 선택만 보여 주기 때문에, 여기서의 공격 설명은 추론이에요. [3] [13]

무작위 패딩은 16바이트 정렬만 맡는 게 아니에요. 프로토콜은 12~1024바이트의 패딩을 요구해요. [3] 현재 송신 코드는 이렇게 패딩을 만들어요.

  1. 128바이트 무작위 캐시에서 먼저 최소 12바이트를 가져와요.
  2. 정렬하도록 채워요.
  3. 16의 배수인 무작위 여분을 덧붙여요. [13]

이 구현의 추가 패딩은 아무 크기나 되는 게 아니라 로컬 알고리즘의 제약을 받는다는 뜻이에요. 이 코드를 교체한다면 프로토콜 범위와 패딩에 대한 msg_key의 포함 범위를 유지해야 해요.

해시 알고리즘은 용도마다 달라요.

  • 초기 핸드셰이크 fingerprint: SHA1을 써요. 프로토콜 호환성 때문에 생긴 예외예요.
  • 메시지 레이어의 MTProto 2.0: SHA256을 써요.
  • 파일 key fingerprint: MD5 조합으로 계산해요. [3]

이 알고리즘들을 이름만 보고 하나의 “통일된 해시 정책”으로 합칠 수 없어요. 각각 다른 wire format과 호환성 위치에 있어요. 구현을 감사할 때는 특정 해시 함수를 검색하는 데서 그치지 말고 호출 지점과 바이트 절단을 검사해야 해요.

미디어의 무결성 경계도 달라요. 비밀 파일 다운로드 함수는 리소스 key를 범용 multipartFetch에 넘기고 평문 길이도 함께 전달해요. [14] 그래서 네트워크 계층은 데이터 센터와 구간 단위로 암호화된 바이트를 내려받을 수 있어요. 리소스 계층은 언제 어떻게 평문으로 바꿀지 알고 있어요. 파일 참조와 실제 key를 분리하면 서버 파일 ID 자체가 복호화 능력이 되는 일을 막아요. 대가는 캐시 무효화, 이어받기, 파일 전달이 모두 올바른 resource 메타데이터를 보존해야 한다는 점이에요.

로컬 보호의 책임 분리

ValueBoxEncryptionParameters는 Postbox를 여는 매개변수예요. 계정의 영속 상태를 덮기 때문에, 저장된 SecretChatState와 키 집합도 덮어요. [20] [21] 이 보호 범위는 코드상의 사실이고 종단 간 프로토콜의 약속은 아니에요. 종단 간 프로토콜은 서버가 채팅 key를 얻어서는 안 된다는 것만 제한해요. 기기가 잠금 해제된 경우, 탈옥된 경우, 백업이 복원되는 경우의 위험은 여전히 로컬 암호화, 운영체제, 접근 제어가 함께 정해요.

메인 앱과 확장이 데이터 루트 디렉터리를 공유할 때는 같은 데이터베이스 매개변수를 얻어야 해요. AppDelegate는 같은 root path에서 device-specific 매개변수를 얻어요. 알림 콘텐츠 확장도 app group 경로에서 같은 key와 salt 쌍을 얻어요. [20] [28] 덕분에 확장은 필요한 계정 데이터를 열 수 있어요. 대가는 확장 프로세스도 로컬 비밀의 공격 표면에 들어온다는 점이에요. 푸시 서비스, 확장 프로세스, 프로세스 간 락의 전체 설계는 푸시, 확장 프로세스와 다중 프로세스 협업을 참고하세요.

데이터베이스를 열 때 SqliteValueBox는 salt가 16바이트이고 key가 32바이트인지 검사한 다음, 둘을 이어 붙여 SQLCipher key 매개변수로 써요. [22] WAL, 메모리 임시 저장소, 동기화 정책도 설정해요. [22] 이 설정들은 각각 동시성, 임시 디스크 쓰기, 성능에 영향을 줘요. 비밀 채팅의 종단 간 암호학은 바꾸지 않아요. 데이터베이스 암호화를 전송 암호화나 채팅 암호화와 같은 계층으로 뭉뚱그리면 서로 다른 키 교체와 위협 모델이 가려져요.

더 새로운 업스트림의 데이터베이스 key 생성 함수에는 하드웨어 개인 키를 읽고 쓰는 능력이 들어 있어요. Keychain access group에서 EC 개인 키를 찾고, 앱 비밀을 암호화·복호화하는 API를 제공할 수 있어요. [20] 하지만 데이터베이스 매개변수 경로의 감싸기 코드는 주석 처리돼 있어요. 유효한 경로는 매개변수 파일을 읽거나 원자적으로 써요. [20] fork의 대응하는 유효 경로는 비원자적 쓰기예요. [32] 그래서 “하드웨어 감싸기 인터페이스를 제공한다”와 “현재 데이터베이스 key가 이미 하드웨어로 감싸져 있다”를 엄격히 구분해야 해요. 후자의 결론은 읽어 본 코드가 뒷받침하지 않아요.

PasscodeCore의 Keychain 항목은 동기화를 명시적으로 꺼요. 기기 잠금이 풀렸을 때만, 그리고 이 기기에서만 접근할 수 있게 제한해요. [23] 기기에 로컬로 있어야 하는 접근 자격 증명을 저장하기에 알맞아요. 모든 Postbox 데이터나 모든 비밀 채팅 미디어가 같은 Keychain 속성을 가진다는 뜻은 아니에요. AppLock은 상태 JSON도 root path에 비동기 원자적으로 기록해서 잠금 화면, 실패 횟수, 자동 잠금 정보를 복원하는 데 써요. [24]

AppLock은 5초마다 앱 활동 타임스탬프를 갱신하고, 단조 시작 시간을 기록의 기준으로 삼아요. [24] 수동 잠금을 하면 PasscodeSession을 더 이상 쓸 수 없게 해요. 잠금을 해제하면 실패 시도를 지우고 활동 시간을 갱신해요. [24] (추론) 단조 시간 덕분에 사용자가 벽시계 시간을 조정해도 자동 잠금 판정이 곧바로 바뀌지 않아요. 대가는 재시작한 뒤 시작 식별자를 연결해야 하고, 절대 초 하나만 영속화해서는 안 된다는 점이에요.

생체 인식은 암호를 곧바로 대체하지 않아요. enableBiometrics는 암호가 있는 settings 세션이 이미 있어야 해요. 새 biometric account를 기록한 다음, 같은 32바이트 session key를 다시 읽어 대조해요. 인증에 성공하면 scope와 lifetime이 제한된 세션을 만들어요. [25] “현재 기기가 인증하려 한다”와 “현재 작업이 어느 리소스에 접근할 권한이 있는가”를 분리하는 거예요. 사용자가 생체 인식을 끄면 정리해야 할 옛 account 목록도 관리해요. [25]

임시 파일 정책에도 솔직한 경계가 필요해요. TempBox는 시작 ID에 따라 옛 디렉터리를 삭제해요. 참조 카운트에 따라 현재 디렉터리를 삭제해요. [26] 크래시로 파일이 남을 확률은 낮추지만, 플래시 블록이 바로 덮어쓰였다는 걸 증명하지는 못해요. secure_delete는 특정 ValueBox 삭제 호출이 요청할 때만 켜져요. [22] 기밀 데이터를 다룰 때는 사후 삭제보다 짧은 수명, 최소한의 사본 수, OS 파일 보호가 여전히 더 믿을 만해요. (추론)

키 집합의 유효 구간은 복구 제약도 나타내요. 초기 key는 영구 유효 항목이에요. 키 교체 뒤의 key는 어떤 정규 송신 인덱스부터 유효해요. [4] key는 방향에 따라 이렇게 골라요.

  • 송신할 때: 그 송신 인덱스를 덮는 가장 최신 key를 골라요.
  • 수신할 때: payload의 fingerprint로 집합에서 key를 찾아요. [4] [10]

이 두 조회는 차원이 달라요. 하나는 이쪽이 이미 약속한 송신 순서를 향하고, 다른 하나는 상대의 암호문이 선언한 key 신원을 향해요.

이렇게 양방향으로 설계해서 “현재 key”만 저장하는 일을 피해요. 한쪽이 전환한 뒤에 옛 key의 늦게 도착한 암호문을 받더라도, fingerprint 조회로 옛 항목을 찾을 수 있어요. 새 key의 첫 로컬 작업이 이미 로그에 기록됐다면, 정규 인덱스 선택이 옛 항목을 잘못 쓰지 않아요. [4] (추론) 그래서 구현은 “옛 key를 잠시 둘 수 있다”를 순서를 채우는 데 필요한 구간으로 한정하고, 모든 과거 key를 장기 복호화 보관소로 삼지 않아요.

SecretChatIncomingEncryptedOperation은 서버의 두 종류 API 업데이트를 하나로 정규화해요.

  • 일반 encrypted message: file reference를 저장해요.
  • encrypted service message: file reference를 저장하지 않아요.

둘 다 randomId, chat ID, 시간, 종류, fingerprint, 암호화된 bytes를 저장해요. [27] 이렇게 정규화해서 이후의 복호화기는 API 생성자를 분기 처리할 필요가 없어요. 재생 로그의 입력도 간결하게 유지돼요.

복호화 이후 단계에서 파서는 SecretApi8, SecretApi46, SecretApi73, SecretApi101, SecretApi144 중에서 구체적인 schema를 골라요. [12] “먼저 업그레이드하고 옛 메시지는 무시한다”는 전략이 아니에요. 새 클라이언트도 과거 레이어의 파싱 분기를 유지해요. 대가는 레이어마다 미디어, 엔티티, 서비스 동작 매핑이 중복된다는 점이에요. 이득은 업그레이드하는 동안에도 옛 세션에 이미 저장된 메시지를 계속 해석할 수 있다는 점이에요.

현재 레이어의 협상 상태는 이쪽이 요청한 레이어와 원격이 요청한 레이어를 함께 저장해요. [1] secretChatCommonSupportedLayer는 받은 원격 레이어를 바탕으로 공통 지원 레이어를 골라요. [10] 덕분에 협상이 끝나기 전에도 양쪽의 의도를 계속 저장할 수 있어요. 단일 값을 곧바로 덮어쓰는 것보다 복구하기 쉽지만, 모든 수정 경로가 이쪽의 공지와 상대의 능력을 혼동하지 않아야 해요.

메시지 자동 삭제도 뷰 타이머가 아니라 영속 속성에 기대요. 수신 파싱은 ttl을 AutoremoveTimeoutMessageAttribute로 기록해요. 서비스 동작이 기본 타임아웃을 바꾸면 채팅 상태에 기록돼요. [12] [17] 만료 관리자는 다시 Postbox 뷰에서 곧 만료될 항목을 가져와요. [16] 이렇게 계층을 나눠서 채팅에 다시 들어가거나, 기기 방향을 바꾸거나, UI를 재시작해도 이미 확정된 로컬 카운트다운이 다시 시작되지 않아요.

스크린샷 경로도 같은 원칙을 보여 줘요. 시스템 스크린샷 알림은 먼저 로컬 관찰자가 중복을 제거해요. 보이는 비밀 채팅은 일반 전송 대기 메시지를 만들고 historyScreenshot 동작을 붙여요. [17] [18] [19] 그래서 네트워크 재시도, 순번 할당, 종단 간 암호화는 일반 송신 파이프라인을 재사용해요. 대가는 상대편 알림이 로컬 API 이벤트에 대한 동기적 확인이 아니라는 점이에요. 네트워크가 오프라인이면 작업이 성공적으로 전송된 뒤에야 도착해요.

더 새로운 업스트림의 데이터베이스 매개변수 파일 동시성 락은 자문 락이에요. 100번 시도하며 시도 사이마다 20밀리초를 기다리고, 락을 얻지 못해도 계속 읽고 써요. [20] 중단된 프로세스 하나가 시작을 영원히 막는 일을 피하려는 거예요. 옛 버전이 락을 지키지 않을 수 있다는 점도 인정해요. 원자적 파일 쓰기는 두 번째 방어선이에요. 락 없는 독자가 찢어진 key 데이터를 보지 않게 해 줘요. [20] fork에는 이 자문 락이 없고 비원자적 쓰기를 써요. [32] 이 차이는 버전 차이이고, fork의 호환성 절충이 아니에요.

SQLite의 secure_delete는 호출마다 동적으로 설정되는 연결 옵션이에요. SqliteValueBox.remove는 목표 secure 값과 캐시된 값을 비교해서 변했을 때만 pragma를 실행해요. [22] 삭제할 때마다 데이터베이스 옵션을 반복해서 설정하는 일을 피해요. 또 호출하는 쪽이 기밀 삭제를 올바르게 표시해야 한다는 뜻이기도 해요. 데이터베이스 암호화에만 기대서는 삭제 의미론의 감사를 대신할 수 없어요.

설계 절충

Telegram은 비밀 프로토콜을 영속화할 수 있는 상태 머신으로 모델링하고, 모든 네트워크 입력과 출력을 작업 로그로 모델링해요. 그 이득은 크래시 복구, 오프라인 전송, 엄격한 순번이 함께 있을 수 있다는 점이에요. 비용은 상태, 로그, 메시지 테이블, 리소스 캐시의 트랜잭션 경계를 올바르게 유지해야 한다는 점이에요.

키 교체는 시간만이 아니라 정규 작업 인덱스로 유효 구간을 나눠요. 그래서 네트워크 재정렬과 늦게 도착한 패킷을 견딜 수 있어요. 비용은 옛 key를 공백이 채워질 때까지 보관해야 하고, 키 교체 서비스 패킷도 정상적인 순서에 들어가야 한다는 점이에요.

메시지 본문과 미디어는 서로 다른 key를 써요. 세션 key는 작은 TL 메시지와 미디어 복호화 재료만 보호해요. 파일마다 key를 두면 독립적인 캐시와 분할 다운로드를 지원할 수 있어요. 비용은 모든 미디어 유형이 추가 키 재료를 올바르게 싣고, 검증하고, 지워야 한다는 점이에요.

로컬 방어는 SQLCipher 데이터베이스 암호화, 시스템 Keychain 자격 증명, AppLock 세션, 임시 파일 회수로 나뉘어요. 계층을 나누면 UI 잠금 하나가 모든 비밀 보호를 떠맡는 일을 피하는 데 도움이 돼요. 비용은 이들이 같은 루트 키 체인이 아니라는 점이에요. 감사할 때는 key 파일, 데이터베이스, Keychain, 확장 공유 디렉터리, 임시 파일을 각각 검증해야 해요.
