Telegram은 서버 이벤트를 복구할 수 있는 순서 있는 로그 여러 개로 다뤄요. 클라이언트는 푸시를 믿을 수 있다고 가정하지 않고, 응답 순서가 고정되어 있다고도 가정하지 않아요. 진행 상황은 계정 수준의 pts, qts, seq, date와 채널별 pts로 찾아요(각각의 뜻은 첫 절에서 설명해요). 순서가 뒤섞여 들어온 입력은 검증할 수 있는 상태 커밋 한 번으로 정리해요. [1] [3]

iOS의 중심 컴포넌트는 AccountStateManager예요. 네트워크 푸시, RPC가 돌려주는 Api.Updates, 로컬에서 시작한 상태 조작을 전용 큐 하나에 줄 세우고, 이렇게 처리해요.

  1. Postbox(로컬 데이터베이스)에서 읽어 AccountMutableState를 만들어요.
  2. AccountFinalState를 계산해요.
  3. Postbox 트랜잭션 하나 안에서 연산을 재생해요.

그래서 카운터의 전진과 메시지, 대화, 읽기 상태의 변경이 따로따로 보이는 일은 없어요. [6] [7] [12]

  • 4원 상태
  • 7종 연산 큐
  • 업데이트 그룹화
  • 연속 접두사
  • 오래된 스냅샷 거부

그래서 이 장의 핵심 동기화 불변식은 그 fork에도 똑같이 적용돼요. [13] [19] [20] [21] [22] [23] macOS fork 장별 검증 (01–07장)

프로토콜 상태와 로컬 모델

Telegram의 공식 규칙은 업데이트를 세 시퀀스로 나눠요.

  • 공개 메시지함 시퀀스: pts로 추적해요.
  • 비밀 채팅 이벤트 시퀀스: qts로 추적해요.
  • Updates 바깥 시퀀스: pts나 qts가 없는 나머지 업데이트로, seq와 date로 추적해요.

처음 로그인하면 클라이언트는 최신 공개 상태를 가져와 저장해요. 채널에는 따로 각자의 pts가 있어서 계정 공개 시퀀스에 섞이지 않아요. [1]

AuthorizedAccountState.State가 바로 이 공개 체크포인트예요. Int32 필드 네 개가 계정 상태에 인코딩돼요. 바깥의 AuthorizedAccountState는 invalidatedChannels도 저장해요. 각 항목에는 채널 식별자, 선택적 pts, 유효성 표시가 들어 있어요. 이 표시 덕분에 계정 수준 복구가 이어서 병렬로 재설정할 채널을 등록해 둘 수 있어요. [3]

submodules/TelegramCore/Sources/SyncCore/SyncCore_AuthorizedAccountState.swift 12–36행 발췌.

여기서 date, seq, pts는 쓰임이 서로 달라요.

  • date: 다른 메시지 로그의 카운터가 아니에요. Updates 시퀀스의 시간 경계이고, pts, qts와 함께 updates.getDifference에 전달돼요.
  • seq: Updates 패킷이 제공하고 상태에 저장돼요.
  • pts: 위치 의미는 업데이트가 싣고 오는 pts_count가 정해요.

pts 항목을 만나면 로컬 값과 비교해서 이렇게 판단해요.

  • 로컬 값이 pts - pts_count와 같으면 그 항목은 정확히 이어져요.
  • 로컬 값이 이미 그 항목의 끝점 이상이면 재생이거나 중복 입력이에요.
  • 그렇지 않으면 구멍이 생긴 것이므로 뒤따르는 항목을 바로 커밋하면 안 돼요.

[1] [2] [4]

소스는 모든 Api.Update에 같은 규칙을 만들어 주지 않아요. 분류는 이렇게 나뉘어요.

  • apiUpdatePtsRange: 삭제, 새 메시지, 읽기 상태, 편집, 웹 페이지, 폴더, 고정 같은 공개 업데이트를 명시적으로 나열해요.
  • apiUpdateQtsRange: 현재 updateNewEncryptedMessage만 카운트가 1인 qts 항목으로 매핑해요.
  • 나머지 업데이트: 바깥 seq나 date만으로 처리해요.

이렇게 분류하기 때문에 복합 Updates 패킷 하나를 서로 간섭하지 않는 순서 도메인으로 쪼갤 수 있어요. [4]

비밀 채팅의 키 협상과 암호문 처리는 여기서 다루지 않아요. qts는 여기서 복구에 참여하는 두 번째 순서 도메인일 뿐이고, 나머지 보안 의미는 종단 간 암호화와 로컬 보안을 참고하세요.

아래 도표는 같은 계정에 왜 공개 상태 필드 네 개와 여러 채널 상태가 필요한지 보여 줘요.

입력 합류와 단일 쓰기 큐

AccountStateManager는 모든 업데이트 처리를 큐 하나로 직렬화해요. 문제는 패킷 유실만이 아니기 때문이에요. 푸시는 아무 때나 도착할 수 있고, API 호출 하나의 Api.Updates 응답도 푸시와 뒤섞여 들어올 수 있어요. 호출마다 곧장 DB에 쓰면 카운터 검사, 중복 필터링, UI 이벤트가 경합해요.

그래서 AccountStateManager.Impl은 AccountStateManager라는 이름의 Queue를 만들고 operations 배열을 유지해요. startFirstOperation은 배열에서 아직 실행되지 않은 첫 연산만 시작하며, 먼저 isRunning을 세워요. 데이터베이스 락에만 기대는 동시 쓰기가 아니라 직렬 커밋 관문이에요. [6]

연산은 일곱 가지예요.

  • pollDifference: 공개 차이를 가져와요.
  • collectUpdateGroups: 합칠 입력을 기다려요.
  • processUpdateGroups: 구성하고 커밋해요.
  • custom: 아무 외부 상태 조작이나 직렬화해요.
  • pollCompletion: 이미 있는 연산이 비워지기를 기다려요.
  • processEvents: 커밋 후 알림을 보내요.
  • replayAsynchronouslyBuiltFinalState: 비동기 채널 작업이 구성한 최종 상태를 커밋해요.

[6]

submodules/TelegramCore/Sources/State/AccountStateManager.swift 7–23행 발췌.

reset은 수신 체인의 시작점이에요. UpdateMessageService(받은 Api.Updates를 UpdateGroup으로 통일하는 서비스)를 만들고 그 ValuePipe를 구독하며, network.addUpdateSink로 네트워크 업데이트 수신기에 등록해요.

네트워크는 래핑된 메시지 안의 Api.Updates를 networkSessionDidReceive에 넘겨요. 같은 서비스가 상태 관리자의 addUpdates도 받기 때문에, 푸시와 RPC 응답이 같은 정규화 경로를 타요. 세션 리셋과 updatesTooLong은 모두 .reset 업데이트 그룹이 돼요. [5] [6]

UpdateMessageService는 완전한 형식, 조합 형식, 짧은 형식에 대해 groupUpdates를 호출해요. 짧은 메시지는 먼저 일반 updateNewMessage로 채워져요. 짧은 전송 확인은 updatePts만 내보내요. 그래서 확인 응답은 진행 상황을 전진시키지만 메시지 객체를 위조하지는 않아요. [5]

일반 RPC의 반환도 이 체인을 우회하지 않아요. 예를 들어 전송 후 처리 코드는 서버의 result를 stateManager.addUpdates(result)에 넘기고 ensurePeerHasLocalState를 덧붙여요. 투표 결과를 가져오는 응답도 똑같이 처리해요. 여기서는 반환된 업데이트의 합류만 설명해요. 전송의 재시도, 무작위 식별자, 오프라인 큐는 메시지 전송 파이프라인과 오프라인 작업 큐에서 다뤄요. [14] [15]

addUpdates는 호출 스레드에서 곧바로 분류하지 않아요. 비동기로 updateService를 호출해요. addUpdateGroups는 다시 같은 큐로 들어가요.

  • 큐 끝이 이미 그룹을 수집하는 중이면: 새 그룹을 기존 그룹에 이어 붙이고 그 연산의 실행 표시를 유지해요.
  • 그렇지 않으면: 대기 시간 0인 수집 연산을 덧붙여요.

이렇게 하면 짧은 시간에 쪼개져 들어오는 푸시의 트랜잭션 횟수가 줄어들고, 최종 정렬 기준은 바뀌지 않아요. [6]

이 큐는 네트워크를 막지 않아요. 구성과 네트워크 파싱은 신호 체인에서 실행될 수 있어요. 상태를 실제로 바꾸는 재생은 여전히 Postbox 트랜잭션으로 돌아와요. 동시성, Queue, Signal의 일반 모델은 리액티브와 동시성 모델을 참고하세요.

큐를 교체할 때도 보존 의미가 있어요. replaceOperations는 실행 중인 첫 항목을 버리지 않아요. 아직 실행되지 않은 항목 중에서 다음을 모아 두고, 새 pollDifference를 이 보존 항목들 앞이나 사이에 끼워 넣어요.

  • processUpdateGroups
  • 폴링 완료 구독자
  • 비동기 최종 상태
  • 이벤트
  • 커스텀 연산

그러면 차이 복구가 오래된 일반 처리를 앞지르면서도, 호출자가 기다리는 완료 콜백이 영영 사라지지 않아요. [6]

custom은 확장을 편하게 하는 데서 그치지 않아요. 동기화와 관련된 상태를 읽거나 바꿀 수 있는 Signal을 같은 인과 순서에 놓아요. 신호의 값과 오류는 내부 ValuePipe로 원래 호출자에게 전달되고, 큐는 그 완료만 기다려요. 외부 API의 비동기 결과가 업데이트 커밋과 분리되는 셈이에요. 대가는 오래 걸리는 커스텀 연산이 큐 뒤쪽 작업을 늦춘다는 거예요. (추론) [6]

커밋과 외부로 나가는 부수 효과도 일부러 나눴어요. processUpdateGroups는 먼저 트랜잭션 안에서 replayFinalState를 호출해요. 성공한 뒤에야 processEvents를 끼워 넣어요. processEvents가 입력 상태 관리자, 웹 구독자, 통화 세션, 알림 파이프, 읽음 확인을 갱신해요. 그래서 구독자가 이벤트를 받을 때는 이벤트가 가리키는 Postbox 내용이 이미 있어요. [6]

pollCompletion은 호출자에게 비우기 펜스(앞선 연산이 모두 비워졌음을 알려 주는 장치)를 제공해요.

  • 뒤에 연산이 더 있으면 자신을 큐 끝으로 미뤄요.
  • 이미 유일한 연산이면 help.test를 보내고, 응답이나 오류가 온 뒤에야 쌓아 둔 메시지 식별자를 전달해요.

동기화 정확성의 근원은 아니에요. “로컬에 커밋되었음”과 “그 이전의 네트워크와 큐 작업이 경계 하나를 넘었음”을 구분하는 인터페이스예요. [6]

큐의 실행 표시는 로컬 실행의 재진입만 해결해요. 네트워크 응답을 직렬화해 주지는 않아요. pollDifference가 요청을 보낸 뒤에도 늦게 도착한 푸시는 수집 큐로 들어갈 수 있어요. 그래서 차이 경로는 네트워크가 돌아온 뒤 시작 상태를 다시 대조해야 해요. 이 계층 구분이 operations 배열과 초기 상태의 동등 비교가 둘 다 필요한 이유예요. [6]

재생 한 번이 1초를 넘으면 관리자가 State 로그를 남겨요. 코드는 이 임계값을 타임아웃이나 취소 조건으로 쓰지 않아요. 성능 관측 지점일 뿐이에요. 네트워크 요청의 재시도는 retryRequest가 맡아요. 공백을 기다리는 2초와 채널 서버가 돌려주는 timeout은 서로 다른 계층의 시간 정책이므로 같은 요청 타임아웃으로 뭉뚱그리면 안 돼요. [6] [8]

검증 컨텍스트의 수명은 뷰 식별자에 묶여 있어요. 뷰가 해제되거나 태그가 맞지 않으면 updateView가 그 context를 삭제해 배치의 disposable을 해제해요. 검증 중인 메시지 식별자는 batchReferences에 등록되기 때문에, 새 프레임의 뷰가 같은 식별자에 대해 요청을 중복해서 보내지 않아요. 뷰의 변화가 네트워크 완료보다 빠를 때를 위한 중복 제거 조치예요. (추론) [10]

여기서 64개 배치 상한은 무효화된 채널 메시지의 뷰 검증에만 써요. getChannelDifference의 100개 요청 제한도 아니고, 메시지 히스토리 페이지 크기도 아니에요. 예약 메시지와 빠른 답장은 서로 다른 검증 함수를 쓰지만, 둘 다 previousPeerValidationTimestamps에 따라 같은 peer에 60초 창을 둬요. 이 숫자들을 각각의 코드 경로에 묶어 두면 성능을 조정할 때 다른 종류의 동기화 리듬을 잘못 고치는 일을 피할 수 있어요. [8] [10]

채널 푸시도 범용 UpdateGroup 흐름에 들어가지만, 그 상태 전진은 결국 공개 pts가 아니라 채널 상태에 반영돼요. updateChannelPts는 서버가 채널 진행 상황만 알려 주는 입력 형태예요. 채널 차이가 이를 로컬 메시지, 읽기 상태, 히스토리 경계로 변환해요. 공개 차이가 채널 차이를 대신하지는 않아요. 두 복구 인터페이스는 서로 다른 두 프로토콜 체크포인트에 대응해요. [1] [4] [8]

푸시가 도착하는 방식, 앱 확장, 여러 프로세스의 협력은 이 장의 범위가 아니에요. 이들은 결국 같은 종류의 업데이트 이벤트를 제공하거나 소비해요. 자세한 내용은 푸시, 확장 프로세스와 다중 프로세스 협업을 참고하세요.

설계상의 선택과 절충

Telegram은 전역 단일 시퀀스가 아니라 논리적 순서 도메인을 택했어요. 공개 채팅, 비밀 채팅, 채널은 독립적으로 진행할 수 있어요. 채널의 고빈도 이벤트가 계정 전체를 붙잡지 않아요. 대가는 클라이언트가 상태를 여러 벌 유지해야 하고, 복합 패킷 하나를 쪼갠 뒤 다시 조립해야 한다는 거예요. [1] [4]

먼저 버퍼링하고 나중에 가져오는 방식을 택했어요. 잠깐의 순서 뒤섞임은 2초만 기다려요. 공백이 계속될 때만 차이 인터페이스를 호출해요. 대가는 구멍이 생기면 일부 새 이벤트가 잠시 보이지 않는다는 거예요. 대안은 이어지지 않는 패킷마다 즉시 가져오는 것이지만, 그러면 네트워크 지터와 서버 부하가 커져요. (추론) [6]

네트워크 패킷을 파싱하면서 Postbox를 직접 고치지 않고, 가변 작업 영역과 연산 로그를 택했어요. 덕분에 초기 읽기, 검증, 커밋의 경계가 분명해져요. 대가는 AccountMutableState가 크고, 업데이트 코드가 연산 해석기와 작업 영역 필드를 계속 맞춰 두어야 한다는 거예요. [7] [12] [16]

채널 차이 과다는 채널의 로컬 메시지를 모두 비우지 않고, 무효화로 표시한 뒤 필요할 때 히스토리를 검증하는 방식을 택했어요. 캐시와 스크롤 경험이 유지돼요. 대가는 뷰 계층이 invalidatedPts, 홀, 배치 검증을 이해해야 한다는 거예요. [8] [10]

이 설계를 재사용하려면 서버가 단조 체크포인트와 권위 있는 차이 인터페이스를 제공할 수 있어야 해요. 프로토콜에 이벤트 타임스탬프만 있고 비교할 수 있는 시퀀스 위치가 없다면, 클라이언트는 중복, 지연, 누락을 안전하게 구분할 수 없어요. 이때는 클라이언트 큐에 재시도를 더하기 전에 프로토콜 계층에서 버전 번호나 커서부터 만들어야 해요. (추론) [1] [2]

작업 영역 패턴은 초기 스냅샷의 범위가 충분히 작아야 한다는 조건도 요구해요. Telegram은 데이터베이스 전체를 복사하지 않고 이번 회차 업데이트와 관련된 peer, 연관 메시지, 채널 상태만 수집해요. initialStateWithUpdateGroups가 그룹으로부터 이 집합들을 알아내요. 푸시 배치마다 메모리와 트랜잭션 읽기가 영향 범위에 따라 늘어나요. 대가는 의존 관계를 빠뜨리고 수집하면 최종 상태를 제대로 해석할 수 없다는 거예요. 그래서 새 업데이트 타입은 필요한 peer와 연관 메시지를 분명히 선언해야 해요. [7] [16]

사용하는 쪽에서 가장 중요한 경계는 Api.Updates 응답 지점에서 Postbox에 직접 쓰지 않는 거예요. 이 응답은 푸시와 중복될 수도 있고, 나중 트랜잭션이 이미 앞지른 스냅샷일 수도 있어요. 상태 관리자에게 일괄로 넘겨서 범위 검사, 초기 상태 검증, 트랜잭션 재생을 맡겨야 해요. 이 규칙은 UI가 시작한 질의가 돌려준 업데이트에도 똑같이 적용돼요. [6] [14] [15]

큐가 처리량 병목에 대한 유일한 답은 아니에요. Telegram은 독립 채널의 네트워크 복구를 병렬화하되, 병합 결과는 다시 정렬하고 단일 트랜잭션으로 커밋해요. 다른 클라이언트라면 병렬화에 알맞은 것은 공유 체크포인트가 없는 가져오기와 파싱이에요. 직렬화에 알맞은 것은 공유 커서의 전진, 눈에 보이는 부수 효과의 생성, 파생 상태의 영속화예요. 뒤의 두 부류 작업을 잘못 병렬화하면 멱등성 로직이 검증하기 어려운 트랜잭션 간 제약이 돼요. (추론) [6]

각 시간 상수도 범위를 반영해요. 이들을 전역 재시도 간격 하나로 통일하면 안 돼요.

  • 2초: 공개 공백 이후 다시 수집하기를 기다리는 시간이에요.
  • 1초: 채널 지속 폴링의 추가 지연이에요.
  • 30초: 채널이 임대를 주지 않았을 때의 기본 완료 지연이에요.
  • 60초: 예약 메시지와 빠른 답장 검증의 peer 수준 스로틀이에요.
  • 64: 채널 히스토리 검증의 배치 크기예요.
  • 100: 프로덕션 채널 차이 요청의 제한이에요.
