macOS 알림 동작과 Dock 배지

TelegramSwift의 알림 답장과 읽음 환류, Dock 미읽음 공식, 앱 잠금 경계를 추적해요.

시스템 설계 · 검증과 보충 · 보충 40 · 도표 1 · 코드 발췌 3 · 인용 23 · 소스 기준선: TelegramMessenger/Telegram-iOS@f1dd7a2d, overtake/TelegramSwift@579cebbf

검증 대상: macOS 클라이언트의 시스템 계층

미검증 사항:

  • 실제 macOS 잠금 화면 환경에서 리액션 알림이 유지하는 답장 동작을 실행할 수 있는지는 미검증이에요.

알림 동작의 실제 환류

알림 동작은 macOS 알림 API 버전에 따라 경로가 달라요. 15장의 알림 개요는 여전히 유효하지만, 동작 경로는 버전별로 나누어 설명해야 해요.

이 보충에서 읽은 telegram-ios 서브모듈 작업 트리는 Gitlink(서브모듈이 가리키는 커밋)가 가리키는 a24bbe45f9861f736a79916a50898512f751e0dc에 있어요. 그래서 아래의 코어 호출은 TelegramSwift 고정 fork의 것으로 바로 볼 수 있어요.

macOS 10.14 이후의 새 알림 API UNUserNotificationsNew는 동작을 이렇게 다뤄요.

  • 등록하는 동작: 식별자 reply인 텍스트 입력 동작 하나뿐이에요.
  • 기본 클릭: 대화로 이동해요.
  • 알림 닫기: 콜백이 곧바로 끝나요.

소스에는 별도의 “읽음으로 표시” UNNotificationAction이 등록되어 있지 않아요. [1][2]

답장 동작은 이 순서로 처리돼요.

  1. 알림 페이로드에서 reply 메시지 ID와 accountId를 꺼내요.
  2. activeAccounts에서 그 계정을 찾아요.
  3. 코어의 공개 함수 enqueueMessages를 호출해요.

이 과정은 현재 키 윈도우에 의존하지 않고, 채팅 입력창도 거치지 않아요. 토픽 메시지라면 코드는 threadId를 알림 메시지 ID로 설정해요. 개인 채팅이 아닌 경우에는 그 메시지를 답장 대상으로 삼아요. [1]

[1]

고정 fork의 enqueueMessages는 선택적 미디어 변환을 먼저 처리한 다음, 해당 계정의 postbox.transaction 안에서 큐에 넣어요. 그래서 알림 답장은 먼저 로컬의 전송 대기 메시지가 되고, 네트워크 전송은 이후의 전송 파이프라인이 맡아요. 알림 delegate가 RPC를 직접 보내는 게 아니에요. [3]

구형 NSUserNotificationCenter 경로는 달라요. 사용자가 alert를 닫을 때 didDismissAlert가 알림의 메시지 ID와 타임스탬프로 applyMaxReadIndexInteractively를 호출해요. 소스에서 볼 수 있는 “읽음으로 표시” 동작이 바로 이거예요. 반면 구형 알림을 클릭할 때의 didActivate는 이미 전달된 알림을 제거할 뿐, 메시지를 읽음으로 만들지는 않아요. [4]

여기에는 다중 계정 경계의 빈틈이 있어요. SharedNotificationBindings가 읽음 클로저를 설치할 때는 self.contextValue?.context에 대해서만 engine.messages.applyMaxReadIndexInteractively를 호출해요. 클로저는 알림의 accountId를 읽지 않아요. 그래서 구형 API의 읽음 동작은 알림을 보낸 계정이 아니라 현재 메인 화면의 계정에 적용돼요. 원래 장이 말한 알림 계정별 라우팅을 증명하지 못해요. [5]

코어의 읽기 동작은 해당 계정의 Postbox 트랜잭션에서 applyInteractiveReadMaxIndex를 호출해요. 일반 클라우드 대화에서는 이어서 AccountStateManager에 읽음 상태 동기화를 알려요. [6]

이 도표의 뒷부분(alert 닫기에서 읽음 색인 적용까지)은 구형 알림 API에만 적용돼요. 새 API의 dismiss 분기에는 메시지를 읽는 호출이 없어요. [2][4][6]

Dock 배지 공식과 갱신 시점

Dock 배지는 모든 계정의 합계가 아니라 계정 하나의 미읽음 수만 보여 줘요. TabBadgeItem이 만드는 GlobalBadgeNode에는 dockTile: true가 전달되고, 이 노드는 자기 context.account의 renderedTotalUnreadCount를 구독해요. 현재 호출은 collectAllAccounts: true를 넘기지 않아서, 이 프로세스에 있는 모든 계정이 아니라 단일 Account의 Postbox를 읽어요. 계정 메뉴의 TabAllBadgeItem만 다중 계정 합산을 쓰고, Dock에는 쓰지 않아요. [7][8]

단일 계정의 원시 카운트는 다음과 같아요.

C = Sroot.count(style.category, category.statsType, K)

  • Sroot: 루트 채팅 그룹의 ChatListTotalUnreadState예요.
  • K: 설정의 태그 집합이에요.
  • C: 채팅 수 또는 메시지 수예요.

각 설정은 이렇게 읽어요.

  • style이 raw이면 absoluteCounters를, filtered이면 filteredCounters를 읽어요.
  • category가 chats이면 미읽음이 있는 대화 수를, messages이면 미읽음 메시지 수를 누적해요.
  • 카운트 함수는 K에 있는 각 태그의 카운트를 하나씩 누적해요.

[9][10]

기본 설정은 filtered, chats, all, 배지 활성화예요. 기본 all에는 연락처, 비연락처, 그룹, 봇, 채널이 들어가요. 그래서 채널은 기본으로 집계돼요. 알림 환경설정 화면의 “Include Groups”와 “Include Channels”는 각각 .group과 .channel을 추가하거나 빼요. 음소거된 대화를 포함하는 독립 스위치는 없어요. [11][12]

음소거는 K가 아니라 style에서 처리돼요. TelegramPeerNotificationSettings.isRemovedFromTotalUnreadCount는 .muted에 대해 참을 반환해요. 채팅 색인을 갱신할 때 이 값이 참이면 코드는 필터링된 카운트의 메시지 수와 채팅 수를 모두 0으로 만들어요. 그래서 기본 filtered는 음소거된 대화를 세지 않아요. 표시 스타일을 raw로 바꾸면 절대 카운트는 여전히 음소거된 대화를 유지해요. [13][14]

보관함은 이 Dock 공식에 들어가지 않아요. 렌더러는 루트 그룹의 총 미읽음을 명시적으로 읽고, 코어는 보관함을 다른 Namespaces.PeerGroup.archive로 매핑해요. 채팅 색인도 groupId별로 totalStates를 따로 유지해요. 그래서 보관함 설정 항목이 없고, “기본으로 보관함을 포함”하지 않아요. [9][15][16]

최종적으로 기록되는 Dock 문자는 다음과 같아요.

  • badgeEnabled가 거짓이면 빈 값이에요.
  • 그렇지 않고 해당 계정의 카운트가 0보다 크면 십진수 문자열이에요.

노드는 badgeEnabled를 한 번 더 확인하고, 같은 문자열을 상태 표시줄 아이콘 생성 흐름에도 써요. combineLatest는 미읽음 뷰, 공유 알림 설정, 폴더 설정을 구독해요. 그래서 아래 변화가 모두 다시 계산되어 NSDockTile.badgeLabel에 바로 기록돼요. [7][9]

  • 메시지 읽음 또는 도착
  • 음소거 상태 변화
  • 채널이나 그룹 스위치 변화
  • 카운트 범주 변화
  • 배지 전체 스위치 변화

[7]

chatListFolderSettings의 사이드바 조건은 노드 자신의 total만 0으로 만들어요. dockText는 그대로 둬요. 그래서 이 조건이 숨기는 건 탭 배지이고, Dock 숫자가 아니에요. [7]

로컬 패스코드, Touch ID, 잠금 화면 가시성

로컬 패스코드는 두 곳에서 경계 역할을 해요. 하나는 콜드 스타트이고, 다른 하나는 실행 중의 자동 잠금이에요.

콜드 스타트에서 AppDelegate는 AppEncryptionParameters.decrypt()가 키와 솔트를 돌려준 뒤에야 ValueBoxEncryptionParameters를 구성하고 계정을 시작해요. 패스코드가 실패하면 콜드 스타트 잠금 화면 컨트롤러를 표시해요. 그래서 패스코드는 윈도우 가림막만이 아니라 데이터베이스 암호화 파라미터를 복원하는 일에도 관여해요. [17]

실행 중의 자동 잠금은 10초마다 검사해요. 기본 타임아웃은 300초예요. 포커스를 잃은 뒤의 경과 시간과 SystemIdleTime을 함께 비교해요. 수동 Command L도 같은 잠금 흐름을 요청해요. 잠글 때 관리자는 이렇게 해요.

  • 인스턴트 페이지와 갤러리를 닫아요.
  • 오디오를 일시 중지해요.
  • 오버레이를 표시해요.
  • 각 계정 윈도우의 SplitView를 숨겨요.

정상적인 잠금 경로에서 로그아웃을 호출하거나 계정 객체를 해제하지는 않아요. [18][19][23]

Touch ID는 이 앱 잠금 계층만 해제해요. 설정 화면은 LAContext.canUseBiometric이 참일 때만 스위치를 제공해요. 해제 컨트롤러는 먼저 .applicationPolicy를 쓰고, 실패하면 .deviceOwnerAuthentication으로 폴백해요. 성공하면 doneValue를 설정하고 잠금 화면 컨트롤러를 닫을 뿐이에요. Telegram에 다시 로그인하지 않고, 클라우드의 2단계 인증도 바꾸지 않아요. [18][20]

[20]

잠긴 동안에는 메인 윈도우의 내용이 보이지 않아요. 채팅 컨트롤러는 canRead를 잠금 상태의 반전으로 취해요. 그래서 가려진 채팅이 여전히 화면에 있다는 이유로 알림을 지우거나 읽음 위치를 진행시키지 않아요. [21]

시스템 알림에는 더 세밀한 경계가 있어요. screenIsLocked가 참이면 일반 메시지 알림은 이렇게 바뀌어요.

  • 제목은 앱 이름으로 바꿔요.
  • 본문은 일반적인 잠금 미리보기로 바꿔요.
  • 부제목, 이미지, 소리는 제거해요.

Dock 배지 계산은 잠금 상태를 읽지 않아서 미읽음 숫자는 여전히 보여요. [7][22]

그런데 리액션 알림에는 소스로 증명되는 예외가 있어요. 잠금 분기가 먼저 제목을 앱 이름으로 설정한 뒤, reaction 분기가 제목을 메시지가 속한 대화 이름으로 다시 써요. 잠금 분기는 여전히 본문과 이미지를 숨겨요. 그룹 경로는 canSendMessage로 처음의 답장 불가 상태를 다시 쓰기도 해요. 알림 delegate 자체는 답장하기 전에 isLocked를 확인하지 않아요.

따라서 추정: 시스템 알림 센터가 잠금 화면에서 이 동작을 실행하도록 허용한다면, 애플리케이션 코드는 로컬 패스코드 문턱을 더 이상 걸지 않아요. 실제 macOS 버전이 이런 상호작용을 허용하는지는 런타임에서 검증하지 않았어요. [2][22]

  • 패스코드와 Touch ID 소절 481–483행, 원문 “Touch ID의 활성화 여부, 키가 어디에 저장되는지, 잠금이 디스크 데이터베이스를 보호하는지는 모두 미검증이에요”. → “소스에서 확인되는 건 이래요. 생체 인식을 쓸 수 있을 때 Touch ID 스위치가 표시되고, LocalAuthentication으로 오버레이를 해제해요. 콜드 스타트에서는 패스코드로 ValueBox 암호화 파라미터를 복원해야 해요. 실행 중의 잠금은 윈도우 내용을 숨기고 자동 읽음을 억제하지만 로그아웃하지는 않아요. 잠금 화면 알림은 보통 메시지 내용을 숨기지만, 리액션 알림은 대화 제목을 노출해요.”로 고치자고 제안해요. 이 수정은 잠금 경계 항목을 해결해요. 결과는 부분 해결이에요. 잠금 화면 알림 동작에 대한 macOS의 런타임 권한 부여는 여전히 미검증이에요. [17][18][20][21][22]

  • 설계 트레이드오프 497행, 원문 “시스템 콜백은 모두 계정 신원을 먼저 가져온 뒤 코어로 들어가므로, 다중 계정에서 알림 조작이 현재 보이는 계정으로 잘못 전달되는 것을 피해요”. → “답장 알림”으로 한정하자고 제안해요. 구형 alert의 읽음 클로저는 accountId로 계정을 고르지 않으니 이 포괄적 결론은 정정이 필요해요. 결과는 원문과 모순돼요. [5]
