Telegram은 전송을 먼저 디스크에 기록하고, 나중에 실행하며, 서버 결과로 고쳐 쓸 수 있는 로컬 트랜잭션으로 이해해요. 흐름은 이래요.

  1. 사용자가 전송을 누르면 클라이언트는 먼저 Postbox(로컬 저장소)에 Unsent 플래그가 붙은 메시지를 삽입해요.
  2. 이어서 PendingMessageManager(전송 대기 메시지를 실행하는 manager)가 미전송 집합을 관찰하고, 미디어를 업로드하고, RPC를 구성해요.
  3. 같은 저장 레코드를 서버 메시지로 고쳐 써요.

덕분에 인터페이스는 네트워크를 기다리지 않아도 되고, 프로세스가 재시작되어도 전송 의도가 사라지지 않아요. [1] [2]

여기서 핵심은 messages.sendMessage 호출 한 번을 비동기 함수로 감싸는 것이 아니라, 로컬 메시지, 업로드 상태, 요청 의존성, 서버 확인을 복구 가능한 단계로 나누는 거예요. 영속화된 메시지가 전송 큐의 사실상 원천이에요. 메모리 안의 manager는 현재 프로세스의 실행기일 뿐이에요. Postbox의 하위 트랜잭션과 뷰 메커니즘은 Postbox 스토리지 엔진에서 별도로 다뤄요.

로컬 메시지가 네트워크보다 먼저

로컬 생명주기를 메시지 정체성에 담은 네임스페이스

전송 파이프라인이 가장 먼저 풀어야 할 난제는 이거예요. 서버가 아직 메시지 번호를 배정하지 않았는데도, 아래가 가능한 메시지가 채팅 기록에 즉시 하나 나타나야 해요.

  • 정렬
  • 답장
  • 삭제
  • 재시작 후 복구

Telegram은 outbox 테이블(보낼 메시지만 모아 두는 테이블)을 만들지 않고, 작성 중인 발신 메시지를 일반 StoreMessage로 메시지 기록에 쓰며 MessageId의 namespace로 그 생명주기를 구분해요.

Namespaces.Message는 메시지의 생명주기를 이렇게 나눠요.

  • 일반 클라우드 메시지: Cloud
  • 로컬 전송 대기 메시지: Local
  • 예약 메시지: ScheduledLocal과 ScheduledCloud의 두 단계가 더 있어요.
  • 빠른 답장: 독립된 로컬 및 클라우드 네임스페이스를 사용해요.

allLocal은 로컬에 있을 수 있지만 아직 일반 클라우드 메시지와는 같지 않은 네임스페이스를 한데 묶어요. [3]

submodules/TelegramCore/Sources/SyncCore/SyncCore_Namespaces.swift 4–31행 발췌.

enqueueMessages의 공개 진입점은 먼저 계정 수준의 미디어 변환기가 기회적으로 처리하게 한 다음 postbox.transaction에 들어가요.

  • 같은 트랜잭션 안에서 여러 메시지를 삽입할 수 있으므로, 앨범, 전달, 텍스트가 반쯤 보이고 반쯤 안 보이는 상태에 놓이지 않아요.
  • inline 스티커를 먼저 미디어 라이브러리에 저장해요.
  • 답장 속성, 텍스트 엔티티, 자동 삭제 속성, 채팅 컨텍스트에 필요한 정보를 채워요. [4]

일반 전송 대기 메시지마다 64비트 난수가 하나씩 만들어져요. 이 난수는 아래 두 곳에 함께 기록돼요.

  • OutgoingMessageInfoAttribute.uniqueId: 나중에 MTProto API의 randomId 필드로 들어가 updateMessageID와 매칭돼요.
  • StoreMessage.globallyUniqueId: addMessages가 로컬에서 배정한 MessageId를 반환하게 해, 호출자가 방금 삽입한 레코드를 즉시 찾을 수 있게 해요. [1] [5]

submodules/TelegramCore/Sources/PendingMessages/EnqueueMessage.swift 942–958행 발췌.

각 식별자의 역할은 달라요.

  • MessageId: 로컬 저장 인덱스로, peer, namespace, 정수 id로 구성돼요.
  • randomId: 전송 멱등성을 위한 연관 키예요.
  • globallyUniqueId: 삽입 반환 매핑에 쓰이는 값이며, 서버 id로 오해해서는 안 돼요.

서버의 최종 id는 확인 결과에서만 나타나요.

앨범에는 여러 미디어가 로컬에서 먼저 같은 groupingKey를 공유해야 해요. 그룹 키는 이렇게 정해져요.

  • 직접 전송할 때: EnqueueMessage.message가 호출자가 준 localGroupingKey를 받아요.
  • 전달할 때: forwardGroupingKey가 원본 메시지의 그룹 키와 로컬 딕셔너리로 대상 그룹 키를 생성하거나 재사용해요.

저장할 때 모든 StoreMessage가 이 키를 보관하므로, manager는 전송 대기 중인 구성원을 sendMultiMedia 요청 한 번으로 묶을 수 있어요. [2] [6]

예약과 빠른 답장은 전송 시점에 덧붙는 불리언 값이 아니라 서로 다른 로컬 네임스페이스예요. 코드는 OutgoingScheduleInfoMessageAttribute를 검사해요.

  • 예약: “상대가 온라인일 때 전송”이면서 현재 presence가 이미 조건을 만족할 때가 아니라면 ScheduledLocal을 선택하고 타임스탬프를 예약 시각으로 설정해요.
  • 빠른 답장: QuickReplyLocal을 선택하고 타임스탬프를 0으로 둬요.
  • 대응하는 네임스페이스가 없으면: 이 속성들을 제거해, 일반 메시지가 무효한 예약 메타데이터를 달고 다니지 않게 해요. [2]

마지막으로 트랜잭션이 transaction.addMessages를 한 번에 호출한 뒤, 각각의 난수 globallyUniqueId로 로컬 id를 조회해요. 쓰기 동작이 Postbox의 unsent 뷰를 구동하므로, manager는 UI가 명시적으로 호출해 주지 않아도 돼요. 이 흐름이 중요해요.

  • UI는 의도를 써요.
  • 저장소의 변경이 실행기를 깨워요.
  • UI가 네트워크 작업을 쥐고 있지 않아요. [5]

요청을 만들 때 나중에 들어가는 입력, 속성

전송 대기 메시지는 텍스트와 첨부만 담은 DTO(데이터를 나르기만 하는 객체)가 아니에요. enqueueMessages는 아래 정보를 MessageAttribute로 표현해요.

  • 답장 대상
  • 인용
  • thread
  • 전송 신원
  • 무음 전송
  • 엔티티
  • 미디어 참조
  • 열람 후 자동 삭제
  • 유료 메시지와 효과 등

이후 manager가 저장된 메시지에서 이 속성들을 다시 읽어 API flags와 매개변수를 구성해요. 덕분에 프로세스가 강제 종료된 뒤에도 메모리 클로저에 의존하지 않고 전체 요청을 재구성할 수 있어요.

여기에는 대가도 따라요. 속성 타입이 로컬 비즈니스 모델과 TL 매개변수 모델 사이의 경계를 떠맡아요. 전송 기능을 하나 추가할 때 엔지니어는 아래를 모두 함께 확인해야 해요.

  • 큐 삽입
  • 콘텐츠 업로드
  • 단일 및 그룹 요청 구성
  • 서버 결과 매핑
  • 실패했을 때 속성이 여전히 재시도 가능한지

UI 모델에만 필드를 추가하면 재시작 후 전송의 의미가 사라져요. (추정)

PendingMessageManager의 실행 상태 머신

Account는 MessageMediaPreuploadManager를 만든 뒤, 이를 아래와 함께 PendingMessageManager에 주입해요.

  • 네트워크
  • Postbox
  • AccountStateManager
  • 입력 활동 관리자
  • 미디어 참조 재검증기

manager는 자체 Queue를 하나 가지며, MessageId를 키로 하는 messageContexts를 보유해요. 상태를 별도의 데이터베이스 레코드로 쓰지 않고 미전송 메시지 뷰로부터 메모리 컨텍스트를 재구성해요. 전송 의도 자체는 여전히 메시지 레코드 안에 있어요. [7]

각 context(메시지마다 메모리에 두는 실행 상태)는 아래를 보관해요.

  • upload, send, activity, postpone의 네 disposable(취소할 수 있는 작업 핸들)
  • 현재 thread
  • 콘텐츠 범주
  • 진행률
  • 실패 원인
  • 일회성 강제 재전송 표식
  • 상태 구독자

상태 enum은 아래 단계를 분명하게 구분해요.

  • 정보 수집
  • 업로드 대기열 진입
  • 업로드 중
  • 앨범 구성원 대기
  • 전송 게이트 대기
  • 전송 중
  • 새 토픽 생성 등 [8]

submodules/TelegramCore/Sources/State/PendingMessageManager.swift 27–58행 발췌.

updatePendingMessageIds는 manager의 직렬 queue 안에서 집합 차분을 구해요.

  • 새로 추가된 id: 정렬된 뒤 beginSendingMessages로 보내져요.
  • 삭제된 id: context를 none으로 표시하고, upload, send, activity, postpone disposable을 취소한 다음 진행률 구독자에게 알려요.

이 취소 경로는 사용자가 업로드 중에 메시지를 삭제할 때를 처리하며, 제거된 앨범 구성원이 계속 네트워크 전송을 일으키는 일도 막아요. [9]

전역 동시성 임계값이 아니라 순서 있는 업로드

미디어 업로드가 가장 먼저 해결하는 것은 같은 대화에서 연속된 메시지의 직관적인 순서 문제예요. 규칙은 이래요.

  • canBeginUploadingMessage: 텍스트에는 곧바로 true를 반환해요. 미디어에 대해서는 MessageId로 정렬하고, 같은 peer에 더 작은 id가 있고 그 상태가 uploading이면 시작을 거부해요.
  • updateWaitingUploads: 매번 이 peer의 대기 항목 중 조건에 맞는 첫 번째 항목만 시작해요.

따라서 코드가 구현하는 것은 peer별로 앞선 미디어가 뒤를 막는 방식이지, 고정된 전역 병렬도 상수가 아니에요. [10]

submodules/TelegramCore/Sources/State/PendingMessageManager.swift 576–595행 발췌.

이 선택은 처리량을 내주고 국소적인 순서와 더 추론하기 쉬운 실패 복구를 얻어요.

  • 서로 다른 peer의 미디어는 이 판정에서 서로를 막지 않아요.
  • 텍스트는 업로드 제한을 우회해, 첨부가 대기 중일 때도 전송될 수 있어요.
  • 앨범에는 다른 규칙이 있어요. dataForPendingMessageGroup은 구성원 중 하나라도 아직 수집 중이거나, 업로드를 기다리거나, 업로드 중이면 빈 값을 반환하며, 전원이 waitingToBeSent에 도달해야 함께 제출해요. [11]

실패, 재시도, 재전송, 편집

업로드 signal의 실패와 전송 RPC의 실패는 모두 메시지를 Failed로 갱신해요. 식별 가능한 오류는 아래로 매핑되어 이 peer의 실패 구독자에게 푸시돼요.

  • flood
  • 공개 그룹 발언 금지
  • 미디어 제한
  • 슬로우 모드
  • 과다한 예약 메시지
  • 음성 비활성화
  • 너무 빠른 전송
  • 비 Premium 제한

파일 참조 만료는 특수한 경우예요. context는 forcedReuploadOnce를 한 번만 허용하고 이어서 콘텐츠 준비를 다시 실행해요. 두 번째에도 만료되면 그때 실패로 처리해, 무한 재업로드를 피해요. [24]

“재전송”은 실패 플래그를 지우고 원래의 로컬 레코드를 재사용하는 것이 아니에요. resendMessages는 이렇게 처리해요.

  1. 실패한 발신 메시지의 텍스트, 미디어, 답장, 전달 원본, 보존 가능한 속성을 읽어요.
  2. 같은 enqueueMessages를 호출해 새 메시지를 만들어요.
  3. 그다음 옛 로컬 메시지를 삭제해요.

그래서 새 메시지는 새 난수 id를 받고 일반 상태 머신에 다시 들어가요. [25]

편집은 PendingMessageManager의 미전송 큐에 들어가지 않아요. requestEditMessage는 이렇게 움직여요.

  • 새 미디어가 필요하면 mediaContentToUpload와 사전 업로드 manager를 재사용하며, 파일 참조가 무효이면 전체를 forceReupload로 한 번 재시도해요.
  • 예약 메시지에는 scheduleDate와 반복 주기를, 빠른 답장에는 shortcut id를 설정한 뒤 messages.editMessage를 호출해요.

반환되는 updateEditMessage, updateNewMessage와 channel 변형은 transaction 안에서 서버의 StoreMessage로 기존 id를 갱신해요. [26]

예약 메시지는 정상적으로 큐에 들어갈 때 ScheduledLocal을 사용하고, 확인되면 ScheduledCloud가 돼요. 사용자가 즉시 전송을 선택하면 클라이언트는 이렇게 처리해요.

  1. PendingMessageActionType.sendScheduledMessageImmediately를 기록해요.
  2. 백그라운드에서 동작 뷰를 관찰하다가 messages.sendScheduledMessages를 호출해요.
  3. RPC가 오류를 내든 말든, 이 worker는 이후 이 동작에 대응하는 로컬 예약 메시지를 삭제해요.

코드는 이 경로에서 자동 재시도하는 동작을 남겨 두지 않아요. 이 방식은 제품 차원에서 명시적으로 평가해야 하며, 모든 영속 동작이 최소 한 번의 원격 실행과 동등하다고 가정해서는 안 돼요. [27]

비밀 채팅의 전송과 삭제는 독립된 상태와 암호화 동작을 따라요. 이 장은 클라우드 메시지 큐만 다뤄요. 비밀 채팅의 종단 간 암호화 의미론은 종단 간 암호화와 로컬 보안을 참고해요.

일반 클라우드 삭제와 채널 삭제는 모두 id 100개씩 나누어 처리해요. 성공하면 pts 또는 채널 pts를 stateManager에 넘겨요. 하지만 네트워크 오류는 nil로 catch되어 signal은 여전히 완료되고, 바깥에서도 작업 로그 entry를 그대로 제거해요.

이는 이 삭제 worker의 이 경로가 “실패하면 성공할 때까지 큐에 남는” 범용 재시도 큐가 아니라는 뜻이에요. 이것은 “최선을 다해 요청한 뒤 로컬 삭제를 마치는” 구현이에요. 이를 신뢰할 수 있는 원격 삭제라고 부르면 실제 의미론을 가리게 돼요. [31]

범용 영속 작업 로그 패턴

메시지 전송은 미전송 메시지 뷰를 큐로 활용해요. 삭제, 고정 동기화, 읽음 동기화, 이모지 동기화와 많은 상태 작업은 또 다른 범용 메커니즘, 곧 peer operation log(peer마다 쌓는 작업 기록)를 사용해요.

이들의 공통 문제는 이래요. 사용자 상호작용이 먼저 로컬 상태를 바꾸지만, 원격 부수 효과는 네트워크가 가능해질 때 이어져야 하고 앱을 재시작한 뒤에도 복구되어야 해요.

각 PeerOperationLogEntry는 아래를 포함해요.

  • peer
  • tag
  • tag별 로컬 일련번호
  • 선택적 merged index
  • PostboxCoding payload

두 연산의 동작은 이래요.

  • addEntry: local index를 자동으로 배정하고, merged index가 요청되면 전역 merged 인덱스에 기록한 뒤 append 연산을 발행해요.
  • removeEntry: 주 테이블과 merged 인덱스에서 삭제하고 remove 연산을 발행해요. [32]

PeerMergedOperationLogView는 tag와 merged index에 따라 한도가 있는 순서 있는 entry를 출력해요. append, remove, 내용 갱신을 증분으로 replay해요. 그래서 worker는 반응형 뷰 하나만 구독하면 되고 데이터베이스를 폴링하지 않아요. 작업 생산자, Postbox commit, 소비자의 깨어남이 같은 트랜잭션 알림 체인에 연결되어 있어요. [33]

아래 도표는 영속 작업이 로컬 변경에서 백그라운드 실행에 이르는 일반적인 과정을 보여 줘요.

고정된 채팅의 동기화는 큐 삽입 시의 중복 제거를 보여 줘요. addSynchronizePinnedChatsOperation은 이렇게 처리해요.

  1. 먼저 이 group의 tag에 대응하는 기존 entry를 열거해 가장 오래된 previousItemIds를 남겨요.
  2. 옛 entry를 삭제해요.
  3. 새 entry를 하나 추가해요.

이는 여러 번의 부분적인 드래그를 “원래의 원격 순서에서 현재의 로컬 순서로”라는 한 번의 동기화로 접는 것이며, 드래그마다 하나씩 전송하는 것이 아니에요. [34]

대응하는 managedSynchronizePinnedChatsOperations도 view limit 10으로 구독해요.

  • peer마다 하나씩만 동시에 처리해요.
  • 같은 가져가기 패턴(트랜잭션에서 entry를 가져가는 방식)을 호출해요.
  • 완료되면 entry를 삭제하고, 추가로 2초를 지연한 뒤 signal을 시작해요.

실제 동기화 함수는 getPinnedDialogs에 retryRequestIfNotFrozen을 사용해요. 여기서 “재시도”는 구체적인 operation의 요청 체인에서 구현되며, operation log가 자동으로 제공하는 보장이 아니에요. [35]

managedSynchronizePeerReadStates는 마찬가지로 중요한 또 다른 변형이에요.

  • peer operation log를 재사용하지 않고 전용 synchronizePeerReadStatesView를 구독해요.
  • currentState, activeOperations, pendingOperations의 세 딕셔너리를 유지해요.
  • 같은 peer에 대해 실행 중에 다른 상태가 또 나타나면 마지막 pending 작업만 남겨요.
  • 완료되거나 오류가 나면 active를 제거하고 다시 update해요.

이는 peer별로 병합되는 최신 상태 동기화이며, 항목마다 순서를 보존해야 하는 삭제 로그에는 맞지 않아요. [36]

엔지니어링 설계에 주는 시사점은 부수 효과에 따라 큐의 의미론을 먼저 골라야 한다는 거예요.

  • 유실되어서는 안 되고 순서가 있는 의도: 메시지 레코드나 operation log가 맞아요.
  • 마지막 상태만 필요한 동기화: per-peer 덮어쓰기 큐가 맞아요.

둘을 섞어 쓰면 RPC가 중복되거나, 오래된 상태가 새 상태를 덮거나, 무의미한 오프라인 적체가 생길 수 있어요. (추정)

macOS 클라이언트는 submodules/telegram-ios를 통해 overtake/Telegram-iOS fork를 가리켜요. 이 submodule은 로컬 gitlink에서 a24bbe45f9861f736a79916a50898512f751e0dc로 고정되어 있으며 직접 검증했어요. 이 fork는 아래를 유지해요.

  • Unsent와 uniqueId가 붙은 큐 삽입
  • 같은 peer의 미디어 업로드 정렬
  • randomId 수신 확인 매핑 [37] [38] [39] [40]

이 장은 관련 단락에 입력 게이트와 요청 매개변수의 알려진 차이를 표시해 두었으며, 나머지 업스트림 코드 단락을 그대로 fork의 사실로 적어서는 안 돼요. macOS fork 장별 검증 (01–07장) macOS 앱 계층의 차이는 macOS 클라이언트의 시스템 계층을 참고해요.

설계 트레이드오프

Telegram은 “메시지가 곧 큐”를 선택했어요. 그래서 사용자가 보는 전송 대기 항목, 실패 항목, 재전송 가능한 항목이 모두 같은 메시지 기록 모델의 일부예요. 이는 오프라인 복구와 UI 일관성을 단순하게 만들지만, 새 전송 기능마다 아래를 요구해요.

  • 직렬화 가능한 속성 표현을 완전하게 갖출 것
  • 결과 매핑이 local과 cloud namespace를 신중하게 유지할 것

peer별 미디어 직렬화와 앨범 전원 준비는 순서 뒤바뀜과 부분 앨범의 복잡도를 낮추지만, 같은 채팅 안에서 큰 파일 뒤에 오는 항목의 처리량을 희생할 수 있어요.

비밀 채팅이 아닌 채팅의 보정하지 않은 원형 비디오만이 녹화 중에 실시간 업로드 context를 공유해 녹화 완료 후의 지연을 줄일 수 있으며, 음성 녹음과 자르거나 이어 붙인 원형 비디오에는 이 경로가 없어요. 이 공유 메커니즘은 여전히 아래 비용을 들여요.

  • 구독 카운트
  • 1초 유예 후 취소
  • 생명주기 관리 [10] [14] [45] [48]

음성 녹음과 사전 업로드

작업 로그는 로컬 변경과 백그라운드 부수 효과를 분리하고, 고정 같은 고빈도 작업에 병합 진입점을 제공해요. 하지만 작업 로그가 자동으로 신뢰할 수 있는 전송 계층인 것은 아니에요. 삭제 worker는 오류를 삼킨 뒤 항목을 제거하는 반면, 고정 동기화는 구체적인 요청 체인에서 재시도해요. 실패를 보존할지, 병합할지, 보상할지, 명시적으로 강등할지는 제품과 백엔드의 의미론이 정해야 해요. [31] [35]

미검증 사항

  • 음성 미리듣기를 삭제한 뒤 초안 LocalFileMediaResource의 디스크 바이트를 MediaBox가 언제 회수하는지는 미검증이에요. [49]
  • 원형 비디오에서 discardVideo를 호출한 뒤 컨트롤러와 노드가 모든 표시 경로에서 언제 소멸하는지는 미검증이에요. 따라서 실시간 업로드의 중단을 취소 이벤트의 동기적 보장으로 적어서는 안 돼요. [14] [50]
