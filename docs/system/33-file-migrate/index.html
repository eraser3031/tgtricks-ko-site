FILE_MIGRATE의 최후 대비책(폴백) 경로

고정 커밋에서 파일 마이그레이션 오류는 범용 데이터 센터 전환이나 새 DC에서의 재전송을 일으키지 않아요.

검증 대상: 인증 키와 다중 데이터 센터

파일 마이그레이션의 실제 결론

이 보충은 「인증 키와 다중 데이터 센터」 장의 마이그레이션, 미디어, 권한 부여 부분만 보완해요. 센터 간 키와 권한 부여 토큰의 기본 메커니즘은 여전히 그 장을 참고하세요.

결론부터 말하면, 업스트림 고정 커밋 f1dd7a2dbd02cbbf513e75d5695d8d36d1cf5838에는 FILE_MIGRATE_X에 대한 클라이언트 폴백 경로가 없어요. 구체적으로는 이래요.

  • MtProtoKit은 RPC 오류를 범용 MTRpcError로 해석해요.
  • TelegramCore의 V1, V2 다운로드 및 업로드 경로는 어느 것도 오류 텍스트에서 대상 DC(데이터 센터)를 꺼내지 않아요.
  • 새 worker를 만들지 않고, 권한 전이(한 DC에서 받은 권한을 다른 DC로 옮기는 일)도 일으키지 않아요.
  • 새 DC에서 원래의 upload.getFile, upload.saveFilePart, upload.saveBigFilePart 요청을 재전송하지도 않아요. [4] [5]

이 결론은 Download.swift에 문자열 매칭이 없다는 사실만으로 나온 게 아니에요. MTInternalMessageParser는 오류 코드와 TL 문자열을 읽은 뒤 곧바로 MTRpcError를 구성해요. 이 계층에는 마이그레이션 유형 열거형도, DC 선택 로직도 없어요.

[4]

303 FILE_MIGRATE_X는 MtProtoKit 안에서 목적지 DC를 고쳐 쓰거나 재전송하지 않고, 실패로서 상위 계층에 넘어가요. MTRequestMessageService가 restartRequest를 설정하는 분기는 다음뿐이에요.

  • 401
  • 500
  • 대기 관련 400 또는 500
  • 420과 FLOOD_WAIT 등

나머지 RPC 오류는 같은 메서드의 끝에서 요청 완료 콜백을 호출해요. [5]

로그인은 마이그레이션 텍스트를 파싱하는 유일한 지점이에요. sendAuthorizationCode는 PHONE_, USER_, NETWORK_ 세 가지 접두사만 받아들이고, 이 접두사가 오면 미인증 계정을 재구성해 auth.sendCode를 재전송해요. 이 정규식은 FILE_과 STATS_를 명시적으로 제외해요. [6]

[6]

업스트림 Rust 엔진의 고정 서브모듈도 이 사실을 테스트 제약으로 삼고 있어요. 테스트는 FILE_MIGRATE_3, STATS_MIGRATE_1 등의 오류를 열거하고, 엔진이 원본 그대로의 실패 이벤트를 내며 인증이나 소프트 리셋 이벤트는 내지 않는다고 단언해요. 이 테스트는 이 엔진이 RPC 계층에서 호스트 대신 마이그레이션 대상을 고르지 않는다는 걸 증명해요. 다만 이 엔진은 macOS fork에 없어서 fork의 증거로 쓸 수 없어요. [7] [25]

macOS fork 검증

TelegramSwift의 submodules/telegram-ios는 고정 커밋 a24bbe45f9861f736a79916a50898512f751e0dc로 체크아웃되어 있어요. fork의 TelegramCore에서 마이그레이션 텍스트를 매칭하는 곳은 sendAuthorizationCode 하나뿐이고, PHONE_, USER_, NETWORK_ 접두사만 받아들여요. FILE_이나 STATS_와는 매칭하지 않아요. [18]

fork에서 나머지 계층은 이렇게 동작해요.

  • MTInternalMessageParser: RPC 오류를 MTRpcError로만 구성해요.
  • MTRequestMessageService: 303에 대해 DC 간 재전송을 설정하지 않아요.
  • V1과 V2 다운로드: 각각 식별되지 않은 오류를 범용 실패로 분류해요.
  • 업로드: 기존 네트워크의 데이터 센터를 고정해서 쓰고, 파트 오류를 범용 오류로 분류해요. [19] [20] [21] [22] [23] [24]

따라서 고정된 macOS fork에도 FILE_MIGRATE_X에 대한 범용 DC 간 폴백 재전송은 없어요. 아래 세 가지는 이 오류와 별개로 남아 있는 독립된 경로예요. 이 오류가 이들을 일으키지 않아요.

  • 알려진 리소스의 예방적 경로 선택
  • 권한 전이
  • CDN 리디렉션

알려진 미디어 DC의 예방적 라우팅

파일을 읽을 때는 보통 오류에서 DC를 알아낼 필요가 없어요. 클라우드 리소스는 datacenterId를 저장하고, fetchResource는 이 값을 fetchCloudMediaLocation에 전달해요. 그래서 첫 upload.getFile부터 이미 리소스 기록의 센터로 가요. [1]

[1]

다운로드 경로마다 DC를 받는 방식은 이래요.

  • V1: 전달받은 DC를 DownloadWrapper에 기록해요.
  • V2: .main(sourceDatacenterId)에 대해 upload.getFile을 보내요.

두 경로 모두 입력은 원래 리소스의 DC이고, MTRpcError에서 파싱해 낸 값이 아니에요. [2] [3]

알려진 대상 DC의 worker는 미리 권한 전이를 마쳐요. 이건 마이그레이션 오류에 대한 보상이 아니에요. MtProtoKit worker는 다음 두 조건이 모두 맞을 때 대상 ID를 requiredAuthToken에 넣어요.

  • 대상이 CDN이 아닌 DC예요.
  • 대상이 메인 DC와 달라요.

MTProto는 토큰이 일치하지 않는 걸 발견하면 대기 상태에서 멈추고 MTContext에 토큰 전이를 요구해요. [8] [9]

MTContext는 대상 DC별로 중복을 제거하며 MTDatacenterTransferAuthAction을 생성해요. 이 액션은 순서대로 이렇게 움직여요.

  1. 원본 DC에서 auth.exportAuthorization을 실행해요.
  2. 대상 DC에서 auth.importAuthorization을 실행해요.
  3. 성공하면 이 대상 DC의 권한 토큰을 저장해요. [10] [11]

[11]

그래서 요청을 보내는 쪽 코드(비즈니스 호출자)가 이미 대상 DC를 알고 있다면, worker는 요청을 보내기 전에 먼저 권한을 가져와요.

추론: 파일 마이그레이션에 폴백을 추가하려면 호출자가 다음을 차례로 해야 해요.

  1. 대상 DC를 명시적으로 해석해요.
  2. 대상 worker를 만들어요.
  3. 권한 전이가 성공하길 기다려요.
  4. 멱등성 규칙에 따라 끝나지 않은 파트를 다시 제출해요.

현재 소스에는 이런 호출자가 없어요.

다운로드, 업로드, CDN의 경계

다운로드는 V1과 V2 모두 FILE_MIGRATE_X에 전용 처리를 두지 않아요.

  • V1: FILEREF_INVALID, FILE_REFERENCE_, WEBFILE_NOT_AVAILABLE만 전용 결과로 매핑해요. 다른 오류는 모두 .generic으로 매핑돼요.
  • V2: 파일 참조 오류 두 종류(FILEREF_INVALID, FILE_REFERENCE_)만 참조 갱신으로 매핑하고, 나머지 오류는 .failure가 돼요. 이어서 가져오기 상태를 .failed로 설정해요. [3] [2]

networkRequestErrorPolicy는 FLOOD_WAIT와 내부 서버 오류 횟수만 관찰해요. 오류 코드나 오류 텍스트를 받지 않아서, 이 정책 계층에서 FILE_MIGRATE_X를 식별하는 건 불가능해요. [12]

[12]

같은 DC에서의 범용 재시도와 DC 간 재전송을 구분해야 해요.

  • Download.part를 직접 호출하는 옛 인터페이스는 실패하면 retryRequest가 이어져요. 이 연산은 같은 Download를 다시 구독하고, 그 datacenterId와 worker는 이미 고정되어 있어요. 그래서 같은 청크 요청을 원래 센터로 다시 보낼 수는 있지만, FILE_MIGRATE_X로부터 다른 센터를 얻을 수는 없어요.
  • V1의 MultipartFetch는 이 인터페이스를 호출하지 않고, 멀티플렉서 매니저를 통해 기존 대상에게 요청을 제출해요. 이 매니저는 오류를 구독자에게 그대로 전달해요.

그러므로 같은 센터로의 재시도라는 예외는 파일 마이그레이션 폴백이 되지 않아요. [3] [12] [17]

CDN 리디렉션은 RPC 마이그레이션 오류가 아니에요. 원본 DC가 upload.getFile에 대해 돌려주는 성공 생성자 fileCdnRedirect예요. V2는 이렇게 처리해요.

  • 원본 DC, CDN ID, 토큰, 키를 저장한 뒤 요청 대상을 .cdn(cdnData.id)로 바꿔 upload.getCdnFile을 호출해요.
  • cdnFileReuploadNeeded를 받으면 클라이언트는 원본 DC로 돌아가 upload.reuploadCdnFile을 호출해요.
  • CDN 요청이 실패하면 V2가 되돌아가는 대상은 여전히 앞서 저장한 원본 DC예요. 오류 텍스트가 가리키는 다른 파일 DC가 아니에요. [2] [13]

업로드에도 파일 마이그레이션 폴백은 없어요.

  • multipartUpload는 network.datacenterId를 고정해서 쓰고, 이어서 .main(datacenterId)로 saveFilePart 또는 saveBigFilePart를 보내요.
  • 이 두 업로드 진입점(saveFilePart, saveBigFilePart)은 400을 .invalidMedia로, 나머지 오류를 .generic으로 분류해요.

그래서 서버가 이 호출에 303 FILE_MIGRATE_X를 돌려줘도 현재 클라이언트는 업로드 센터를 바꾸거나 실패한 파트를 재전송하지 않아요. [14] [15]

NetworkTelemetry는 303을 .migrate로 분류해요. 하지만 이 분류 함수는 텔레메트리 분류만 반환해요. 요청을 소유하지 않고, 연결을 만들거나 재시도를 호출하지도 않아요. [16]
