macOS fork 장별 검증(08–15장)

08장부터 15장까지의 핵심 결론이 TelegramSwift 고정 fork에서 어떤 구현 상태인지 검증해요.

시스템 설계 · 검증과 보충 · 보충 32 · 도표 0 · 코드 발췌 6 · 인용 52 · 소스 기준선: TelegramMessenger/Telegram-iOS@f1dd7a2d, overtake/TelegramSwift@579cebbf

검증 대상: Postbox 스토리지 엔진, Postbox 뷰와 메시지 이력 모델, 미디어 리소스, 다운로드/업로드, 캐시, 종단 간 암호화와 로컬 보안, 푸시, 확장 프로세스와 다중 프로세스 협업, 통화 시스템, 다중 계정, 로그인, 구성 동기화, macOS 클라이언트의 시스템 계층

미검증 사항:

  • fork의 메시지 이력 공백(hole) 채우기가 실패한 뒤 업스트림처럼 두 번째 RPC 재시도가 없는지(업스트림 maxRetries는 0) 한 줄씩 대조하지 않았어요.
  • 알림 서비스 실행 시 사용 가능한 메모리 상한을 시스템이 어떻게 부과하는지.
  • macOS의 실제 서명, App Group entitlement, 배포 채널, 빌드 결과.

이 보충은 overtake/Telegram-iOS의 a24bbe45f9861f736a79916a50898512f751e0dc를 대조해요. 이 커밋은 업스트림 f1dd7a2dbd02cbbf513e75d5695d8d36d1cf5838보다 앞서요. 판정 라벨은 이렇게 읽어요.

  • “동일”: 핵심 메커니즘과 인터페이스가 fork 소스에서 보인다는 뜻이에요.
  • “차이 있음”: 코드 경로나 상수가 다르다는 뜻이에요.
  • “fork에 없음”: 이번에 해당 구현에서 그 메커니즘을 찾지 못했다는 뜻이에요.

핵심 결론fork 위치와 판정
AccountRecordId는 무작위 64비트 디렉터리 식별자이고 레코드에 임시 세션 ID가 있어요fork의 구조와 무작위 생성 방식이 일치해요. 동일. [41]
디렉터리 레코드 삭제는 secure:false를 써요fork의 record table이 그 삭제 매개변수를 유지해요. 동일. [42]
AccountManager는 직렬 트랜잭션에서 beforeCommit 뒤에 ValueBox를 커밋해요fork가 그 커밋 경계를 유지해요. 동일. [43]
인증 전과 인증 후 상태는 같은 account factory가 복원해요fork의 accountWithId가 두 종류의 상태 분기를 유지해요. 동일. [44]
전화 인증 코드는 auth.sendCode를 거치고, 비밀번호 요구는 SESSION_PASSWORD_NEEDED에서 변환돼요fork가 같은 호출과 오류 분기를 유지해요. 동일. [45]
App config는 hash로 가져오고, 변경이 없거나 오류이면 캐시를 덮어쓰지 않으며, 매시간 suspend aware로 폴링해요fork의 managedAppConfigurationUpdates가 같아요. 동일. [46]
macOS AuthController는 UI만 담당하고 인증 동작은 공유 코어로 들어가요UnauthorizedAccount의 state view를 저장하고 authorizeWithCode를 호출해요. 동일. [47]

이 장에서 fork와 다른 부분은 주로 이후의 API 필드와 생성 코드의 형태이고, 계정 모델은 아니에요. 기존의 “fork 미체크아웃” 제한은 삭제해야 해요. cleanupAccount가 각 종류의 디렉터리와 미디어 파일을 하나씩 삭제하는 부분은 이 보충에서 펼치지 않았어요. 그래서 그 세부 사항은 계속 미검증 사항으로 남겨요.

15장 macOS 클라이언트의 시스템 계층

핵심 결론fork 또는 TelegramSwift 위치와 판정
TelegramSwift는 package 경로로 fork의 TelegramCore, Postbox, SSignalKit을 참조해요PrivateCallScreen 매니페스트가 이 상대 경로 의존성을 직접 선언해요. 동일. [40]
컨테이너 루트는 App Group에서 오며, 비어 있는 새 디렉터리에서 옛 내용을 마이그레이션해요ApiEnvironment.containerURL과 migrate가 그 조건을 유지해요. 동일. [48]
계정 전환은 SharedAccountContext.switchToAccount로 현재 레코드를 갱신해요macOS 코드는 AccountManager 트랜잭션에서 current id를 설정해요. 동일. [49]
데스크톱 알림은 alert, badge, sound를 요청하고 peer와 최대 메시지 ID에 따라 정리해요UNUserNotifications의 권한 요청과 정리 로직이 일치해요. 동일. [50]
Sparkle 래퍼는 TelegramUpdater에 있어요AppUpdateViewController가 여전히 SUUpdaterPrivate 래퍼를 정의해요. 동일. [51]
크래시 표식은 두 타임스탬프의 차이가 10초 미만이면 비정상으로 판정해요CrashHandler가 이 알고리즘을 유지해요. 동일. [52]
submodules/telegram-ios와 submodules/tgcalls는 초기화되지 않았어요둘 다 현재 읽을 수 있고 커밋은 각각 a24와 5ddc예요. 원래 주장은 현재 체크아웃과 모순돼요. [40]

로컬에서 검증해 보니 TelegramSwift가 고정한 두 코어 서브모듈(telegram-ios와 tgcalls)이 이미 있어요. 그래서 15장은 “Gitlink만으로 추론”에서 “고정된 fork 소스를 읽었으나 더 새로운 업스트림과 같다고 볼 수는 없음”으로 바꿀 수 있어요. 이렇게 하면 08, 10, 11, 12, 13, 14장에 있던 같은 fork 미체크아웃 제한도 함께 풀려요.
